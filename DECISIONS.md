# Watchdog — Decision log

The dated record of architectural decisions, each operating within the **Invariants** in [ARCHITECTURE.md §15](ARCHITECTURE.md#15-invariants). An entry is the authority on its *specific* change — the rationale weighed and the tradeoff accepted — not on the general principle (that lives in the Invariants). For the current structure of the system, read ARCHITECTURE.md; read here only when you need the *why* behind a specific past decision.

**Appending:** add the next `### D<n>` at the **end** (ascending, newest last). Keep entries concise — a few sentences of rationale, then the tradeoff. A decision earns an entry only if it forecloses a future option or would read as a bug without the rationale; pure refactors belong in the commit message. When a decision establishes or revises an invariant, update the Invariants section in ARCHITECTURE.md in the same change.

### D1 — Local-first preprocessing

Source documents never leave the machine; no API cost for chew

**Tradeoff:** Bound by local compute for OCR/layout

### D2 — Deterministic code writes, model decides

Reproducible, testable, cheap bookkeeping; model reserved for judgement

**Tradeoff:** More Python surface to maintain

### D3 — ~~Isolated extractor subagent per document~~ **Superseded by D18.**

Kept the (model) orchestrator's context flat by extracting each doc in a throwaway subagent. Moot once the orchestrator became Python (no model context to keep flat)

**Tradeoff:** —

### D4 — Classification at extraction time, by the model (§6)

Accurate, near-free (doc already read), deleted the embedding subsystem

**Tradeoff:** `document_type` null until extraction

### D5 — Structured vs. synthesized note split (§7)

Mechanical merge is correct+free for facts; prose needs the model

**Tradeoff:** Two write paths

### D6 — Contradictions as a discrete cited section, verified at extraction (§7)

Verifiable claims; the extractor is the sole verifier (no orchestrator removal pass); chronological sort would be a worse timeline

**Tradeoff:** Extra section + extraction field; a bad callout isn't caught downstream

### D7 — Carryforward + gated entity-synthesis (§8)

Cost scales with contested entities, not all entities; fixes summary clobber and the within-batch race

**Tradeoff:** Single-new-mention entities only revised, not fully re-synthesized

### D8 — Fragments as a write-time byproduct (§8)

Synthesis input with zero extra extractor tokens

**Tradeoff:** Run-scoped scratch state in tmp

### D9 — Raw-then-canonical timeline files (§9)

Subagents write lock-free; merge deferred to one post-batch step

**Tradeoff:** Two file generations on disk

### D10 — MinHash near-dup, detect-only (§10)

Cheap local dedup signal; journalist decides

**Tradeoff:** Approximate similarity

### D11 — Separate lightweight manifest (§12)

Cheap candidate lookup in pre-flight

**Tradeoff:** A second index to keep in sync (done in `write_vault`)

### D12 — ~~Generate `records/_index.md` by scanning the per-vault records dir~~ **Superseded by D21.**

A static index file silently drifts from the skills it describes. Moot once the classify index is built in memory from the global catalog (D21) — no file to scan or keep fresh

**Tradeoff:** —

### D13 — Sectioned extraction for large documents (§5)

Documents over the token threshold don't fit one context; sequential page-range sections with a carried scratchpad + deterministic `merge-sections` preserve cross-section consistency

**Tradeoff:** Large docs are extracted serially (slower); needs overlap + merge-dedup

### D14 — ~~Timeline reconciliation + briefing in one finalize subagent~~ **Superseded by D18.**

Kept scratchpad prose and timeline NDJSON out of the model orchestrator's context. Moot under Python orchestration — `_post_ingest` reads them directly

**Tradeoff:** —

### D15 — Runaway guard + `ingest-abort` (§5)

A stuck subagent bails (`STATUS: failed`) instead of wedging the batch; clean bail leaves no partial vault writes, so the doc re-ingests cleanly

**Tradeoff:** A failed doc must be manually moved back from `queue/_failed/` to retry

### D16 — ~~Entity synthesis (§8) and finalize (§9) kept as separate subagents, not merged~~ **Superseded by D17.**

Kept the per-entity synthesis fan-out apart from the whole-batch finalize to avoid serializing entity work. Moot once the fan-out itself proved to be the cost problem and both merged into one post-ingest agent (D17)

**Tradeoff:** —

### D17 — Merge synthesis + finalize into one post-ingest subagent fed a Python-built bundle (§8, §9)

The per-entity fan-out launched one subagent per `count ≥ 2` entity (36 in a representative run), each paying startup + preamble cache-write to do a few hundred tokens of judgement — ~$5 of a $19 run. D16 feared merging would re-bloat context, but fragments are *compact digests* (D8), so one agent reading the whole bundle stays small; the cost win (one agent, one cached preamble) dominates the serialization cost. The bundle's `build_bundle`/`apply_bundle` survive into D18; only the surrounding subagent is gone

**Tradeoff:** A very large batch could need bundle splitting by token budget (not yet implemented)

### D18 — Python orchestrator; the model is called only for reasoning (#118 W3)

A Claude Code skill session *is* a model loop, so the orchestrator (and per-turn coordination) cost model tokens even for pure dispatch — the orchestrator alone ran $1–3+ of a representative batch, ~38–86% of pipeline spend was per-turn context re-send. Moving the loop to Python (`orchestrate.py`) calling the model only for classify/extract/synthesis/timeline-dedup/briefing removes that floor and lets each task route to a backend + tier (`model_client`, D-auth #119). Supersedes the subagent split (D3) and the off-orchestrator finalize (D14)

**Tradeoff:** Extraction now runs the Claude Agent SDK in-process and parallel concurrency is bounded by subscription/API rate limits (`extract_concurrency` knob); the `claude-api` backend is unproven until a metered key is used

### D19 — Force-section on whole-doc output overrun (§5)

Sectioning triggers on *input* size (`section_token_threshold`), but truncation is *output*-driven — a moderate-input, entity-dense doc overruns the model's output ceiling on the agent-SDK backend (which can't cap output), truncating the JSON and escalating the retry toward a pricier tier. On a multi-page doc whose whole-doc extraction is rejected, the orchestrator re-runs it through the sectioned path with a small forced budget (≥2 sections) to bound per-call output

**Tradeoff:** Adds one (failed) whole-doc attempt before the fallback; single-page docs can't be split, so they still just fail

### D20 — Configured model only — no automatic escalation; classifier model is its own knob

`model_client` originally bumped the tier up (haiku→sonnet→opus) on a JSON-validation failure. That makes ingest cost unpredictable and can silently spend opus money — the opposite of a budgeted pipeline. Now a failed call retries on the **same** configured model (the orchestrator's post-flight repair + D19 sectioning handle genuine failures), and the classify step gets its own `classifier_model` knob (default haiku) alongside `extractor_model`/`finalizer_model`, so each stage's model is explicit and stable

**Tradeoff:** A doc that a stronger model would have salvaged now fails instead of auto-upgrading — the user opts into a stronger model deliberately via config

### D21 — Record skills are global, not per-vault (`skills_catalog`)

Copying skills into every vault was a holdover from the Claude-Code-skill ingest, which needed them under `.claude/commands/` for discovery. The Python orchestrator (D18) just reads the file, so the copy was vestigial and created drift (each vault stale until `refresh-skills`). Skills now live in the package + `~/.watchdog/skills/records/` (user overrides) and are read directly; the classify index is built in memory (supersedes D12); per-skill `description:` frontmatter lets a user-added skill set its own index line. Pinning (`--skill`/`default_skill`, a name or path) and `watchdog show-skills` round it out. Pre-production, so vault-local copies are simply ignored (strictly global) rather than migrated

**Tradeoff:** Loses per-vault skill freezing/customization; mitigated by `--skill PATH` for one-offs and by stamping the skill used into each document's note + registry (`record_skill`) for provenance. Custom skills in `~/.watchdog` aren't carried with a shared vault

### D22 — Extractor emits structured **evidence fragments** instead of prose `analysis`; optional verbatim `quote` on fragments and `key_facts` (#107) **— the extractor no longer emits fragments directly (D26); they are reconstructed from tagged `key_facts`, but everything downstream (the structured-claims-feed-synthesis digest, the `## Analysis` render) is unchanged.**

The per-entity `analysis` prose was thrown away and rewritten by synthesis for every multi-mention entity (D7/D17), so the extractor did prose work twice. Replacing it with `{claim, page, confidence, reason}` fragments gives the synthesizer a clean, page-anchored, citable digest to compose from rather than re-prosing prose — and single-mention notes render the claims directly under `## Analysis`. Quotes are *captured* at extraction only when the wording is significant, and on entity fragments are *surfaced* into synthesized prose only in exceptional cases (the synthesis prompt gates this); on `key_facts` the quote renders verbatim in the document note (terminal, reader-facing — the strongest placement). This is a **quality/citability** change, not a cost trim (structured fragments cost slightly more output tokens than the prose they replace) — the cost trim is the separate #127

**Tradeoff:** More structured extractor output; a captured quote against garbled OCR isn't verified to appear on the page (that check is the deferred #106 evaluator); existing notes keep their old prose `## Analysis` until the entity is next extracted

### D23 — Post-ingest is a re-runnable `finalize` step over per-run on-disk inputs (#135)

Post-ingest (synthesis + timeline + briefing) calls the model, so a rate limit can interrupt it *after* extraction has already written the vault — and `ingest_setup` wipes the fragment queue at the next ingest's start, so a re-ingest would silently drop the un-synthesized batch. Post-ingest is now `orchestrate.finalize`, fed inputs that persist in `tmp` (entity fragments + per-doc `result_*.json` + scratchpads); `watchdog ingest` calls it at its tail, and `watchdog finalize` re-runs it standalone to complete an interrupted batch. A clean pass clears the inputs (idempotent, and fixes a latent scratchpad-accumulation bug where briefings re-included prior runs); an interrupted pass leaves them for retry. A new `watchdog ingest` over a pending batch prompts to **merge** (keep the inputs via `wipe_pending=False` so both batches finalize together), **finalize** first, or **discard**; `watchdog status` flags a pending batch

**Tradeoff:** No cross-run finalization queue beyond the merge prompt; synthesis re-runs are idempotent (bulk overwrite), so a partial finalize is safe to repeat

### D24 — Roles are extracted by `target_id` only; `target_name`/`target_type` are re-inflated deterministically (#140)

Extraction output is ~95% of run cost and roles were the single largest field — and ~43% of the roles payload was the target's `target_name`/`target_type`, both *derivable from `target_id`* via the registry, re-typed by the model on every role (e.g. an 86-char case name repeated across a dozen roles). The extractor now emits roles by id; `write_vault._resolve_role_targets` fills name/type from this batch's entities + the registry right after id reconciliation, so every downstream consumer (note links, pre-flight context, synthesis digest) is unchanged. First concrete cut from #140 — moves derivable data out of paid model output into free deterministic code

**Tradeoff:** A dangling `target_id` (no matching entity) falls back to the id as name + `Unknown` type; the win is only realized while extraction stays on a metered tier (Sonnet output is the cost)

### D25 — `confidence` is omitted when `high`; absent ⇒ `high` (#140) **— field reworked into `basis` by D34; the omit-default mechanism survives, the 4-level scale does not.**

Measured across a 5-doc run, **99% of all confidence values were `high`** (411 rendered, 8 non-high). Requiring it on every fact/role/event/key-fact paid model output to restate the default ~99% of the time (~6% of extraction output). The extractor now emits `confidence` only for `medium`/`low`/`disputed`; the schema makes it optional and every consumer defaults absent → `high`, so notes render identically and the rare exception stands out instead of hiding in a sea of `high`. Same omit-defaults pattern extends to `page` (omit when no marker) and empty arrays

**Tradeoff:** Defaulting absent → `high` is the *optimistic* direction — a forgotten mark silently reads as `high` — but empirically the model flagged all 8 non-high cases, so exposure is ~8-in-411. Whether `confidence` is well-calibrated at all (≈always `high`) is a separate quality question (#143)

### D26 — Unified **fact primitive**: the model emits each material fact once on `document.key_facts`, tagged with `entities` + an optional `date`; postflight fans it back out (#140)

The extractor restated the same fact up to three times — as a `document.key_fact`, as each involved entity's `evidence_fragment`, and (if dated) as each entity's `timeline_event` — plus a per-entity `summary`, so a 5-page order emitted ~4× the source text in JSON (32K chars from 7.7K of Docling markdown). That redundancy was rational only because the Docling text was **discarded** after extraction, making the JSON the sole text record. D26 retains the full text in the morgue as a sibling `<name>.md` (deterministic, $0), then collapses the restatement: the model emits a fact once with `entities` tags (who it's about) and an optional `date` (when it occurred); `postflight.explode_key_facts` deterministically reconstructs the per-entity `evidence_fragments` and `timeline_events` the writers already consume, and `stage_timeline_events` reads the dated facts directly. Entities keep only the graph layer (identity, aliases, roles, contradictions); no per-entity summary/fragments/timeline. `key_facts` is materiality-driven with no fixed count. Stacks on D24/D25. Synthesis is now gated on **project-wide recurrence** (`appears_in ≥ 2`) rather than batch-local mention count, so an entity recurring across separate batches/years is promoted; single-document entities are deterministic stubs with no Summary section (§8)

**Tradeoff:** A single-document entity gets no synthesized summary at all (by design — its facts sit in `## Analysis`), and a model only ever judges an entity from one document plus carried prose, never a fresh re-read of all sources (that's `/watchdog-entity`). A dated fact must be *tagged* to reach an entity's per-entity timeline (the global timeline still gets it untagged). Timeline recall now depends on the model attaching `date` to occurrence-facts rather than filling a dedicated field

### D27 — Skip exact duplicates at chew, not just at ingest (#146)

Re-extraction was already a no-op — `preflight` skips a sha already in `documents.json` before any model call (§5). But the wasteful part remained upstream: a re-dropped file was still re-OCR'd, queued, then quietly skipped at ingest. Chew now hashes each file first and, if the sha is already ingested / already queued / a repeat within the batch, moves it to `_INCOMING/_SKIPPED/` with a warning instead of OCR'ing it. Chosen over a content-addressed *text cache*: skipping is simpler (a hash + set lookup, no persistent store or version-invalidation), covers the same cases, and is the correct intent — "I already have this document," not "re-OCR it cheaply."

**Tradeoff:** Exact-bytes only — a near-duplicate (re-scan, different export) has a different sha and still chews (the MinHash flag handles that, §3). Files dropped *simultaneously* with identical bytes keep the first and skip the rest, which is right for true duplicates but would also skip a deliberately-reprocessed copy

### D28 — Task-prompt prose lives in `prompts/*.md` templates, in a **separate directory** from record skills

`prompts._text` loads a template (cached) and `_render` substitutes `{{token}}` placeholders; the builders still own all data assembly and conditionals in Python (model copy out of code, logic in code). The load-bearing constraint is the separate directory: `skills_catalog` only ever scans `skills/records/`, so a prompt template never leaks into the classifier index or `watchdog show-skills`. Packaged like the skills `.md` (hatchling bundles non-`.py` files under `src/watchdog`)

**Tradeoff:** Editing a template changes model behavior with no type-checking — prompts are plain-text copy to be reviewed like prose. Whitespace was naturalized for markdown, so the assembled prompt is semantically identical but not byte-identical to the old string literals

### D29 — Stop round-tripping deterministic document fields through the model; stamp them in Python (#140 family)

The extractor was asked to echo back document **identity** (`sha256`, `filename`, `original_path`, `page_count`) — values the pipeline already holds from `preflight` — and to re-derive **provenance** (`source`, `obtained`) by parsing the `.yml` sidecar text it was handed. Both are deterministic: Python knows the identity, and the sidecar is structured YAML. `orchestrate._stamp_document` now sets all six on the extraction right before post-flight (`_sidecar_provenance` parses the sidecar with `yaml.safe_load`, coercing an auto-parsed date back to a string); the schema drops `sha256`/`filename` from `_DOCUMENT.required` (kept optional in `properties` so the stamped dict validates) and the extract/section prompts no longer instruct the model to produce them. The sidecar text still reaches the model as extraction context (its free-form `notes`). Same lever as D24/D25 — derivable data out of paid output — plus a correctness win: `write_vault` keys the vault write on `document.sha256`, so stamping removes a latent desync if the model ever mis-transcribed the 64-char hash. Also dropped the never-read `document_type` from the classify call's schema/prompt (it was discarded; the `document_type` the vault uses is the separate extraction-stage field)

**Tradeoff:** Provenance parsing is now strict YAML rather than the model's lenient reading — a malformed sidecar yields no `source`/`obtained` (returns `{}` on `YAMLError` or a non-mapping) instead of a best-effort salvage; the documented `key: value` sidecar format is unaffected

### D30 — `document_type` is deduped against a per-vault registry (match-or-coin), its slug is derived, and dead/duplicate type fields are dropped (#140 cleanup, stacks on D29)

An audit of the extract schema found three more issues with the document-type fields. (1) **Drift:** `document_type` is a free string the model coined per document with no guidance, so the same instrument came out worded differently across docs — fragmenting the `watchdog status` "Documents by type" tally. Fixed with the same dedup pattern the pipeline already uses for entities: `preflight` collects the distinct types already in `documents.json` (the registry is the vault itself — no new file), passes them as `KNOWN_DOCUMENT_TYPES`, and the prompt instructs reuse-verbatim-or-coin-new. (2) **Redundancy:** the model emitted both `document_type` (descriptive, e.g. "Annual Report") and `morgue_document_type` (the slug, e.g. "annual-report") — the same fact twice; `_stamp_document` now derives `morgue_document_type = slugify(document_type)` and it leaves `EXTRACTION.required`. (3) **Dead field:** `near_duplicate_of` was in the model schema but never prompted and always sourced by Python from the MinHash pass — removed from the model-facing document schema. `title`/`document_type`/`date_of_document` (schema-required or note-rendering, but previously undescribed in the whole-doc prompt) are now documented in `extract_instructions.md`

**Tradeoff:** The known-types list is a `preflight` snapshot, so two genuinely-new types in the **same parallel batch** can still be coined inconsistently (neither is in `documents.json` yet) — the same race the entity layer reconciles post-merge; a type-reconciliation pass is deferred until it bites. The registry only shapes new docs going forward; types coined before this change aren't retroactively normalized

### D31 — Timeline-dedup returns kept **indices**, not echoed event objects; and collapses only pure restatements, never divergent accounts

The same-date dedup step (post-ingest, only on cross-document date collisions) had the model echo back the full kept event objects — re-typing a 64-char `source_sha256`, `page`, `confidence`, and the event text per event, all of which Python already holds. It now returns `keep` (a list of indices); `orchestrate._select_kept` maps them to the **original** objects (deduped, order-preserving) and falls back to keeping **all** events on any unusable response (non-list / out-of-range / empty), so dedup can drop a redundant restatement but never silently wipe a date. The criterion was also tightened: only **pure restatements** (same facts, different words) collapse to the most precise wording; any event adding a material fact, detail, or distinct perspective is kept — including two sources describing the same day differently (e.g. opposing legal teams), which stay as separate rows each attributed to its own `source_sha256`. The model no longer rewrites event text (indices only), so kept events are preserved verbatim

**Tradeoff:** "Merge with attribution" is realized as co-dated, separately-attributed rows, **not** a single fused event — the timeline event model carries one `source_sha256` per row, so a literal one-row merge citing multiple sources would need a schema change (multi-source events) and is deliberately not done; it would also blur the clean per-document provenance the vault relies on. Dedup correctness still rests on the model's same-occurrence judgment (unchanged risk from before), now biased toward keeping

### D32 — Advisory page-coverage warning flags a likely skim

A classic LLM failure is not reading a long document to the end. Extraction can't *enforce* reading, but `key_facts` carry a `page`, so `orchestrate._coverage_warning` deterministically flags a probable skim: for a document of ≥ `_COVERAGE_MIN_PAGES` (8) pages, if no fact cites anything past roughly the first half (`_COVERAGE_TAIL_FRACTION`), it prints a yellow `⚠` after the `OK` line and logs a `WARN`. Pairs with the read-every-page instruction now in `extract_instructions.md` (the prompt nudges; this catches when the nudge failed). Purely advisory — never fails the extraction, since a document whose material genuinely sits up front trips it too. Real *enforcement* of coverage remains structural (large-PDF sectioning, the `chunk_size` knob — §6), not this heuristic

**Tradeoff:** Heuristic with false positives (front-loaded-but-complete docs) and false negatives (a model that fabricates a single back-page fact passes); it is a review prompt, not a guarantee. A doc with no page anchors at all can't be assessed and is silently skipped

### D33 — Briefing reads figures + chronology from `key_facts`; the scratchpad is slimmed to forward-looking leads (#150)

The per-document scratchpad — free-text notes the model wrote to feed the end-of-batch briefing — was ~19% of one doc's extraction output, and ~half of it (its "Key figures" and "Chronological" sections) hand-retyped facts the model had already emitted structurally in `key_facts`, paying to state the same facts twice as prose. The briefing couldn't simply drop those sections, because it **only read the scratchpads** and was never handed `key_facts`. So this is a swap, not a trim: `_compact_result` now carries a `key_facts` projection (`_briefing_facts` → fact + date only, dropping page/confidence/entities/quote as narrative noise), the briefing prompt draws figures and chronology from those structured facts, and the scratchpad/`observations` instructions are slimmed to *forward-looking* notes only (leads, open questions, cross-document threads) with figures/chronology/contradictions explicitly excluded. Stacks on D26 — same principle of not emitting prose that duplicates structured data. The compact result is also the standalone-`finalize` input (D23), so putting `key_facts` there keeps an interrupted batch's briefing fully reconstructable from disk

**Tradeoff:** Briefing input gains the (deduped) `key_facts` and loses the scratchpads' restated figures — roughly a wash on tokens, a net output cut at extraction. "Leads only" is a softer instruction than a structured field, so thin or empty scratchpads are possible (an empty scratchpad just yields no notes file for that doc); contradictions still reach the briefing via the separate `contradiction_flags`, not the scratchpad

### D34 — `confidence` (4-level) → `basis` (`stated`/`inferred`) — provenance, not graded certainty (#143)

An audit of the 4-level `confidence` field (D25) found ~99% of values were `high`, raising the question of whether the field carried signal. The diagnosis: the scale conflated two axes and overpromised on a third. (1) `high`/`medium`/`low` claimed to grade *inference depth* (none / one step / multi-step), but there's no evidence the model discriminates one-step from multi-step, and the journalist's action is identical for any inferred fact — *verify it*. (2) `disputed` is not a confidence level at all but a *cross-document conflict* signal, fully redundant with the `[!contradiction]` mechanism (and never emitted in the sample). So the field collapses to the one distinction that is both real and decision-relevant: did the document **state** this, or did the model **infer** it? The field is renamed `basis` with enum `stated`/`inferred`, keeping D25's omit-default (absent ⇒ `stated`, the overwhelming default — so the model emits `basis` only for the rare `inferred` exception). `disputed` leaves the field entirely (conflicts live only in `[!contradiction]`); the contradiction gate is retightened from "both sides high or medium" to "both sides stated". Renderers now show only the marked exception — `*(inferred)*` — across key_facts, per-entity claims, timeline events, and roles (fixing a D25-era inconsistency where three of four renderers printed `confidence: high` on every line, burying the signal the design meant to surface). A binary keyed on "is this literally on the page?" is also more honestly calibrated than a self-rated scale — a sharper, checkable question is harder to reflexively max out

**Tradeoff:** Loses any ability to grade inference *depth* (a deep chain reads the same as a one-step guess) — judged not worth keeping, since page cite + quote let the reader gauge that and the reader's action doesn't change with depth. Pre-production, so no migration: notes written under the old scale keep their `confidence: <level>` text until the entity/document is next extracted. Absent ⇒ `stated` is still the optimistic direction — a forgotten mark reads as directly-stated — but the question "is it on the page?" is more concrete than "rate your confidence," which should reduce silent misses

### D35 — Watch-word alerts are a deterministic post-ingest text scan, no model (#165)

A user wants to be alerted when a newly-ingested document mentions a tracked name/company/address/term. This is done entirely in deterministic Python — no model call — because the scannable material already exists for free: D26 retains each document's full text as a page-aligned morgue `<stem>.md` (with `<!-- PAGE N -->` markers). `pipeline/watchlist.scan` reads the vault-root `watchlist.md` (one term per line; `#` comments; literal terms matched case-insensitively on word boundaries via lookarounds so leading/trailing punctuation still matches; a `/.../`-wrapped line is a regex), greps this run's `ok` documents, and records term + document + page (resolved from the nearest preceding marker) + a bolded context snippet. Each hit is *annotated* — not gated — with the matching registry entity when `m.group(0)` resolves against `manifest.json` (name/aliases), so the text scan stays complete while gaining entity links where available. It runs as step 4 of `_post_ingest` (after the morgue text and registry both exist), writes `briefings/alerts-<date>.md` (dated, append-per-run, matching the `surface-<date>` convention) and prints a console summary; an empty/absent `watchlist.md` is a silent no-op. Chosen over (a) entity-only matching (recall gaps — misses terms the model never surfaced as an entity) and (b) a chew-time pre-scan (would predate the registry, losing annotation)

**Tradeoff:** Matches only what survived chew/OCR into the morgue text, and a term not extracted as an entity gets no link (by design — completeness comes from the text layer). Scans only this run's documents by default — but `watchdog watchlist` (#220) now covers the deferred retro-scan case: it builds a synthetic all-`ok` results list from every `documents.json` entry and feeds it straight into the same `scan`/`write_alerts`, so a term added after documents are already in the vault can still be swept against the whole corpus on demand. That command has no memory of previous scans, so it re-reports every past hit on each run — acceptable, since it's a deliberate on-demand sweep, not a background job. Per-document matches for one term are capped at 50 to bound a too-broad regex. The other end of the same problem — an empty `watchlist.md` at the start of an investigation, relying on the reporter to remember to seed it — is now covered by `/watchdog-context` (#229): it proposes candidates from the same material it already synthesizes for `context.md`, for explicit accept/edit/skip, and appends approved terms via the new internal `watchdog watchlist-add` (deterministic dedup + append in Python, not the model hand-editing the file — I1)

### D36 — Per-stage **reasoning-effort** knobs as an output-token cost lever (#163)

The #140 validation run concluded the one remaining cost lever was *output-token volume per doc*, and thinking tokens **bill as output**. Neither backend set any thinking parameter, so the model thought at each backend's default (`high`). `extractor_effort` and `finalizer_effort` (`low`/`medium`/`high`, default `high`) are now config keys — mirroring the per-stage *model* knobs — resolved in `model_client` and mapped to each backend's native control: `output_config.effort` (claude-api, composed into the same dict as the structured-output `format`) and `ClaudeAgentOptions.effort` (claude-agent-sdk). `_resolve_effort` drops the knob on Haiku-tier models (which reject `effort` with a 400 — so the Haiku **classify** stage has no knob) and treats `high` as "no override" (it ≡ the model default), so an unconfigured pipeline sends nothing and behaves exactly as before. The lever lives in `model_client` (the backend-abstraction layer), not the orchestrator, because the available controls are provider-dependent (#125/#137): the config key is an abstract `low`/`medium`/`high` *intent* that other backends can map to their own reasoning-effort parameter (OpenAI `reasoning_effort`, etc.) or ignore. Operates within I4 — explicit knob, stable default, no auto-escalation

**Tradeoff:** The deliverable per the cost-reduction thread is a measured A/B (default vs `extractor_effort=low`/`medium` on a fixed corpus via `scripts/analyze-session`); the knob ships structured and tested, but whether a lower effort actually cuts cost *without* degrading extraction quality is a numbers question to settle on a real run. `xhigh`/`max` (Opus-only) are deliberately not exposed — the lever is for spending *less*, and `low`/`medium`/`high` is the portable set across providers

### D37 — OpenAI-compatible backends (OpenAI, DeepSeek) behind a provider abstraction (#125)

Output tokens are ~88% of extraction cost and non-Claude providers are dramatically cheaper there, so the pipeline needs to route to them. D36 had already moved the *effort* knob to an abstract `low`/`medium`/`high` intent precisely so other providers could slot in; this realizes that. **Abstraction:** (1) a per-provider **effort policy** (`_EFFORT_POLICY`) translates the intent to each provider's native control — Claude `output_config.effort` with `high`≡default and Haiku-rejects, OpenAI `reasoning_effort` on reasoning models only (and `high` is *not* a no-op there), DeepSeek nothing (the reasoner thinks by default; no portable knob) — so the shared `acomplete_json` path never hard-codes one provider's semantics; (2) `_resolve_backend_auth` resolves the key per backend — Claude backends keep the subscription/api-key mode, others read their own stored key (`watchdog auth set openai|deepseek`) independent of the Claude mode, so a user with only an OpenAI/DeepSeek key can run those backends; (3) a single `_openai_complete_async` (httpx Chat Completions, no new SDK dep) serves both providers, selected by base URL via `functools.partial`. Structured output uses portable JSON-object mode + schema-in-prompt + the existing validate/retry shell (full `json_schema` mode isn't universal). `cmd/auth.py` already had a `_PROVIDERS` table, so OpenAI/DeepSeek are additive there. **User-facing selection:** each stage's existing model knob (`extractor_model`/`finalizer_model`/`classifier_model`, config or `--*-model` flag) accepts a `backend:model` form — `claude-api:opus`, `openai:gpt-5-mini`, `deepseek:deepseek-chat` — parsed by `ingest._resolve_stage` into `(backend, model)` and threaded through `orchestrate.run` to each stage's `acomplete_json`; a bare tier (`sonnet`/`opus`/`haiku`) keeps the stage on Claude routed by auth mode. One knob carries both halves so a stage can't be half-configured. Watchdog stays Claude-by-default; other providers are opt-in per stage. **Deferred:** a Claude fallback on invalid non-Claude output, and full pricing fidelity

**Tradeoff:** Quality on dense legal/financial extraction is unproven (the issue's caveat), so the defaults stay on Claude — a non-Claude backend is used only when the user selects it, and there's no automatic fallback if it returns junk after retries (it just fails the doc, like any backend). Pricing is approximate and output-only (DeepSeek's cache-hit input discount isn't modelled; OpenAI rates aren't populated, so cost reports None there). `max_tokens` (not OpenAI's newer `max_completion_tokens`) is sent, so OpenAI *reasoning* models would reject it — fine for DeepSeek and OpenAI chat models. The reasoning-model detection for `reasoning_effort` is a substring heuristic (`gpt-5`/`o1`/`o3`/`o4`/`reasoner`)

### D38 — Corpus search indexes overlapping sub-page **passage windows**, not whole pages; corpus and notes are separate streams; bge query prefix + `+`/`-` arithmetic + advisory threshold (#138)

The per-page index (one vector per page) was too coarse for concept-to-passage search — a page averages many topics into one vector and dilutes a short query. Borrowing Semantra's windowing, `add_document` now splits each page into overlapping word windows (`_WINDOW_SIZE`=128, `_WINDOW_OVERLAP`=16) and stores one vector per window tagged with its page; windows never cross a page boundary, so each passage keeps an exact page cite and the matched window *is* the citable span (no separate highlighting pass). Three smaller fixes ride along: (1) **bge asymmetric retrieval** — short queries are embedded with the model's instruction prefix (`_QUERY_PREFIX`), passages without one, a free recall gain the old symmetric path left on the table; (2) **`+`/`-` associative queries** — `_parse_query` splits a query into positive/negative phrases (a sign counts only after whitespace, so `anti-bribery` stays whole) and the query vector is `Σpos − Σneg`; (3) **separate corpus/notes streams** — `search(scope=)` ranks source passages apart from synthesized notes so prose never dilutes source ranking, surfaced as two sections in `watchdog search`, with `min_score`/`--threshold` to drop weak hits. The model stays `bge-small-en-v1.5` by default but is now an `embed_model` knob: it already beats Semantra's mpnet on retrieval, the real lever was granularity not model size, and the genuinely-stronger 2025 models (Qwen3-Embedding, EmbeddingGemma) aren't in fastembed yet — the knob is the forward door for when they are. Indexing stays deterministic and on-machine (I2)

**Tradeoff:** Word-count windows approximate true tokenization (fastembed has no exposed tokenizer split), so window sizes are roughly, not exactly, 128 tokens. Pre-production, no migration: the old per-page `docs/` vectors are simply re-written as passages on the next chew (and the legacy monolithic-index migration was dropped — its per-page target no longer exists). Cosine still has no universal cutoff, so the threshold is advisory and corpus-tuned, and a `+`/`-` query shifts the score scale lower (judge those by ranking). Changing `embed_model` requires a full rebuild — vectors from two models aren't comparable — but not a re-chew: `watchdog reindex` (D53) does it from disk. A window never spans a page break, so a concept split across the page boundary is only captured within each page's own windows

### D39 — `watchdog export` emits the entity graph as Neo4j-import CSV / Cypher, fully deterministically from `entities.json` (#69)

The relationship graph is already structured in the registry (`roles` per entity), so external network analysis (Neo4j, Gephi, NetworkX) needs only a read-and-emit step — no model, no markdown parsing, on the deterministic side of I1. Two non-obvious filters keep the output correct: (1) **only stated-direction roles are emitted** — `write_vault._add_reverse_role` stores a mirrored `is_reverse: true` copy of every relationship so the entity notes can render both sides, but emitting both would double every edge; the export drops reverse roles and keeps the original direction; (2) **edges to never-profiled entities are skipped** — a `target_id` can point at an entity that was named but never got its own registry record, and `neo4j-admin import` rejects an edge whose endpoint isn't in `nodes.csv`. Columns track the current schema, not the issue's 2026-06-10 sketch: per-entity `confidence` no longer exists (D25/#143 replaced it with `basis`), so nodes carry `doc_count` (= `len(appears_in)`) and edges carry `basis`/`date_range`/`source_page`

**Tradeoff:** Graph quality is bounded by ingest-time entity dedup — the same person under name variants that weren't resolved appears as separate nodes, which the export can't fix (an existing vault limitation, not an export bug). The Cypher path uppercases/sanitizes relationship strings into rel-type tokens and backtick-quotes labels, so two source relationships that differ only in punctuation collapse to one type

### D40 — Deterministic whole-vault **lead sweep** (`pipeline/leads.py`): named-but-unprofiled, recurring-isolated, unresolved-contradiction — surfaced post-ingest and via `watchdog leads` (#155, slice 1)

Karpathy's "LLM Wiki" lint surfaces *what's missing* across the whole corpus; the cheapest, highest-value slice of that is pure graph analysis needing no model, so it lives on the deterministic side of I1 alongside the watch-word scan (D-watchlist/#165). Three registry-only signals: (1) **named but never profiled** — a `role.target_id` absent from `entities.json`; because every *extracted* entity becomes a registry record (so document `key_facts`/`entities_extracted` tags can never dangle), the *only* place a name appears without a record is a relationship target the extractor named but didn't profile — making this a precise, low-noise lead rather than a fuzzy coverage heuristic; (2) **recurring but isolated** — `appears_in ≥ 3` with empty `roles`, the registry-only proxy for thin coverage that avoids reading note bodies and gates out the single-mention long tail; (3) **unresolved contradictions** — the per-ingest contradiction flags already on the entity, just *listed* standing. `leads.scan` runs in `_post_ingest` after the watch-word scan, snapshotting `briefings/leads-<date>.md` (overwrite, not append — current-state, not an event log) and printing a `⚠`-line; `watchdog leads` re-runs it on demand and a bare `watchdog` with nothing pending nudges the count. The vault resolver shared with `export` was promoted to `cmd/base._resolve_vault`

**Tradeoff:** Scope is deliberately the *deterministic* slice only: the model-driven whole-vault pieces — a cross-document contradiction re-check (beyond per-batch) and stale/superseded-claim detection — are a separate follow-up (#155 slice 2) that consumes these signals as cheap pre-filters. The "named but never profiled" name falls back to the bare `target_id` slug when no entity ever supplied a `target_name`, so a lead can read as a slug rather than a display name. The isolated threshold (`_ISOLATED_MIN_DOCS = 3`) is a fixed heuristic, not yet a config knob

### D41 — Activate `queries/` as the compounding-exploration log: `/watchdog-query` auto-persists substantive answers, which graduate to `wiki/` threads (#155, slice 3)

Karpathy's sharpest strategic point is that valuable query outputs should be *filed back* so explorations compound instead of re-deriving from scratch each session. The vault already shipped an inert `queries/` directory and `wiki/` threads; slice 3 wires the loop with no new Python — pure skill/template prose, the cheapest #155 slice. `/watchdog-query` now writes synthesised, citation-preserving answers to `queries/<slug>.md` (create or update, never a near-duplicate) and promotes a finding that reaches the wiki threshold (≥2 entities tied by ≥2 documents) to a `wiki/` thread; a standing rule in the vault `CLAUDE.md` makes the reflex session-wide, not only on an explicit `/watchdog-query`. `Write`/`Edit(queries/**)` and `Write`/`Edit(wiki/**)` were added to `_VAULT_PERMISSIONS` so the habit doesn't prompt (wiki writes were previously unauthorised — an existing gap closed here). The `queries/` log and `wiki/` threads form the two-tier compounding substrate (transient explorations vs matured angles)

**Tradeoff:** Persistence is auto with a *substantive-vs-trivial* filter the model judges (skip one-line lookups), not a deterministic gate, so a borderline answer may or may not get a page. Being skill prose, the behaviour can't be unit-tested like the deterministic slices — correctness is a prompt-adherence question, not a pytest. Existing vaults need `watchdog refresh-skills` (for the updated skill + CLAUDE.md) and the new permission lines before the loop runs without prompts. The model-driven whole-vault lint (slice 2) and image-as-evidence (slice 4) remain separate follow-ups

### D42 — Native Obsidian Bases dashboard, replacing Dataview (#184)

The vault dashboard — the live tables of most-mentioned entities, recent documents, people, companies, and possible duplicates — moved from Dataview queries embedded in `index.md` to a native Obsidian **Bases** file (`dashboard.base`); `index.md` is now a thin landing page that links to it. Bases is a *core* Obsidian feature (1.9+), so the dashboard renders with no community-plugin install and no "restricted mode" step — removing the only onboarding friction the dashboard carried, and dropping a third-party dependency. The scaffold writes `dashboard.base` deterministically at `watchdog new`, alongside `graph.json`/`app.json`, from the entity/document note frontmatter the pipeline already stamps (I1/I2: no model, no network). Recurrence (an entity's `appears_in` count) is surfaced as a sortable **column** rather than a declarative sort, because Bases has no documented `sort:` key — its tables sort interactively on column click. Two review-oriented views were added that Dataview lacked: single-source entities (`appears_in.length == 1`) and possible duplicates.

**Tradeoff:** loses Dataview's declarative auto-sort — the user clicks a column header to sort, rather than the view opening pre-sorted — and the dashboard now requires Obsidian 1.9+ (Bases predates that only as beta). In exchange the dashboard works out of the box with zero plugin setup. Existing vaults keep their old Dataview `index.md` until re-scaffolded; `watchdog refresh-skills` does not touch vault root files, so migrating an existing vault is a manual drop-in of `dashboard.base` (or living with the Dataview version, which still works if the plugin is installed). Contradiction-status and other note-*body* signals can't be surfaced (Bases queries frontmatter only); those stay with `/watchdog-health` (#188).

### D43 — Hybrid corpus retrieval + contextual prefix; search index built at ingest (#185)

The corpus search was pure dense cosine over passage windows (D38). #185 makes it a three-stage hybrid: a **BM25** sparse leg fused with the dense leg by reciprocal-rank fusion, then a local **cross-encoder reranker** (`rerank_model`, default `bge-reranker-base`) over the fused pool. BM25 recovers the exact tokens embeddings blur — case numbers, dollar figures, statute cites, names — which is exactly the investigative query shape; reranking is the single biggest precision lever (Anthropic's contextual-retrieval research). BM25 is computed in-memory from the already-loaded passages (no persisted sparse index, no staleness); the reranker is a second local fastembed model — pre-fetched by `watchdog setup` alongside the embedder/Docling models, else downloaded on first search — and is the only new dependency, gated behind `rerank_model` (set `none` to disable) and per-query `--no-rerank`; if it can't load, search degrades to the fusion order rather than failing (announced once, not silent). The hybrid applies only to `scope="corpus"` — notes (synthesized prose) stay cosine, and `scope="all"` keeps the legacy cosine merge. Each result's `score` stays the cosine value so the `--threshold` cutoff keeps its meaning even though fusion/rerank set the order.

Anthropic's method also prepends an LLM-written **contextual prefix** to each chunk; watchdog builds that prefix **deterministically** from extraction output (the document's title, type, and named entities) — no per-chunk model call (I1). That forces a move: passage embedding ran at **chew**, before extraction, so the prefix's inputs didn't exist yet. Corpus embedding therefore moved from `preprocess.py` (chew) to `write_vault` (ingest), where title/type/entities are known. The index is now wholly an ingest product, like the notes already were; it stays fully local, so I2 holds.

**Tradeoff:** the reranker adds a ~300 MB local model and first-search latency (both opt-out-able). The deterministic prefix is cruder than an LLM-written one and could, in principle, slightly homogenize same-document windows; it was chosen for $0 cost and is reversible (re-ingest without it). Moving embedding to ingest means a chewed-but-not-ingested document is not searchable (acceptable — its notes don't exist yet either), and existing vaults must re-ingest to pick up the prefix + populate the BM25/rerank path (old dense-only vectors still search, just without the sparse/rerank gains until re-indexed). The live cross-encoder reorder could not be exercised in CI (model download is network-gated); the reorder *logic* is unit-tested with a fake reranker, the `rerank()` API + model name are verified, and the load-failure fallback is covered.

### D44 — `watchdog-query` gains a semantic lane over the corpus index (#189)

The investigation `/watchdog-query` skill navigated by `manifest.json` + entity notes + grep — entity-anchored, exact-string. That misses conceptual/passage-level questions and wording the documents phrase differently, exactly where the hybrid corpus index (D43) is strong. The skill now shells out to `watchdog search --json` as a **lane**, not a replacement: a new `--json` flag emits `{query, passages[], notes[]}` (each passage carrying its `text` — the citable span — `filename`, `page`, cosine `score`), which the skill consults for conceptual questions or when manifest+grep don't surface a confident answer. The investigation layer (Claude Code) thus consumes the locally-built index a CLI tool produces — a clean reuse of the two-runtime boundary (§1). The skill is instructed to read the synthesized digest first and use search to *find* documents, not to synthesize from raw passages — preserving the D18/D26 "reason over curated notes, not raw chunks" guardrail.

**Tradeoff:** manifest/grep stays the primary path, so the lane is a model-judgment escalation (prompt prose), not a deterministic route — a borderline question may or may not trigger it. `--json` keeps `score` as cosine (matching the human listing), so a consumer can't read the fusion/rerank rank off the number — order is the only ranking signal. Existing vaults need `watchdog refresh-skills` to pick up the updated skill.

### D45 — Web research mode: agentic sourcing that re-enters via `_INCOMING/` (#186)

A new investigation-layer capability. The `/watchdog-research` skill (launched by `watchdog research`), seeded by the vault's entities/`leads`/health gaps, conducts bounded web research and **queues the sources it finds for `_INCOMING/`** so they flow through the normal `chew → ingest` pipeline — it never writes vault notes. This clarifies the I2 boundary: local-first (I2) was always about *source documents never leaving the machine during chew*, not web abstinence — investigation already runs as agentic Claude Code sessions. Routing findings back through `_INCOMING/` keeps the deterministic pipeline the single writer (dedup, provenance, registry bookkeeping all preserved). **The skill curates URLs; Python downloads them** — the split between model-judgment (which sources are worth keeping) and deterministic fetching is the heart of the design. The skill only *reads* the web (WebSearch/WebFetch) and records each keeper in a links file (`.watchdog/tmp/research-queue.tsv`); the download is a deterministic **post-flight** of `watchdog research` (which launches Claude via `subprocess` so control returns). The egress hygiene lives in tested Python (`pipeline/research.py`): **fetching happens in Python so URL validation runs *before* the network call** — the real SSRF guard (http/https only; reject hosts resolving to private/loopback/link-local space; re-validate every redirect hop) — plus a body-size cap, `<script>`/`<iframe>` stripping, and wikilink/frontmatter-delimiter defanging on sidecar values (fetched web text is an injection surface). The download runs in the terminal (ungated) and is deliberately *not* folded into `chew`, which stays local-first/no-network (I2). Sources land as the **faithful original artifact** (HTML → Docling, or any Docling-supported type by Content-Type) rather than a lossy model-summarized capture, and provenance rides the **existing `.yml` sidecar** convention (`source`/`obtained` stamped deterministically at ingest; `retrieved_by: research-mode`, a `source_type` reliability tag, and per-doc `relevance` reach the extractor as notes and travel to the morgue). Per-doc rationale → sidecar; **batch rationale → a `briefings/research-<date>.md` memo (forward-looking leads only), never `context.md`** — that human-anchored layer sits behind a deliberate trust gate and must not be machine-seeded with unverified web inference. The links file is the durable product: the skill updates it as it goes, so a long "deep" run that exhausts its tokens never loses what it queued — `watchdog research` offers to download a leftover queue on its next run and the internal `research-fetch` re-pulls one on demand (downloads are idempotent, deposit names being a stable hash of the URL).

**Tradeoff:** the effort bounds (`research_max_rounds`/`research_max_fetches`, the quick/standard/deep tiers) are *advisory* — the interactive skill self-limits to them; only the egress hygiene is hard-enforced in Python. The SSRF guard resolves-and-checks at validation time, accepting minor TOCTOU/DNS-rebinding residual risk rather than pinning the connect-time IP. Downloading the raw artifact (vs. WebFetch's processed text) duplicates the fetch the model may already have done to assess a page, accepted for capture fidelity and because the pipeline — not the session — does the deep reading. Deferring the download to a post-flight means a source isn't in `_INCOMING/` until the session ends and the user confirms — chosen over per-source live deposit because it makes the links file the single durable artifact and keeps all outbound *archival* fetching out of the interactive skill entirely. `watchdog research-fetch` (the recovery/manual download) is an internal command (hidden from the CLI banner, dispatched before argparse); the user-facing entry is `watchdog research`. The skill's only outbound reach — `WebSearch`/`WebFetch`, for *reading* — is pre-approved **only** by its own `allowed-tools` frontmatter (granted while `/watchdog-research` is active, never added to the vault-wide `_VAULT_PERMISSIONS`; `allowed-tools` adds a pre-approval without restricting the skill's other tools), and the archival download runs in the terminal, ungated and never granted to the skill — so a vault of sensitive source material carries no standing outbound-fetch grant. Existing vaults pick this up with `watchdog refresh-skills`.

### D46 — Research URL registry: a durable pending worklist; done-ness derived, not stored (#196)

D45 left the links file in `.watchdog/tmp/` (scratch, swept by `setup`) and archived each consumed queue to a `fetched-*.tsv` "done" ledger. Two gaps: a session that crashed before its post-flight silently lost the queued URLs, and a recurring investigation re-searched and re-downloaded sources it already had. The fix follows from seeing that a URL passes through the **same stages as a PDF**, and pending work is already tracked the way PDFs are — by *filesystem presence*, not a registry (`_count_incoming` walks `_INCOMING/`; `_count_queued` counts the chew queue; there is no pending-PDF ledger). So the only URL-specific state is *queued-but-not-downloaded* (no file exists yet): that becomes the one durable store, moved to `.watchdog/research/queue.tsv`, and bare `watchdog`, `watchdog chew`, and `watchdog status` warn when it is non-empty (`_warn_pending_research` → `research.pending_count`). Past download a URL is an `_INCOMING/` file (tracked like any pending PDF); once ingested it is a `documents.json` `source`. This **eliminates `fetched-*.tsv`**: re-fetch avoidance is *derived* — `research.seen_urls` unions `documents.json` `source` (ingested) with in-flight `_INCOMING/**.yml` `source` (downloaded, not yet ingested), exposed to the skill via the internal `watchdog research-seen` command, which the skill runs at seed time and skips (never-unless-asked revisit policy). A download pass consumes the worklist, retaining only rows that *failed* to fetch (at-least-once), and the stale-recovery prompt no longer archives on decline (D45's version discarded URLs there). Also: the size cap rises to 20 MiB with a readable over-cap error, and `prompts/extract_instructions.md` gains an untrusted-content note (web text is an injection surface reaching the extractor).

**Tradeoff:** deriving "seen" from artifacts (vs. an explicit URL→status registry) means no single inspectable ledger and no per-URL metadata (fetch timestamp, read-but-discarded) — accepted because the artifacts are the single source of truth that can't drift, and the metadata would only serve revisit-after-N-days / discarded-tracking, both explicitly out of scope. A URL that was downloaded but then deduped-away or failed ingest, and whose `_INCOMING/` sidecar is gone, isn't in the seen set and could be re-fetched — but `chew`'s sha-dedup (D27) catches the re-download's bytes, exactly as it does for a re-dropped PDF, so the behaviour is consistent. Retaining failed rows can re-nag on a permanently-dead URL; chosen over silently dropping a possibly-transient failure (losing a source is worse for a journalism tool). Richer capture (single-file HTML with inlined assets, SPA rendering — #200) and Wayback archiving (#201) were split into their own issues rather than expanded here. Existing vaults gain the `Write/Edit(.watchdog/research/**)` permission via `watchdog refresh-skills`.

### D47 — Optional Wayback Machine archiving of research sources (#201)

`watchdog research`'s download step can additionally submit each source to the Internet Archive's Wayback Machine (Save Page Now / SPN2) and stamp the snapshot URL into the source's `.yml` sidecar as `archived:` — a citable public copy that survives if the original page later changes or is taken down, a natural fit for the tool's provenance ethos. It is **off by default** and gated on `wayback_save` plus archive.org S3 keys (`wayback_access_key`/`wayback_secret_key`) set via `watchdog configure`; the keys live in `config.json` and are masked in the listing (a `secret` flag on the config-key metadata). Archiving is **strictly best-effort and never a gate**: `save_to_wayback` catches every error and returns `None`, so a failed or unauthorized save just leaves the sidecar without an `archived` field — the local deposit remains the source of record for ingest. Scoped to **SPN save only** — the availability/CDX "retrieve an existing snapshot" half of the original issue was dropped, since we already keep a faithful local copy, so reading one back adds nothing.

**Tradeoff:** the save is *fired, not polled* — it records the latest-capture URL (`…/web/<url>`, which resolves to the newest snapshot once the async job finishes) rather than polling SPN2's status endpoint for the exact timestamped permalink. This keeps the download loop fast (one quick POST per source instead of a multi-second poll each), at the cost of a less precise citation and a small window where the URL resolves to nothing until the job completes; a submission that isn't even *accepted* (bad keys, rate limit) records nothing rather than a dead link. The snapshot URL is written to the sidecar only, not stamped into `documents.json` or the rendered document note — keeping the change minimal; surfacing it in the note is a possible follow-up. Storing the S3 keys in `config.json` (plaintext, masked on display) rather than the OS keyring matches the "configure it in `watchdog configure`" request and the low sensitivity of archive.org save keys; it is a deliberate simplicity choice, not a security claim.

### D48 — `watchdog fetch`: a non-agentic bulk-URL front door (#197)

A public `watchdog fetch <url… | file>` downloads a batch of links straight into `_INCOMING/`, for when you already have a list (a spreadsheet, a colleague, your own browsing) and don't need a research session. It is a **thin CLI wrapper over the existing `deposit_many` egress path** — the same URL validation, size cap, sanitization, and `.yml` provenance sidecar as research sources (and the same optional Wayback archiving, D47). The input is disambiguated simply: a single argument that is an existing, scheme-less path is read as a links file (one URL per line, or the tab-separated `url⇥title⇥source_type⇥relevance` form); anything else is treated as URLs given directly. Unlike the research post-flight it does **not** touch the durable worklist — its input is the explicit list you hand it, so there is nothing to queue or recover. Deposits are tagged `retrieved_by: fetch` in the sidecar (vs. `research-mode`) so provenance stays honest about how a source was acquired.

**Tradeoff:** of the issue's three candidate front doors — a terminal command, a special `.links` file dropped in `_INCOMING/` (a pre-chew download step), and a browser extension posting URLs to a local listener — the command is the smallest delta and the most scriptable/discoverable, and it leaves chew's local-first/no-network boundary (I2) untouched. The `.links`-in-`_INCOMING/` drop-in (more native to the "drop files in `_INCOMING/`" model, but it threads a network step into the guided walk) and the extension (a new local-endpoint security surface; the Obsidian Web Clipper already covers "clip as I browse") were declined for now; both could layer on the same `deposit_many` core later. The command is kept deliberately decoupled from the fetching internals so the downloader can be replaced (e.g. with a single-file capture tool, #200) without touching `watchdog fetch`.

### D49 — Sectioned-extraction carry-forward: bounded + deduplicated, and the brief is now included

Found during a token-cost review (issue #210): the sectioned-extraction carry-forward (§5) was built by string-concatenating each section's block, so an entity present in every section of a large filing was re-listed once per section (growing ~quadratically with section count), and every prior section's full `observations` text rode forward verbatim in addition to the current one. Separately, `build_section_prompt` never received the investigation brief that `build_extract_prompt` does, so the largest documents (the ones big enough to need sectioning) were extracted without the journalist's stated intent. Fixed together: the carry-forward is now a dict keyed by entity id, rebuilt fresh each section (one line per unique entity, regardless of how many earlier sections mentioned it), carrying only the immediately preceding section's `observations` (capped); and `build_section_prompt` gained the same `brief` parameter `build_extract_prompt` already had.

**Tradeoff:** later sections lose access to *early* sections' free-text observations (only the most recent section's carry forward). Acceptable — observations are forward-looking briefing leads (D33), not extraction context the model needs preserved; the entity list, the thing the prompt says to reuse ids from, is preserved exactly and is now more reliable (no duplicate-id noise). Including the brief adds a small, constant amount of input per section until prompt caching (tracked, issue #213) lands, at which point it costs one cache write per run rather than per section.

### D50 — Per-run model-call usage telemetry (issue #207)

`model_client.ModelResult` has always carried `usage`/`cost_usd`/`attempts` per call, but the orchestrator discarded it once a call returned — there was no way to answer "how many tokens did this ingest spend, by stage?" without spelunking Claude Code session logs (whose own pricing table had itself drifted stale — #208). Every reasoning call now routes through a single wrapper, `orchestrate._call_model`, which appends `{task, model, backend, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, cost_usd, attempts}` to a run-scoped accumulator; `run` and a standalone `finalize` (`watchdog finalize`) each write it to `.watchdog/Registry/usage-<ts>.json` and surface totals on the returned summary, which `watchdog ingest` prints as one line.

**Tradeoff:** usage is only recorded for calls that return successfully — a call that exhausts `model_client`'s own internal retries and raises `ModelError` contributes nothing, since no `ModelResult` exists to read `usage` off. Accepted: the client itself doesn't expose partial-attempt token spend today, and fixing that is a `model_client` concern, not this telemetry layer's. OpenAI-compatible backends' usage dicts use different field names (`prompt_tokens`/`completion_tokens`) and don't report cache tokens yet (D37's own noted v1 simplification); `_record_usage` tolerates both shapes but the cache fields stay zero for those backends — tracked separately (issue #170).

### D51 — Prompt caching on the `claude-api` backend: extraction prompts are content blocks (issue #213)

No backend wired Anthropic prompt caching, so every extraction call paid full price for a ~5.2K-token static prefix (instructions + skill + schema) that's byte-identical across every document sharing a skill in a run — #86 attempted this for the pre-#118 subagent architecture, but that architecture no longer exists (D18), so the gap was real again. `build_extract_prompt`/`build_section_prompt` (`pipeline/prompts.py`) now return a list of Anthropic content blocks — a stable block (instructions + brief), a skill block carrying `cache_control: {"type": "ephemeral"}`, then a volatile block (per-document data) — instead of one string. The section-prompt builder's block order also changed from the old string layout: the section label/metadata-mode note used to lead, but since it (and the carry-forward) change on every section call, they had to move after the skill block so the cacheable prefix — the only genuinely stable content across a document's sections — stays at the front of the content array. `_api_complete_async` passes the block list straight through (the Messages API's `content` field accepts either shape); `_agent_complete_async` and `_openai_complete_async` flatten it to plain text via the new `model_client._flatten_prompt`, since neither the agent SDK nor the OpenAI-compatible backends expose a cache-control knob to us. `_simple_extract`'s post-flight repair retry (which used to string-concatenate a correction note onto the prompt) now goes through `_append_repair_note`, which appends a block instead when the prompt is a list.

**Tradeoff:** only the `claude-api` backend (a metered key) benefits — the subscription-only `claude-agent-sdk` path, the one the review's "burns a full session" problem is actually about, sees no change (that's the batch-backend issue, #214, and the deferred `claude-batch` idea). The classify prompt (~2K tokens on Haiku) was deliberately left as a plain string — Haiku's cache minimum is 4,096 tokens, so it wouldn't cache regardless, and adding block structure there would just be complexity with no payoff.

### D52 — `claude-batch`: bulk extraction via the Message Batches API (issue #214)

The actual fix for the review's problem statement — a routine document dump exhausting a full Claude subscription session — since D51's caching only helps a metered key. The Message Batches API is 50% off every token, stacks with D51's caching, and (combined) puts bulk extraction around $0.005–0.01/page at **zero subscription tokens**. D37 already built the provider-abstraction (`backend:model` routing) this needed; the API itself was never wired.

The Batches API is submit-many/poll/collect over minutes-to-24h, not one call per document, so it doesn't fit `model_client`'s single-call backend shape at all — `claude-batch` is a real, selectable backend name (`_BACKEND_PROVIDER`, `CLAUDE_BACKENDS`) but is deliberately excluded from `_ABACKENDS` and raises a clear error if routed through the normal `acomplete_json` path. `orchestrate._run_batch` (called from `run`, not `_extract_document`) owns the whole flow: it requires a pinned skill (classification is one-document-at-a-time and isn't batchable — the biggest complexity cut in this design) and `api-key` auth (a metered key; the Batches API isn't available on subscription). It splits the queue into sectioned documents — which can't be independent batch requests, since each section depends on the previous one's carry-forward, so they extract via `claude-api` instead, announced not silent — and whole documents, submitted as one batch (`pipeline/batch_extract.py`) using the 1-hour cache TTL (batches routinely outlive the default 5-minute window). `watchdog ingest` submits and exits rather than blocking on a wait that can legitimately take 24h; state persists to `.watchdog/Registry/batch-pending.json` (one batch in flight per vault, mirroring `has_pending_finalization`'s "resolve the pending thing first" precedent), and a *later* `watchdog ingest` invocation checks it first — collecting and writing to the vault if `ended`, or reporting progress and exiting if not — before ever looking at the queue, so a pending batch is never silently skipped even when nothing new is queued. `ingest_setup.run` normally skips lock acquisition on an empty queue; a pending batch now passes `force_lock=True` so two concurrent `watchdog ingest` invocations still can't both try to collect the same batch. A batch result that fails schema validation gets one synchronous `claude-api` repair call (not a whole new batch) — the same single-repair-attempt semantics `_simple_extract` already has.

**Tradeoff:** the pinned-skill requirement means a mixed-document-type dump can't batch everything in one pass without being split by skill first — classify-then-batch is a real follow-up, not this pass. The exact Anthropic SDK method shapes (`client.messages.batches.create/retrieve/results`) were verified against current API docs, not the installed package — this sandbox has no `anthropic` package and no network egress to install one, so the SDK boundary (`batch_extract._client`) is unit-tested with a mock, not exercised against a live account; that's the one part of this change a first real run verifies, not this session.

### D53 — `watchdog reindex`: rebuild the search index from disk, no re-chew (issue #218)

D38's tradeoff note recorded that changing `embed_model` required a full re-chew, since embedding happened at chew time back then. D43 later moved embedding into `write_vault` because the contextual prefix needs extraction's title/type/entities — but for an already-ingested vault, those outputs already live in `documents.json`/`entities.json`, and the full per-page text lives in the morgue `<stem>.md` sibling files (D26). `watchdog reindex [name]` (`cmd/reindex.py`) rebuilds `.embeddings/` entirely from those three sources: it wipes the index, then for each `documents.json` entry re-derives the same contextual prefix `write_vault._index_corpus_passages` builds at ingest time (title, type, and the entities mentioning it — found via each entity's `appears_in` in `entities.json`, since the original per-document entity list isn't itself persisted), reconstructs `[{page, markdown}, ...]` from the morgue text's `<!-- PAGE N -->` markers, and calls the same `embed.add_document`/`add_note` ingest already uses. No OCR, no model call — the only new parsing logic is turning the morgue markdown back into pages.

**Tradeoff:** a document ingested before D26 (no morgue text on disk) has nothing to rebuild its corpus passages from and is skipped with a printed reason; its note still reindexes normally, since notes are read directly from the note files on disk, not reconstructed. The full-wipe-then-rebuild approach means an interrupted reindex leaves a partial index — accepted, since the command is idempotent and re-running it is the recovery path, matching how other maintenance commands in this pipeline are re-run to recover rather than resumed mid-way.

### D54 — `watchdog merge-entities <keep-id> <merge-id>`: deterministic registry surgery to fix a duplicate entity (issue #219)

Three shipped features could only *detect* the same real-world entity living under two ids — the dashboard's "Possible duplicates"/"Single-source entities to review" views (D42), `/watchdog-health`'s near-duplicate check, and D39's Neo4j-export tradeoff note — with no way to fix it short of hand-editing `entities.json`. `pipeline/merge_entities.merge()` unions `aliases`/`appears_in`/`roles`/`timeline_events` onto the surviving id and remaps every `role.target_id` **across the whole registry**, not just the two entities being merged — a third entity naming the losing id as a relationship target follows the merge too, matching the acceptance bar the issue set. Roles that would end up self-referential after the remap (the two merged entities already pointed at each other) are dropped rather than kept as a relationship to oneself; roles that collide on `(relationship, target_id)` dedupe, but two *different* relationships to the same now-shared target both survive (an entity can legitimately be both Director and Officer of the same company). `run()` layers the note-level work on top: the losing note's `## Analysis` is concatenated into the survivor's with dated provenance (never a blind splice), the losing note becomes a short redirect stub rather than disappearing (existing wiki-links elsewhere in the vault stay resolvable), and any third-party entity whose own Relationships section just changed gets its note regenerated from the updated registry entry (every other section — Analysis/Contradictions/Notes/Summary — is read back untouched). No model calls; must be run from inside the vault (mutating the registry in place makes a project-name lookup pointless).

Two judgement calls, not specified by the issue: journalist annotations in the losing note's `## Notes` section are carried into the survivor's (labelled, not silently dropped) since nothing else recovers them once the note is stubbed; and the timeline question the issue flagged as needing verification resolved as *no NDJSON involvement* — `.watchdog/timeline/*.ndjson` stages `entity_ids` at ingest time, but `timeline.cmd_rebuild_timeline` (the renderer that runs at the end of every `_post_ingest` and therefore has the last word on `timeline.md`'s content) only ever reads `event`/`basis`/`date` off those records, never `entity_ids` — so the field is already write-only dead weight in the current pipeline, independent of this change. `entities_reg[id]["timeline_events"]` is the only representation merge-entities needed to reconcile, by unioning and deduping the two entities' lists with the same `(date, event-prefix)` key `write_vault` already uses, then re-rendering `timeline.md` via `write_vault._rebuild_global_timeline`.

**Tradeoff:** the merged-away entity's stale corpus/notes search-index entries aren't cleaned up by this command — `watchdog reindex` (D53) is the documented follow-up, since a full rebuild already drops vectors for anything no longer in the registry and duplicating that logic here would be redundant machinery for a one-line instruction printed after every merge.

**Confirmation, added before merge (review feedback):** the CLI prints both entities (name, type, document/relationship counts) and requires an explicit `y`/`yes` before mutating anything — this is registry surgery with no undo, so the default on a bare Enter is *no*, and `--force` is required to skip the prompt outright. A merge across mismatched entity types (a Person folded into a Company) is still not *blocked* — the two ids are the journalist's explicit input, and a hard validation rule would be a footgun-shaped assumption about what a journalist might legitimately want to fix (a mistyped type field, a genuinely ambiguous case) — but it now surfaces as an explicit warning inside that same confirmation step, shown *before* the action instead of only in the summary after it.

### D55 — Fourth lead-sweep signal: inferred facts to verify (issue #221)

D34 defined `basis: inferred` as "a lead to verify, not a finding," but D40's deterministic lead sweep (`pipeline/leads.py`) shipped with three registry-only signals and none of them surfaced inferred facts — the pipeline's own verify-me markers never reached `watchdog leads` or the post-ingest briefing. The fourth signal scans each entity's `roles`/`timeline_events` for `basis: inferred` entries (the only two registry-persisted per-entity fact shapes — `evidence_fragments` is rendered into the note body at ingest but never written back to `entities.json`, so it isn't available to a registry-only scan) and lists the entity once with all its inferred claims underneath, sorted by claim count then name. Same shape as the other three signals: pure function (`find_leads`), no model call, folds into the existing `briefings/leads-<date>.md` snapshot and `watchdog leads` output via a new "Inferred facts to verify" section.

**Tradeoff:** `evidence_fragments` (the model's per-entity prose claims, distinct from `roles`/`timeline_events`) isn't covered by this signal since it isn't persisted to the registry post-#140 — extending the sweep to it would mean either round-tripping it into `entities.json` (a schema change beyond this issue's scope) or parsing note bodies (breaking the "registry-only, no file reads beyond `entities.json`" design this sweep has kept since D40). Left for a future slice if inferred `evidence_fragments` prove to be where most verify-me leads actually live.

### D56 — Fact/event dedup keys match on full text, not a truncated prefix (issue #231)

Found while discussing #231 (the dead `entity_ids` NDJSON field): three independent mechanical dedup keys — `write_vault._timeline_dedup_key` (entity registry, cross-document), `timeline._stage_dedup_key` (raw per-document NDJSON staging), and `merge._dedup_key_facts` (cross-section merge within one sectioned document) — all matched on a truncated prefix of the fact/event text (80 or 120 characters) rather than the full string. Since `key_facts` are written as full sentences with no length cap, and per-entity events on the same date often share a long opening clause ("On March 3, 2019, Acme Holdings Ltd. transferred beneficial ownership of the Cayman Islands shell company to…"), a prefix key could collide two *genuinely different* facts whose divergent, material detail (who it went to, on what terms) lands past the cutoff — silently discarding the second, not just leaving a harmless duplicate. All three now key on the full lowercased fact/event text.

**Tradeoff:** this stays a mechanical, non-semantic dedup — deliberately not routed through a model call, unlike the global timeline's `timeline-dedup` pass (D31, `_select_kept`), which is the only stage with a semantic backstop today. That means two near-identical facts with even trivial wording differences (a comma, reordering) across distinct documents will no longer collapse at the entity-note level — left as-is on purpose, since an entity's own note has no other cross-document restatement dedup (`## Analysis` already accumulates per-document without collapsing near-restatements), and two independently-sourced entries attributed to different source documents (via `source_sha256`, rendered as a wikilink per document) read as corroboration signal to a journalist, not noise. `merge._dedup_key_facts`'s key deliberately still omits `date` — unlike the other two — since it exists to fold the same fact restated with and without date context across sections of one document (the "keep a date if any duplicate carries one" backfill), and scoping by date would break that intended merge.

### D57 — Full-text (FTS5) search lane + batch search (issues #109, #110)

`watchdog search` (D38, D43) is a semantic index — cosine similarity over embeddings, fused with an in-memory BM25 leg that's recomputed per query over whatever's already loaded. That leg answers "what's most relevant" for a bounded top-N; it was never a true full-text index and can't answer "every place this exact term appears," which is what #109 asked for after Datashare comparison flagged the gap: content that never got promoted into a synthesized note is otherwise unfindable. The fix is a genuinely separate, persisted index — `pipeline/fulltext.py`, a local SQLite FTS5 table (no new service, no API) over the same morgue page text plus every generated note (entity, document, timeline, briefing, hot cache, log). It is additive, not a replacement: built at the same ingest call sites as the embedding index (best-effort, same failure handling), rebuilt in full by `watchdog reindex`. Query syntax is deliberately simplified from raw FTS5 MATCH grammar (quoted phrase / bare-word AND, every token escaped) since this tool is for journalists, not database users. Presented in `watchdog search` as a third "Exact matches" section rather than a new command or flag — early design discussion considered `watchdog grep`, but a separate verb assumes the Unix-literate audience this tool explicitly can't assume; one command outputting everything it found, grouped by how it found it, needed no new vocabulary.

`#110` (batch search — "does any of these N names from a leaked roster/sanctions list/donor list appear anywhere") became a natural same-change follow-on once the FTS module existed, since it explicitly depended on the "companion FTS issue." Shipped as `watchdog search --batch <file>` rather than a new `batch-search` command, for the same one-verb reason. Each term is checked against the manifest (name/alias substring) and the full-text index; the semantic/embedding lane is deliberately skipped for batch mode.

**Tradeoff:** batch search skips semantic matching entirely — a list of hundreds of terms paying per-term embedding + cross-encoder rerank cost doesn't scale the way an in-process SQLite query does, so a near-miss (a nickname or transliteration variant with no manifest alias and no literal occurrence) won't surface in a batch run the way it would in a single interactive `watchdog search`. The full-text index also depends on the local Python's SQLite build shipping FTS5 (near-universal since ~2020, verified present in both the system Python and the pipx venv at build time) — `fulltext.py` raises a clear error rather than the raw `sqlite3` one if it's ever missing, and `watchdog search`'s semantic lane keeps working regardless since the two indexes are independent.

### D58 — Stripped the dead `entity_ids` field from the timeline NDJSON schema (issue #231)

#231 found that `stage_timeline_events` tagged every raw timeline NDJSON record with `entity_ids` (unioned from the source `key_fact.entities`), but nothing downstream ever reads it — not `cmd_rebuild_timeline` (only `event`/`basis`/`date`), not the `timeline-dedup` prompt (only `event`/`page`), not `merge-entities` (D54 already found this independently while reconciling timeline events during entity merges). The apparent intent was to let a *deduped* global-timeline outcome sync back onto the entities it was tagged to, correcting each affected entity's own `## Timeline` section to match after cross-document dedup collapsed a near-restatement — that sync was never built, and D56 settled (in conversation, not as a separate implementation) that it shouldn't be: an entity's own note has no other cross-document restatement dedup, and near-duplicate entries there — each attributed to its source document — read as corroboration signal to a journalist, not noise worth collapsing. With no consumer and no planned one, `entity_ids` is confirmed dead weight rather than an unfinished feature. Removed from `stage_timeline_events` and the NDJSON records it writes; the entity registry's own `timeline_events` (rendered into each entity's `## Timeline`) is populated independently by post-flight straight off `key_facts`, so nothing downstream loses information.

**Tradeoff:** none functionally — this is pure removal of write-only weight, not a behavior change to any read path. Old on-disk NDJSON files from before this change may still carry a stray `entity_ids` key; harmless, since every reader already ignored it.

### D59 — One global-timeline renderer, with document + entity attribution (issue #237)

Two structurally different renderers both wrote `timeline.md`, and which shape landed on disk depended on which command last touched the vault. `write_vault._rebuild_global_timeline` walked every entity's registry `timeline_events`, so it carried document and entity attribution but never deduped across documents (a fact tagged to two entities printed twice). `timeline.cmd_rebuild_timeline` read the cross-document-deduped canonical NDJSON — real dedup via the `timeline-dedup` model pass — but rendered only bare event text, no attribution or links. A normal `ingest` ended on the deduped-but-unattributed shape; `merge-entities` and `write_entity` left the attributed-but-not-deduped one.

Unified on the canonical-NDJSON renderer — dedup is the harder-to-replicate property — and gave it what the other had: `cmd_rebuild_timeline` now resolves each record's `source_sha256` → document link (+ `page`) and `entity_ids` → entity links, year-grouped, and is the single code path all four call sites route through (`_post_ingest`, `merge-entities`, `write_entity`, standalone `watchdog timeline`). This re-adds `entity_ids` and `page` to the NDJSON record that D58 had stripped — but for a genuine reader this time (the renderer's own links), not the entity-note sync D58 declined; the entity registry's per-entity `## Timeline` stays independent and mechanically deduped, exactly as D58 left it. To make an event's attribution survive a cross-document collapse, the `timeline-dedup` contract changed from a flat `keep: [indices]` to `groups: [{keep, duplicates}]`, so `_select_kept` can **union** each dropped duplicate's `entity_ids` onto the survivor rather than keeping whichever restatement the model happened to pick. `merge-entities` gained a parallel deterministic step (`_remap_timeline_ndjson`) rewriting the losing id → survivor inside the NDJSON records, so the timeline's entity links follow a merge instead of pointing at the deleted stub.

**Tradeoff:** `write_vault` no longer renders the global timeline at all — the deduped canonical NDJSON it would read only exists after `_post_ingest`'s batch-end dedup, so a *standalone* `watchdog-write-vault` (rare; not the orchestrated path) leaves `timeline.md` untouched until the next `watchdog ingest` or explicit `watchdog timeline`. The `--skip-timeline` flag that guarded the old per-document render is gone. The dedup model now returns slightly richer output (groups, not a flat list) but still one call per colliding date — no cost change. Not addressed: events whose dates differ only in precision (`2026-03` vs `2026-03-12`) live in separate date buckets, so they are never compared, deduped, or entity-unioned against each other — a pre-existing property of the date-keyed collision design, left out of scope.

### D60 — Bound the pre-flight entity digest at the matching layer, not by truncating content (issue #216)

Pre-flight ships every manifest entity whose name or alias substring-matches the document into the extraction prompt, each with its full summary, `## Analysis` prose, timeline, and roles — nothing capped. In a mature vault, hub entities match nearly every document, so per-page extraction cost climbs with investigation age; short names/aliases make it worse (`"Lee"` substring-matches `"asleep"`). The issue proposed per-candidate caps (truncate analysis to ~N chars, timeline to N events, etc.).

We deliberately did **not** cap analysis. `## Analysis` is an append-only ledger of dated, source-attributed claim-blocks, and it is the substrate for the extractor's contradiction check — the *sole* contradiction pass, with nothing downstream to re-verify. Contradictions are not recency-bound (a document ingested today can contradict a claim from years ago), so a char/recency truncation drops precisely the old claims a new document is as likely to contradict — and the loss is silent (you cannot A/B the contradictions you failed to flag). Trading a measurable token saving for an unmeasurable recall loss is the wrong trade for an investigative tool. Instead we attacked the two safe levers: **(1) candidate *selection*** — whole-token (word-boundary) matching replaces raw substring, so `"Lee"` no longer matches `"asleep"`, with a plain-substring fallback for non-ASCII-edged names (CJK etc.) that regex boundaries can't segment, so non-Latin names never match less than before; and an aliases-only length floor (`preflight_alias_min_length`, default 3) since accumulated short aliases (initials, abbreviations) are where the false-match noise concentrates — the canonical name always matches at any length, so `BP`/`GE`/`3M` stay findable. **(2) instrumentation** — pre-flight reports the digest's byte size and candidate count per document, surfaced during ingest, so the per-candidate caps (timeline/roles/analysis) can be sized from real data on a mature vault rather than guessed. Those content caps are deferred to a follow-up, made with data.

**Tradeoff:** word-boundary matching can, in principle, miss a genuine mention written in an unusual joined form, and the alias floor drops real 1–2-char aliases — both bias toward fewer false candidates at a small risk of a missed real one, mitigated by the canonical-name-any-length rule and the non-Latin substring fallback. The dominant growth driver (analysis prose × hub matches) is only *reduced* (fewer candidates), not *bounded*, until the measured content caps land — an accepted interim state, since bounding it correctly requires the data this change starts collecting.

### D61 — Rendered web capture: sandboxed JS execution, traded for faithful static+SPA snapshots (issue #200)

A single urllib GET plus a two-tag regex (`<script>`/`<iframe>`) never captured what a page actually looks like: no images or CSS, and a client-rendered SPA deposited as an empty shell. Fixing that means running the page's JavaScript somewhere — the architectural fork #200 named — so the fix is to render every HTML deposit in headless Chromium via Playwright and save one self-contained, already-rewritten `.html`: script-stripped, assets inlined as data URIs, CSP-pinned. The containment answer to the posture #186 established (URL validation *before* any network call) is per-request SSRF interception — `context.route` re-checks every subresource request a rendered page issues, XHR included, against the same public-host rule as the top-level fetch, not just the URL the journalist queued. The plain-fetch fallback's sanitizer is upgraded from the regex to `nh3` (an `ammonia` binding) at the same time, since it's a strictly more complete tag/attribute stripper and the regex was already known to be an approximation.

**Tradeoff:** this reintroduces a JS-execution surface into the pipeline that the regex-strip design had deliberately avoided — contained by Chromium's own sandbox plus the per-request guard, but not eliminated; a sufficiently novel browser exploit is a theoretical residual risk the old design didn't carry. Playwright + Chromium is a ~150 MB install, so it's an **optional dependency** (`watchdog-intel[web]`): a vault owner who never runs `watchdog research`/`fetch`, or who wants zero JS-execution surface, pays nothing and gets the plain, nh3-sanitized fetch, same as before. Every HTML deposit is now fetched **twice** — the existing urllib GET (kept for type-detection and provenance) and then the browser render — a deliberate simplicity/latency tradeoff over threading Content-Type detection and provenance through the rendered path instead.

### D62 — Drop VERIFY_X509_STRICT on egress fetches so TLS-inspecting proxies don't break capture (issue #243)

Python 3.13 turned on `VERIFY_X509_STRICT` by default, and it rejects the re-signing CAs that corporate TLS-inspection proxies present when those CAs aren't RFC 5280-conformant (commonly: no keyUsage extension). Journalists on managed newsroom machines sit behind exactly such proxies, so every HTTPS research/fetch fails outright — and because the urllib fetch runs before the rendered capture (D61), it takes the Chromium path down with it, even though Chromium itself accepts the same CA via the system trust store. The egress openers (`fetch` and the Wayback submission) now use a context with the strict bit cleared: full chain validation and hostname verification remain on; only the extension-conformance check — which browsers, curl, and pip don't enforce either — is dropped, restoring the pre-3.13 posture.

**Tradeoff:** a deliberate, narrow loosening of TLS validation. A malformed CA that strict mode would reject is accepted if it chains to a trusted root — the same acceptance every mainstream client grants, so watchdog is no weaker than the browser beside it, but it forecloses "strictest available TLS" as a differentiator. Not configurable: a knob would push a cryptic PKI decision onto a non-technical journalist whose realistic alternatives are "capture works" or "capture is dead on their work laptop".

### D63 — Reconcile timeline events that differ only in date precision (issue #239)

The timeline collision/dedup machinery buckets events by their literal date string, so a month-precision event (`2026-03`) and the specific day it restates (`2026-03-12`) land in different buckets and are never handed to the dedup model together (D59 scoped this out). Both survive as separate lines, and their `entity_ids` are never unioned even when they describe the same occurrence.

Added a second post-ingest pass, after the exact-date dedup and before the rebuild: `timeline.month_precision_groups` finds each month holding **both** a `YYYY-MM` event and `YYYY-MM-DD` events, and one focused `timeline-precision` model call per such month matches each coarse event to the day it restates (if any). `apply_precision_matches` then drops the matched coarse event, keeps the precise one (precise date always wins), and unions the coarse event's `entity_ids` onto it. The pass is **gated on a month carrying both precisions**, so a typical ingest — where events are almost all day-dated — makes zero extra calls. The matching prompt is deliberately narrow (return few or no matches; when in doubt don't match) and the schema only expresses coarse→precise pairs.

**Tradeoff:** the guard against false collapse is structural, not just prompt-level — the pass can only ever *remove a coarse restatement*, never a precise event, so it can't merge two genuinely distinct days into one. Scoped to month↔day only: a bare-year (`YYYY`) event is left unreconciled, because a year spans too many days to match a specific occurrence safely. The residual risk is an over-eager coarse→precise fold (one vague line absorbed into the wrong day), bounded by the conservative prompt; the cost is at most one small model call per month that actually mixes precisions.

### D64 — Usage records carry per-call filename/detail, batch extraction usage is no longer silently dropped, and `scripts/analyze-session` reads `usage-<ts>.json` directly (issue #247)

`scripts/analyze-session` still parsed Claude Code `.jsonl` session transcripts (orchestrator + `subagents/`), a model D50 (#207) had already replaced with `usage-<ts>.json` per-call telemetry — the tool was simply never updated. Rewrote it to read that file directly, grouping calls by stage (`classifier`/`extractor`/`finalizer`, matching the CLI's own `--classifier-model`/`--extractor-model`/`--finalizer-model` flags) and, for extraction calls, showing the filename and page range/section label. This also drops the script's own hardcoded pricing table entirely — `cost_usd` is already computed authoritatively by `model_client` at call time, which is what eliminates the staleness D50 named (#208) as the reason to stop reading session logs in the first place.

Two things needed to change in `orchestrate.py` to make this possible: (1) `_record_usage` took a `filename`/`detail` param, threaded from every call site (`_classify`, `_simple_extract`, `_extract_sectioned`, the batch repair path, `timeline-dedup`, `timeline-precision`); (2) tracing every `_call_model` site surfaced that batch-collected extractions (D52) never reached the usage accumulator at all — only a repair retry (when a batch result fails validation) went through `_call_model`. A batch run's real token spend was silently absent from `usage-<ts>.json`. `_record_usage` was decoupled from `model_client.ModelResult` (now takes explicit `model`/`backend`/`usage`/`cost_usd` fields) so `_finish_batch_item` can record a batch item's own usage directly, not just the repair call's.

**Tradeoff:** none of this changes what gets billed or how ingest behaves — it's telemetry-only. The batch-usage fix is a real bug fix bundled into what reads as a doc-tooling issue; done here because leaving it would mean the rewritten script still under-reports for anyone running `claude-batch`, defeating the point of the rewrite.

### D65 — Raw timeline files are consumed at promotion/dedup, not retained (issue #250)

`stage_timeline_events` writes one raw `.watchdog/timeline/{date}_{sha7}.ndjson` per (date, document); `collisions()` promoted raw-only dates to a canonical `{date}.ndjson` but **left the raws on disk**, and the collision-dedup loop in `_post_ingest` never deleted them either. So every raw file that ever existed was re-read on every later ingest: a promoted date came back as a phantom collision (canonical vs. its own already-promoted raws), producing one `timeline-dedup` model call per historical date on every run (the #216 unbounded-call class), and — worse — when a dedup call failed, `_post_ingest` fell back to `kept = events` (the canonical+raw *union*, i.e. every event twice) and wrote that back to the canonical, permanently duplicating rows on a documented failure path (a rate limit during post-ingest).

Fix: consume each raw once its events are merged into the canonical. `collisions()` deletes the raws in the promotion branch immediately after writing the canonical. The collision branch in `_post_ingest` deletes a collision's raws only after a **successful** dedup write; on a failed dedup call it now leaves the canonical *and* its raws untouched (`continue`) so the next ingest retries the same collision cleanly, rather than writing the doubled union back. The steady state is the intended one: nothing new collides → zero model calls, and a promoted date never re-collides with itself.

**Tradeoff:** none of substance. The raws' only other legitimate reader is `abort.run`, which deletes the raws of a *failed* document (one that never reached post-flight) — "delete only what was merged" preserves that: a raw is removed exactly once, either when its document's events are folded into the canonical (success) or when its document is aborted (failure). A failed dedup no longer surfaces the batch's new events in `timeline.md` until a later ingest succeeds, but nothing is lost on disk.

### D66 — Run locks are acquired atomically with O_CREAT|O_EXCL, not check-then-write (issue #257)

Every run lock was acquired check-then-write: `if lock.exists(): ...refuse/take-over; lock.write_text(...)`. Two processes racing the window between the check and the write both passed and both proceeded — no mutual exclusion, exactly what `force_lock` (#214) claimed to provide for concurrent claude-batch collection. Chew was worse: `preprocess_batch.run_ingest` wrote `.chew-lock` **without any existence check**, so `watchdog watch` plus a manual `watchdog chew` could run two chews on one vault, racing the staging renames and near-dup computes. A malformed lock (no parseable `started_at`) was also deleted regardless of age.

Added `pipeline/locks.py`: `acquire_lock` uses `os.open(O_CREAT|O_EXCL|O_WRONLY)` — atomic on every platform, so exactly one caller creates the file and writes its contents to that exclusive descriptor (no window where the lock exists but is empty). `acquire_or_take_stale` layers the staleness policy on the failure branch: take over a lock provably older than 30 minutes, but **refuse** a fresh one *or* one whose age can't be determined, leaving it for `watchdog unlock`. Wired into all three sites — the ingest lock (`ingest_setup.run`, now acquired before the pending-wipe so the wipe itself is mutually excluded), the shared finalize lock (`cmd/ingest._run_finalize`), and the chew lock (`preprocess_batch.run_ingest`, which now check-and-refuses). Cross-process contention is now under test (`test_locks.py`), where deleting the acquisition previously left the whole suite green.

**Tradeoff:** the stale-takeover path (unlink the stale lock, then re-create) still has a small window if two processes both find the *same* >30-min-old lock at the same instant — an acceptable residual, since the common case (two fresh invocations) is fully closed by the `O_EXCL` create, and a 30-minute-old lock racing a fresh start is vanishingly rare. Refusing an unparseable lock (rather than deleting it, as the old code did) means a genuinely corrupt lock now requires an explicit `watchdog unlock` instead of self-healing — the safer default, given `unlock` exists precisely for this.

### D67 — write_vault is transactional around a single commit point; derived writes are idempotent (issue #259)

`write_vault.run` wrote entity notes, appended per-entity finalizer fragments, and updated the embed/FTS indexes *before* atomically persisting the registries. A crash between those writes and the persist left rewritten notes and appended fragments whose registry entry was rolled back, and the model-repair retry (`_simple_extract` re-runs post-flight → `write_vault`) re-appended: the `## Analysis` block (keyed only by date + doc link) and the fragment block (`_record_entity_fragment` opened `<id>.md` in append mode and did `count + 1`) both doubled, so synthesis saw the same claims twice.

The registries are now the sole **commit point**: they persist last, atomically, and everything rebuilt-from-source — the embed/FTS indexes and the finalizer fragments — is (re)written *after* the commit, keyed for idempotent replay. Indexes already upsert by note_path; fragment blocks are now keyed by the source sha and *replaced* (`_drop_fragment_block`), the queue tracks the contributing-sha *set* (count = `len(shas)`, no longer a raw `+1`), and the entity note's `## Analysis` block is stripped-then-reappended by its doc-note link (`_drop_analysis_entry`) so a re-run for the same document replaces its contribution rather than duplicating it. The registry merges were already sha-idempotent, so a repair retry now converges (regression: `test_repair_retry_converges_after_crash_*`). `abort.py`'s docstring, which described a pre-D18 "subagent" world where a failed extraction never touched notes, is updated to state the real post-crash contract: notes/indexes may lead the rolled-back registry, and are left in place because re-ingest replaces them idempotently and `reindex` rebuilds them — half-deleting a note a journalist may have annotated is the worse failure.

**Tradeoff:** entity/document notes are still written *before* the commit (the model-repair loop needs the notes on disk to detect the partial write, and moving all note writes after the commit would not remove the phantom-on-permanent-discard case, only relocate it). The residual is that a permanently-discarded document can leave note prose and index rows with no registry entry — invisible to registry-driven views and reconciled by `reindex`/re-ingest — which is preferable to clobbering journalist annotations on rollback. The `_queue.json` `count` field is retained (now = distinct sha count) purely for display in `pending_finalization`; the synthesis gate reads registry `appears_in` (D26), not this.

### D68 — A single resolution overlay gives leads, watch-word alerts, and contradictions a workable-queue property (issue #266)

The vault had no memory of what the journalist had already dealt with. Three deterministic report paths kept re-surfacing handled items: `watchdog watchlist` re-scans the whole vault and re-reported every historical hit (D35), the lead sweep regenerated `briefings/leads-<date>.md` from scratch on every ingest (D40), and contradiction callouts accumulated append-only in entity notes with no way to mark one handled short of hand-editing. Fixed with one mechanism shared by all three: an acknowledgment store at `.watchdog/Registry/resolutions.json` (`pipeline/resolutions.py`) keyed on stable, human-copyable ids — `lead:<signal>:<entity_id>`, `contradiction:<sha1 of the normalized callout>`, `alert:<sha7>:<sha1 of the term>`. The report generators consult `resolved_ids(vault)` and drop acknowledged items from the active list; the entity-note writer applies the same set as a render-time overlay so a resolved callout leaves the note body too. Acknowledgment is populated three ways into the same JSON — `watchdog resolve <id>`, a `- [x]` checkbox sync from the briefing files (each rendered item carries an unobtrusive `<!--wid:<rid>-->` marker), and `watchdog unresolve` to undo.

**Tradeoff:** a second piece of state to keep consistent with the registry. Following #219/D54, a merged-away entity's lead resolutions are remapped onto the survivor in `merge_entities.run`; contradiction and alert ids are keyed on content, not entity id, so they need no remap. The store is a pure overlay — the registry keeps the full contradiction list, so unresolving restores an item to the leads report — with one accepted limitation: a callout already stripped from a note body only reappears in that note when a later document re-extracts it (the leads report, driven by the registry, is the authoritative queue and does restore immediately). Checkbox parsing is friendlier but fragile to hand-edits, which is why the explicit command is the robust path and the checkbox is a convenience layered on top of the same JSON.

### D69 — The registry write-lock gets a real Windows branch (`msvcrt.locking`), not just a documentation caveat (issue #258)

`_registry_lock` imported `fcntl` in a `try`/`except ImportError` and set `_HAS_FLOCK = False` on the `ImportError` (i.e. on Windows), but the `except` branch was empty — the lock context manager still opened and yielded the file with no actual mutual exclusion. README and ARCHITECTURE §4 both described the lock unconditionally ("file-locked", "flock"), which was true only on macOS/Linux; on Windows, cross-process writers (a concurrent `merge-entities`, `reindex`, or a second `ingest`) had zero serialization beyond D18's in-process sequencing. Found by a mechanical production-review pass (not run on a real Windows machine — CI is Linux/macOS only).

Added an `msvcrt` branch alongside the existing `fcntl` one: `msvcrt.locking(fh.fileno(), LK_LOCK, 1)` locks a 1-byte region as a mutex (writing a placeholder byte first, since `msvcrt.locking` locks bytes that must already exist in the file). This is a real behavioural difference from `flock`, not just an API swap: `LK_LOCK` retries roughly once a second and raises `OSError` after ~10 seconds of contention rather than blocking indefinitely. README and ARCHITECTURE §4 now state this bounded-wait difference explicitly instead of describing locking as a single unconditional guarantee.

**Tradeoff:** the ~10-second bound means a Windows writer that loses a very long lock race (e.g. a huge batch write) raises instead of waiting it out, where macOS/Linux would simply wait — a real platform gap, but preferable to silently proceeding unlocked as before. Untested on an actual Windows machine (CI doesn't run one); the branch is covered by mocking `msvcrt` in `tests/test_write_vault.py`, not by a live lock-contention test.

### D70 — Extraction provenance (`record_skill_hash`/`extract_model`/`extract_effort`) stamped per document (issue #268)

D21 stamped `record_skill` into each document's note + registry so a skill *rename/removal* wouldn't orphan a vault's memory of what classified it, but #68 is about to revise the skills' *content* under the same filenames — after that lands, an existing vault has no way to tell which documents were extracted under a superseded skill version. Model and effort have the same gap: `usage-<ts>.json` (D50) records them per model call, not per document, so the registry alone can't answer "what produced this extraction" once config changes.

`orchestrate._stamp_document` now stamps three more fields alongside `record_skill`, from the same information already in scope at each of its three call sites (`_simple_extract`, `_extract_sectioned`, `_finish_batch_item`): `record_skill_hash` (first 12 hex of `sha256(skill_text)`), `extract_model` (`model_client.resolve_model_id`'s resolved id, not the tier name), and `extract_effort` (the abstract per-stage intent, D36 — `None` meaning "model default"). They land wherever `record_skill` already lands — `documents.json` and the document note's frontmatter (`write_vault.py`) — so nothing downstream needs a second read path.

**Tradeoff:** three more registry fields per document, all `None` on a document extracted before this change (no backfill). This is deliberately just the stamping — the "N documents extracted under an out-of-date skill" report and any targeted re-extract command are follow-ups; landing the stamp itself first is the point, so nothing extracted between now and #68 loses its provenance.

### D71 — Irreversible operations snapshot the files they're about to destroy (issue #270)

`merge-entities` (D54), ingest's `discard` choice, and `delete --purge` are all explicitly one-way and prompt accordingly, but the state actually at risk in each is small — a couple of registry files, a handful of notes, or a few post-ingest scratch files. A scary confirmation prompt and "recoverable if you get it wrong" are different tools, and for a non-technical user the second is the one that actually helps.

Added `pipeline/backup.py`: `snapshot(vault, operation, paths)` copies whichever of `paths` exist into `.watchdog/backups/<ts>-<operation>/`, preserving each path's position relative to the vault, and prunes to the 5 most recent. Wired into all three sites, each backing up only what it's about to overwrite or delete: `merge_entities.run()` snapshots `entities.json`, `manifest.json`, both entity notes, and any third-party note `stats["touched_entities"]` says is about to be regenerated — taken right after `merge()` computes those stats but before any file is written, since the mutation is in-memory only until the registry write near the end of `run()`. `ingest_setup.run()` snapshots `entity-fragments/`/`result_*.json`/`notes_*.md` immediately before the `wipe_pending` block deletes them — this naturally scopes to genuine discards only, since a routine ingest with no leftover residue from an unfinalized batch finds nothing to snapshot and creates no backup directory. `cmd_delete`'s `--purge` branch snapshots the registry files only, before `shutil.rmtree(vault)`. Each site prints a one-line restore hint (`backup: <path> — copy files back to undo`) when a snapshot was actually taken.

**Tradeoff:** a real `watchdog undo-merge` command (or equivalents for the other two) is deferred indefinitely — the snapshot is the load-bearing part, and manual file restoration is acceptable for what should be a rare recovery. `--purge`'s snapshot is the one asterisk: it lives inside the vault being deleted, so it only hedges a delete that fails partway, not a completed one — the CLI hint says so explicitly rather than implying full recoverability. Bounded disk cost from pruning; no attempt to snapshot anything beyond the handful of files each operation actually destroys.

### D72 — Pre-flight cost estimate at the ingest confirm, from queue est_tokens × this vault's own usage history (issue #269)

D50 gave a subscription user a post-hoc token/cost total after a batch finished; nothing helped them decide *before* committing, so the first sign of trouble was hitting the session limit mid-run. Both halves needed already existed — `ingest_setup`'s per-file `est_tokens` (computed for the sectioning threshold) and this vault's own `usage-<ts>.json` history (D50) — they just weren't multiplied together.

`ingest_setup.cost_estimate(vault, queue_files, backend)` does the arithmetic: sum the queue's `est_tokens`, then derive a $/token ratio from each of the last 3 `usage-<ts>.json` files' `totals` and present `cost_low`/`cost_high` as the range across those runs (not one blended average) — extraction output varies with document density, and a single falsely-precise figure would undercut the trust the feature is meant to build. `cmd_ingest` prints the formatted line (`_format_cost_estimate`) right before the existing `Ingest now with your <mode> auth?` confirm, and a new `--estimate` flag prints the same line and exits before the lock is touched — the "should I split this batch" case, and a queue-status check when nothing needs to run. Subscription auth (`claude-agent-sdk`) always gets tokens only, never a dollar figure, since there's no real billing to project — reporting a fabricated fraction of a session limit would be worse than reporting nothing. First-run vaults (no `usage-<ts>.json` yet) get the same token-only treatment. The queue-scanning loop in `ingest_setup.run` was factored out into `scan_queue` so both the locking path and the lock-free `--estimate` path read the same per-file metadata without duplicating the parse loop.

**Tradeoff:** the $/token ratio is derived from *input* tokens only — it implicitly bakes in each historical run's output/input mix, so it stays accurate for a vault's typical document density but skews if a batch's mix (e.g. much longer or much shorter documents than usual) differs sharply from the last 3 runs. Accepted, since the alternative (modeling output tokens separately) needs the same per-document output/input ratio history this pass doesn't build, and the range already communicates that the figure is approximate.

### D73 — Cross-vault search: `watchdog search --everywhere`, the cheap first slice of #67 (issue #272)

The question a reporter actually asks across investigations is "have I seen this name in *any* of my vaults?" — #67's full answer (cross-investigation entity resolution, a shared registry) is a big architectural lift, but every vault already carries a manifest, an FTS5 index, and an embeddings index, all local, so the literal question is answerable today with no new storage. `--everywhere` drops the single-project scope, iterates every registered, non-archived project in `projects.json`, and runs the same manifest-substring + full-text lanes `--batch` already uses (D57) per vault, reporting hits grouped by investigation name. It composes with `--batch`, so a term list can be checked across every vault in one pass, not just one.

Deliberately skips the semantic/rerank lane, for the same reason D57 gave for `--batch`: N vaults × embedding + cross-encoder rerank per query doesn't scale the way an in-process SQLite query does. A vault whose registered path is missing, or isn't a Watchdog vault (`_check_project_health`), is skipped rather than failing the whole scan — the same tolerance `watchdog doctor` already applies to a broken registry entry.

**Tradeoff:** the same recall gap `--batch` accepts — a name variant with no manifest alias and no literal occurrence won't surface, since there's no semantic lane to catch a near-miss. Latency scales with the number of registered vaults; fine at the realistic handful a journalist runs, but not designed to scale past that. This is intentionally not #67: no shared registry, no cross-vault entity resolution, no new invariants — and it doubles as instrumentation, since how often a cross-investigation hit actually occurs is the evidence needed to size (or decline) the real global registry.

### D74 — `watchdog ingest --wait` sleeps through a rate limit and auto-resumes (issue #271)

A large document dump run unattended (the natural overnight slot) hits the Claude subscription rate limit partway through and stops cleanly — correct, but a 200-doc batch can need several human touches spread across session windows just to nudge it forward each morning. The resume machinery (queue-file lifecycle, `already_extracted` skip, pending-finalization merge) already made re-running `watchdog ingest` a no-op-safe continuation; the only missing piece was doing that re-run automatically.

`--wait` wraps the existing loop in `cmd_ingest` rather than changing `orchestrate.run`'s behavior: on a rate-limited summary it sleeps (via `RateLimitError.resets_at` plus a small buffer, or a fixed fallback when the backend didn't report one — only `claude-agent-sdk` does; `claude-api` and the OpenAI-compatible backends never populate it) and calls `orchestrate.run` again, merging each cycle's summary (results/extracted/skipped/failed/usage accumulate; point-in-time fields like `rate_limited` reflect only the latest cycle) so the final report covers the whole run, not just the last leg. The sleep is chunked under `ingest_setup.STALE_SECONDS` (30 min), refreshing the held lock's `started_at` after each chunk (`locks.refresh_lock`) — otherwise a wait longer than the staleness window would let a second `watchdog ingest` invocation mistake a live, sleeping run for an abandoned one and steal its lock. Mutually exclusive with a `claude-batch` extractor model, which already submits-and-exits rather than waiting. Explicitly opt-in (I4 spirit: no silent behavior change) — without the flag, a rate limit stops the batch exactly as it did before.

**Tradeoff:** a long-lived terminal process holding the run lock across hours, and `resets_at` being frequently unavailable (subscription-only), so the fallback interval is a guess rather than an exact wake time on the more common `claude-api`/OpenAI-compatible paths. Laptop sleep pauses the countdown — acceptable for v1, not handled specially.

### D75 — Deterministic quote verification against the morgue text (issue #267)

D22's tradeoff note deferred checking that a captured `key_facts[].quote` actually appears on its cited page to the model-graded #106 evaluator, since the Docling text was discarded after extraction and re-verifying would have meant a model re-read. Post-D26 the page text is already in hand at post-flight time — read from the chew-time queue descriptor, the same source `write_vault` uses to write the morgue markdown — so the check is now a few lines of Python, not a model call.

`quote_verify.verify_quotes` runs in post-flight after `explode_key_facts` (so both the document-level `key_facts` and the fanned-out per-entity `evidence_fragments` get annotated): an exact substring match on the cited page wins outright; failing that, a case/whitespace/punctuation/hyphenation/accent-normalized match is tried against the cited page and its immediate neighbors (OCR noise, page-marker drift routinely shift a quote by one page); failing that, the quote is flagged `quote_verified: False` and rendered with a visible `*(quote not found on cited page — verify against source)*` note. A document with no page text available at all (e.g. `watchdog finalize` re-run with the queue descriptor already gone) is left unannotated rather than flagged — absence of evidence isn't evidence of a bad quote. Same posture as the D32 coverage warning: annotation only, never a gate.

**Tradeoff:** a quote from a genuinely garbled-OCR page will legitimately fail matching and get flagged — arguably correct, since the journalist should verify it against source anyway. This covers quotes only; whole-fact faithfulness remains the deferred model-graded evaluator (#106).

### D76 — The registry `contradictions` list is the sole source for an entity note's rendered callouts; merges union it like every other list field (issue #288)

D68's overlay promised "the registry keeps the full contradiction list, so unresolving restores an item" — true for the leads report (registry-driven), but false for entity notes. `write_vault.run` rendered the note body by accumulating the *note's own prior text* plus this batch's incoming callouts, then filtering resolved ones — it never consulted `entry["contradictions"]` at all. So the first ingest touch after a resolve physically deleted the callout from the note with nothing left to restore it from, and `merge_entities.merge()` didn't union the `contradictions` field the way it already unioned aliases/appears_in/timeline_events, so a merge silently dropped the losing entity's registry callouts wholesale — reintroducing the #252 dead-signal bug for anything that arrived via a merge.

Both writers now treat the registry list as the ledger: `write_vault.run` folds the note body's existing callout blocks into `entry["contradictions"]` (a one-time self-healing backfill for pre-#282 vaults or a stray hand-edit), persists the union, and renders the note from that list minus resolved ids — a per-item filter (`resolutions.filter_callouts`, now list-in/list-out) rather than re-splitting rendered text on blank lines, which also fixes a callout with an internal blank line evading resolution. `merge_entities.merge()` unions `contradictions` the same way as its other list fields; `merge_entities.run()` renders the survivor's note from that merged list (plus any note-only backfill from both notes) instead of concatenating note bodies. `pipeline/resolutions.py` gained `split_callouts`/`dedup_callouts` to support this; `filter_callouts`'s signature changed from string-in/string-out to list-in/list-out.

**Tradeoff:** none of substance — this closes the gap between D68's stated contract and what the code did, using the same registry-as-ledger design D68 already committed to. A callout hand-deleted from a note body now resurfaces from the registry on the entity's next touch, which is correct under that design (the sanctioned way to silence one is `watchdog resolve`, not editing the note) but is a behavior change worth knowing about if anyone had been relying on the old, silently-broken deletion.

### D77 — `document.summary` becomes a whole-document digest; sectioned docs compose it post-merge (issue #279)

The one-line orientation summary is redefined as a variable-length, fact-grounded digest — for a working journalist a digest of the material facts beats "what this document is." Non-sectioned docs compose it inline in the extraction call (zero extra calls, full-text grounding); sectioned docs — where no section ever sees the whole document — get one post-merge call over the merged key_facts, with a deterministic stitched fallback on failure (no retry/backfill machinery). Both paths run at the **extractor tier** (`extract_model`, default Sonnet — the same model that read the document), not the finalizer tier: `document.summary` is conceptually extraction output, so the same knob that governs how well the document is read governs how well it is digested, and the two paths never disagree on model. The post-merge call is handed the same context a whole-document extractor gets short of the raw text itself — filename, domain skill, investigation brief, sidecar — so the only thing the sectioned path lacks is the full text, for which the merged key_facts stand in; the skill/brief guide emphasis and framing, never new facts. The post-merge call is small (facts, not full text), so the extra Sonnet call on a sectioned doc is negligible next to the many section calls already paid for it. This is a conscious partial reversal of D26 ("extraction indexes, doesn't restate") for the summary field only: restatement is bounded by a hard three-paragraph cap and by the rule that every claim in the digest must also exist in key_facts (framing/posture/absence observations are the only permitted additions). That grounding rule is enforced by the prompt, not by code — there is no post-hoc check of the digest against key_facts (unlike quote verification), so a hallucinated claim would pass; the field is a reporter's orientation aid, not a citable source, which is why the unverified restatement is an acceptable cost. Tradeoff: the two paths are deliberately inconsistent — sectioned (usually the densest, most important) docs get the leaner facts-derived digest — because feeding 200 pages to one composing call is not possible; levelling down to facts-for-everyone would make the common case worse and cost an extra call on the majority.

### D78 — Entity id/type sanitized before use as a path segment, in two layers; entity name / document title defanged before wikilink interpolation (issues #303, #305)

I1 already stamps `morgue_entity_id`/`morgue_document_type` as slugs before they become path segments (D2 et al.), but entity `id`/`type` — the sibling fields that name every entity note's path — were the one model-supplied path source left raw: `write_vault._new_entity` built `note_path` from `entity['id']` verbatim and `_type_dir` only lowercased `type`. A hostile document could induce an id like `"../../../ESCAPED"`, and the poisoned path is persisted to the registry, so the escape is durable, not one-shot (#303).

Fixed in two layers, matching the security review's proposal: (1) `postflight._sanitize_entity_ids` slugifies every entity `id` immediately after `_apply_match_ids`, remapping `key_facts.entities` tags and `roles.target_id` so referential integrity holds, with a name-derived (then generic placeholder) fallback and collision disambiguation for the rare id that slugifies to empty; `write_vault._type_dir` now runs `type` through the same `slugify` (not just `.lower()`) rather than mutating the stored `type` field, since `type` is a display value (e.g. "Person") shown as-is in frontmatter — slugifying it in place would silently lowercase every entity's displayed type. (2) `write_vault._assert_in_vault` is a resolve-based backstop at the three points a note/morgue path is built (entity note, document note, morgue dir): it `sys.exit`s if the resolved path would land outside the vault, in case a malicious value slips past layer 1. Separately, entity `name` and document `title` — interpolated into wikilink display text and headings without the `[[`/`]]` defang that `research.neutralize` already gives sidecar values — let a hostile name close a wikilink early and forge a second one (#305); those interpolation points now route through a `write_vault._defang` wrapper around `research.neutralize`. The mirror image on the *target* side is `_role_line`'s `role['target_id']`: for a profiled target it's already slugified upstream, but a role can name an unprofiled entity (leads.py's "named but never profiled"), whose `target_id` never passed that pass and lands raw in the wikilink target — so `_role_line` slugifies it at interpolation, which both blocks the forge and keeps the link pointing where the note would live.

**Tradeoff:** slugifying ids can rarely collapse two distinct ids to one slug, routing them through the existing merge/reconcile path — acceptable, and already how `morgue_entity_id` behaves. When two entities carry a *literally identical* id, `_sanitize_entity_ids` disambiguates the second to `-2` but leaves references bound to the surviving first entity (it only remaps an old id that no longer names any entity), so a duplicate can't silently steal the original's fact tags. `_defang` inserts a space into a literal `[[`/`]]` in a legitimate name — vanishingly rare, a cosmetic cost against a link-forgery vector.

### D79 — `watchdog.cmd.setup._persist` chmods `config.json` to 0600 unconditionally (issue #304)

`config.json` holds the archive.org S3 `wayback_access_key`/`wayback_secret_key` in plaintext (both marked `"secret": True`), but `_persist` never chmodded the file, so it landed at the process umask's default (typically 0644, group/other readable) — unlike the model-API-key store (`auth._save_state`), which already does `os.chmod(path, 0o600)`. On a shared machine, any other local user/process could read the key and submit Wayback captures under the journalist's account.

`_persist` now chmods the file 0600 after every write, mirroring `auth._save_state`, so an existing loose-permission file from before this fix is corrected on the very next `watchdog configure` rather than requiring a one-time migration.

**Tradeoff:** none — `config.json` also holds non-secret settings, but 0600 on the whole per-user file is harmless.

### D80 — Briefing gets extraction's output ceiling; on overrun it fails loudly rather than shipping a silently degraded retry (issue #296)

The post-ingest briefing call ran at the generic 8000-token output ceiling while its schema's arrays (`what_was_ingested`/`connections`/`leads`/`anomalies`/`emerging_patterns`/`open_questions`) scale with batch size — a large or dense batch could truncate the JSON mid-object and lose the whole briefing, and a bare re-run via `watchdog finalize` hit the identical ceiling deterministically (a guaranteed second failure re-spending the full input).

Two changes: (1) `briefing` gets the same 16000-token ceiling as `extract`/`extract-section` — a value already proven safe non-streaming on this SDK, so no new streaming plumbing; this alone roughly doubles the headroom and fixes the reported case. (2) When the briefing still overruns, `_post_ingest` records `out["briefing_error"]` and surfaces a loud, cause-specific warning ("output limit exceeded — re-ingest in smaller batches") rather than retrying. An earlier draft retried once with a degraded prompt (scratchpads dropped, facts capped to 8/doc, sliced positionally), but two problems sank it: the retry *silently* shipped a briefing missing material facts — a subtle trust hazard in a tool whose whole value is not missing facts — and there is no telemetry yet showing 16000 is ever overrun (the reported bug was at 8000), so the retry was machinery for an unmeasured case (contrast #241/#263, which explicitly wait on real per-call data). Failing loudly loses nothing else — per-doc facts, entity notes, and the timeline are already on disk; only the synthesized briefing is absent — and the pending batch can be discarded on the next ingest to unstick.

**Tradeoff:** a batch large enough to overrun even 16000 gets no briefing (just its constituent facts on disk) and must be re-ingested in smaller batches, rather than an automatically-degraded briefing. Accepted deliberately: for an investigative tool a silently-incomplete briefing is worse than an honest failure, and the real fix is streaming (an unbounded ceiling), left as future work in a follow-up issue and gated on telemetry (`usage-<ts>.json` `output_tokens`) actually showing 16000 binds.

### D81 — Session skills report; only the pipeline writes pipeline-owned notes (prompt review)

`/watchdog-surface` used to instruct the session to write new `[!contradiction]` callouts directly into entity notes. Pipeline callouts are verified at extraction time and tracked by the resolutions layer (`watchdog resolve`/`unresolve`); hand-inserted ones bypass both, so a session-written callout was never verified and could never be resolved away. Surface now reports cross-document discrepancies as labelled candidates in its `briefings/surface-*.md` report only — extending the I1/I5 single-writer principle to investigation sessions: a session writes its own artifact classes (`queries/`, `wiki/`, briefings, the research links file), never pipeline-owned notes. Riding along: untrusted-content guards added to the two model prompts that consume document-derived text without one (`briefing`, `synthesis`) and to the two session skills that read raw untrusted text (`watchdog-query`'s search passages, `watchdog-research`'s fetched pages), matching the guard `extract_instructions` and `digest` already carry; stale `/watchdog-ingest` references and drifted registry field names corrected across the skills.

**Tradeoff:** newly detected contradictions no longer land in the entity note automatically — and no later ingest re-derives them, because the extraction-time check only compares an *incoming* document against the vault, never two already-ingested documents against each other; a surface-found candidate lives only in its report until acted on. Accepted because an unverified, unresolvable callout in a pipeline-owned note is worse than a labelled candidate in a report. If candidates prove common in practice, the escape hatch is a small deterministic promote command (a `watchdog` CLI that writes a verified callout through the pipeline's own writer, in the mould of `write-entity`/`watchlist-add`) — not session writes.

### D82 — `watchdog contradiction-add` promotes a verified surface candidate into the note (issue #312)

Builds the escape hatch D81 anticipated. `/watchdog-surface` now only *reports* cross-document contradictions as candidates; there was no sanctioned way to get a verified one into the entity note (sessions must not write pipeline-owned notes, and no CLI covered it). `watchdog contradiction-add <entity-id> --label … --a … --a-doc … --b … --b-doc …` (`cmd/contradiction.py` → `pipeline/contradiction.py`) writes the callout in the exact `[!contradiction]` format extraction emits, into the entity's registry `## Contradictions` ledger, then re-renders the note through the pipeline's own `build_entity_note` with the resolved-contradiction overlay applied. Because callouts are content-keyed (`contradiction:<callout-hash>`), the promoted one is picked up by the lead sweep and acted on by `watchdog resolve`/`unresolve` with no extra registration. Run from inside the vault, no model call; validates the entity id and both document slugs, and is a no-op if the callout already exists. The surface report ends each candidate with a ready-to-run command line, so promoting a verified one is a copy-paste — the journalist stays the gate, the pipeline stays the sole writer (§I1, §I5).

**Tradeoff:** the callout's two sides are whatever the journalist types on the command line — this command trusts that input rather than re-deriving the discrepancy from the documents, so a mistyped value or wrong slug produces a wrong-but-well-formed callout. Accepted because the journalist has already verified the candidate against the sources by the time they run it (that is the whole point of the surface-candidate → verify → promote flow); re-deriving would just rebuild the extraction-time check this deliberately sits downstream of. Registry-sourced document titles are still defanged on the way into the wikilink (D78/#305); the journalist-typed values are left verbatim.

### D83 — `contradiction-add` is an internal action, promoted via `/watchdog-surface` confirmation

The #312 implementation exposed `watchdog contradiction-add` as a public, long-flag command and had `/watchdog-surface` print copy-paste command lines per candidate. That pushed friction onto the journalist and cluttered top-level CLI discovery for something that is really a niche follow-up action from a specific report.

The command remains deterministic and available, but is now treated as internal: hidden from top-level `watchdog -h` and removed from the public README command table. `/watchdog-surface` now asks for explicit promotion confirmation per candidate and, when confirmed, runs `watchdog contradiction-add` itself and reports the outcome. This keeps the verification gate with the journalist while avoiding manual command construction.

**Tradeoff:** power users lose easy discoverability of a direct CLI affordance and now depend more on the `/watchdog-surface` workflow to invoke it. Accepted because the command is semantically tied to that workflow, and reducing accidental/drive-by usage matters more than direct discoverability.

### D84 — The classifier reads the document's provenance sidecar

Classification saw only the document's first `classify_pages` pages, so a document whose type is ambiguous from its text alone — a bare form, a scanned table, a spreadsheet dump — could be misrouted even when its `.yml` sidecar named exactly where it came from. The sidecar (`source`/`obtained` plus the collection `notes`) now rides into `build_classify_prompt` alongside the excerpt and skill index, mirroring how extraction already receives it (`_read_sidecar` at the classify call site). The classify prompt labels the sidecar as data, not instructions, and the call's output schema is constrained to a skill filename, so a hostile or injected sidecar can at worst nudge skill selection — it cannot exfiltrate context or execute. The block is omitted entirely when no sidecar exists, so pinned-skill runs and sidecar-less documents are unchanged.

**Tradeoff:** a misleading or stale sidecar note can now pull classification the wrong way (e.g. a source URL that no longer matches the document's actual content). Mitigated because the document text is still present in the same prompt and, per the template, governs when the two disagree — the sidecar is a tie-breaker for ambiguous text, not an override.

### D85 — `scripts/analyze-session` folded into `watchdog usage` (issue #319)

D64 rewrote the tool to read `usage-<ts>.json` directly but left it as a standalone script under `scripts/`, requiring a repo checkout to run. Moved the same logic verbatim into `cmd/usage.py` (presentation-only — reads and formats an existing registry file, no pipeline logic to split out) and registered it as `watchdog usage [project]`, resolved through the same `_resolve_vault` helper `leads`/`watchlist` already use (a name, or the current directory). `--all` still compares every run; a new `--run TIMESTAMP` flag picks one specific past run by (partial) filename match, replacing the script's "pass a path to a specific usage-<ts>.json" mode now that the command addresses vaults by name/cwd rather than arbitrary paths. `telemetry` is registered as an alias.

### D86 — `watchdog usage` shows cache-write/effort/auth per call; usage files moved into `Registry/usage/` (issues #317/#319 follow-up)

Two gaps surfaced while using `watchdog usage` day to day. First, `cache_creation_input_tokens` was accumulated into every totals dict since D50 but never printed anywhere — a call could process (and pay for) tens of thousands of tokens on a cache miss while showing a single-digit `Input` figure, with no visible number accounting for the rest. Second, `effort` and `auth_mode` were available on `ModelResult` per call but never threaded into `_record_usage`, and `attempts` (already recorded) was never surfaced in the CLI output — so neither the reasoning-effort tier nor which billing lane (subscription vs. api-key) paid for a call, nor a call that needed a schema-validation retry, was visible.

Fixed by: adding a `C.write` column alongside `C.read`/`Output` in every table (`_print_stage`, `_analyze_run`'s TOTAL line, `_analyze_all`'s comparison table); threading `effort` and `auth_mode` through `_record_usage`/`_call_model`/`_finish_batch_item` (the batch call site hardcodes `auth_mode="api-key"` since the Batches API requires it, D52); and adding `Effort`/`Auth` columns plus a `×N` retry marker on the cost figure to `_print_stage`'s per-call rows (kept out of `_analyze_all`'s cross-run comparison table, to avoid over-widening a table meant for at-a-glance comparison — matching the precedent already set for `Effort`).

Riding along: `usage-<ts>.json` moved from the flat `.watchdog/Registry/` dir into `.watchdog/Registry/usage/` — it is the one registry file that accumulates a new instance every run rather than being a fixed single current-state file, so it no longer belongs alongside `entities.json`/`documents.json`/etc. A new `orchestrate.usage_files(vault)` helper reads both the new subfolder and the old flat location (merged, sorted by filename since the timestamp format sorts chronologically) so a vault ingested before this move keeps its full usage history; `latest_usage`, `ingest_setup.cost_estimate`, and `cmd/usage.py` all now go through it instead of globbing a registry dir directly.

**Tradeoff:** none of substance — the cache-write/effort/auth/attempts additions are pure display of already-computed data, and the folder move is fully backward-compatible via the merged helper. The one real cost is a slightly wider per-call table (two more columns), accepted since the alternative — telemetry fields silently computed but never shown — was the actual bug this closes.

### D87 — User docs restructured: slim README plus a `docs/` folder (issue #166)

Replaced with a ~120-line README that is only a front door, and eight single-purpose pages under `docs/` (install, getting-started, investigating, commands, configuration, vault, skills, troubleshooting) governed by a one-canonical-home-per-topic rule: a topic is documented on exactly one page and linked from everywhere else. `docs/` is MkDocs's default source directory, so these pages become the GitHub Pages site (#19) as-is. ### D88 — DeepSeek V4 readiness: corrected pricing, non-thinking default, thinking as a `-thinking` model marker (issue #320)

Preparing DeepSeek as a cheap seeding backend for large-project ingest surfaced three problems. First, `_OPENAI_PRICING` still carried the deprecated V3 `deepseek-chat`/`deepseek-reasoner` split at stale rates; replaced with the V4 tiers at current per-token prices (`deepseek-v4-flash` $0.14/$0.28 per M in/out, `deepseek-v4-pro` $0.435/$0.87). Second, DeepSeek V4 collapsed thinking and non-thinking into a single model switched by a request param whose provider default is thinking-**on** — wrong for schema-bound extraction, which is cheaper and more predictable without it. We wanted non-thinking as the default and a way to opt in, but without adding a provider-specific knob: the existing `effort` intent can't express it (it already defaults to `high`, and its Claude semantics would leak).

Resolved by encoding the choice in the model token itself — `deepseek-v4-flash` (non-thinking) vs `deepseek-v4-flash-thinking` — so it rides the existing `[backend:]model` grammar with zero new knobs. `_openai_complete_async` strips the `-thinking` marker (DeepSeek base URL only), uses the bare id for both the request and cost lookup, and always sends DeepSeek's explicit toggle (`{"thinking": {"type": "enabled"|"disabled"}}`, verified against DeepSeek's official docs) so the mode is pinned rather than left to the provider default. Effort stays dropped for DeepSeek (its reasoning is the thinking toggle, not a tier).

**Tradeoff:** the marker overloads the model string with a mode bit, which is slightly less discoverable than a dedicated flag — accepted because the alternative was a DeepSeek-only knob threaded through every stage's config, CLI, and help text. Kept separate from the provider-aware sectioning work in #321.

### D89 — Provider-aware sectioning: thresholds scale with the model context window (issue #321)

Sectioning was tuned around Claude: a fixed `section_token_threshold` (120K est tokens) and `section_token_budget` (60K), regardless of which model does the extraction. With DeepSeek V4 (a 1M-token window) available as a seeding backend, those fixed numbers left most of the window unused — a large document that DeepSeek could read in one call was split into many, adding calls, latency, and orchestration overhead for no reliability gain.

Resolved by deriving both defaults from the extraction model context window instead of hard-coding them. `model_client.context_window` maps a resolved model id to its window via a substring table (DeepSeek V4 1M, Claude 200K, gpt-5 400K, …, with a conservative 128K fallback for anything unlisted), and `section.py` takes the threshold as 0.6 of that window and the budget as 0.3 — reserving ~40% for the schema, domain skill, carried entities, scratchpad, and the extraction output. The fractions are chosen so a 200K Claude window reproduces the historical 120K/60K exactly, so the default path is unchanged. The extraction model is threaded into the two sectioning-decision `section.run` call sites; the output-overrun fallback keeps its own small forced budget. The two config keys become advanced overrides: their default is the `auto` sentinel (an unset key or `"auto"` means model-aware; a fixed integer pins the value). A pinned integer does **not** rescale when `extractor_model` changes — `configure` shows the value `auto` resolves to for the current model, and the help text flags the caveat.

**Tradeoff:** larger single-call chunks on big-window models increase the per-call output-complexity and schema-failure blast radius, but the existing output-overrun fallback (force-section at 15K, D19) already re-sections a call that truncates, so the downside is a rare extra retry, not a lost document. Window figures are hard-coded and will drift as vendors change them — accepted as a small, centralized table to update, and unlisted ids degrade to the safe 128K default.

### D90 — Removed the `embed_images` config knob (dead-on-arrival visual path)

`embed_images` (default off) switched Docling's markdown export to `ImageRefMode.EMBEDDED`, base64-embedding figures into the OCR'd markdown "so Claude can see charts." It never worked: extraction prompts are built as `{"type": "text"}` content blocks (`prompts.build_extract_prompt`), and `_flatten_prompt` keeps only `.text` for the non-Claude backends — there is no image content block anywhere in the pipeline. So an embedded base64 data URI reached the model as *text*, not vision: the model cannot decode it, and a single image adds thousands of tokens of noise (base64 is ~33% larger than the bytes). The knob was pure cost with none of its advertised benefit, and its help text was misleading.

Removed the key, its Docling toggle (export is now always `PLACEHOLDER` → `[image]`), the guided-setup membership, the docs row/prose, and the test reference. Image-as-evidence is handled properly by #183's on-demand page rasterization to a vision model, which sends a real image block — the approach that embedding-everything-as-text could never be.

**Tradeoff:** a user who had turned `embed_images` on loses a setting, but it was delivering no vision to begin with, so there is no capability regression — only a smaller, honest config surface and lower token cost. The one real image-as-evidence path is deferred to #183.

### D91 — Non-Claude pricing fidelity: OpenAI rates populated and cache-hit input modelled (issue #170)

`_OPENAI_PRICING` was output-approximate: it held only DeepSeek's cache-*miss* input rate (so a cache hit was over-charged) and no OpenAI rates at all (so cost reported `None` for every OpenAI run). Both are needed before a non-Claude backend can be defaulted to with honest cost reporting.

Widened the table entries from `(input, output)` to `(input, output, cached_input)` and added the GPT-5 family standard rates alongside DeepSeek V4. `_openai_cost` now splits `prompt_tokens` into cached vs uncached from the provider's usage fields — OpenAI nests the count under `prompt_tokens_details.cached_tokens`, DeepSeek reports `prompt_cache_hit_tokens` (with `prompt_tokens` = hit + miss) — and prices each portion at its own rate. A model with no published cache rate repeats its input rate (no discount), so the split is always safe to apply.

**Tradeoff:** the hard-coded rate tables now cover two vendors' fast-moving model lineups and will drift as prices change — accepted as a small, centrally-commented table with source links, matching the existing Claude `_PRICING` approach; an unlisted id still degrades to `None` cost rather than raising, so drift is a stale figure, never a crash.

### D92 — OpenAI request-shape: explicit capability table replaces the substring reasoning heuristic (issue #170)

Reasoning-model detection was a substring tuple (`gpt-5`/`o1`/`o3`/`o4`/`reasoner`) consulted only to decide whether to send `reasoning_effort`. It was fragile (a coincidental substring, not an intent) and, worse, it did not govern the token field: the client always sent `max_tokens`, which OpenAI *reasoning* models reject — they require `max_completion_tokens`.

Replaced it with a single explicit `_OPENAI_MODEL_CAPS` prefix table (`gpt-5`/`o1`/`o3`/`o4` reason; `gpt-4`/`chatgpt` chat) behind `_openai_is_reasoning`, and routed **both** decisions through it: reasoning models get `reasoning_effort` **and** `max_completion_tokens`; chat models and DeepSeek (classic wire format) get `max_tokens`. The two can no longer drift apart. An id matching nothing is treated as a chat model.

**Tradeoff:** an unlisted id defaults to chat, so a brand-new OpenAI reasoning model is silently denied effort until it is added to the table. Chosen over the reverse (guess reasoning) because the failure modes are asymmetric: a denied effort is a quality/perf miss, while sending `reasoning_effort`/`max_completion_tokens` to a chat model — or `max_tokens` to a reasoning model — is a hard 400. Correctness-safe by default; effort is opt-in per known family.

### D93 — `watchdog auth` collapses to one interactive command; no more `status`/`use`/`set`/`get`/`remove` subcommands

User feedback: a person trying to add a DeepSeek key couldn't figure out the `set`/`get`/`use`/`remove` surface, and `watchdog configure` gave no hint that model authentication lives in a separate command at all. Both were self-inflicted UX debt from `cmd/auth.py` growing subcommand-by-subcommand as providers were added (D37).

`watchdog auth` (bare, no positional arguments) now always shows current settings first — Claude mode, Claude Code login detection, and any stored provider keys, unchanged from the old `status` view — then, on a terminal, asks `Change something? [y/N]`. A "yes" opens one wizard: pick a service (Anthropic, OpenAI, DeepSeek), then, for Anthropic, choose subscription vs. API key (the same choice `watchdog setup` offers, now shared via `_apply_anthropic_choice`); for the OpenAI-compatible providers, store, replace, or delete that provider's key. Off a terminal it just prints status, matching `watchdog configure`'s own bare-mode behavior. `watchdog configure` (bare) now prints a one-line pointer to `watchdog auth` at the top, since the two commands are easy to conflate. All `watchdog auth set/use/...` references in error messages (`model_client.py`, `cmd/ingest.py`, `pipeline/orchestrate.py`) were updated to point at the single `watchdog auth` entry point.

**Tradeoff:** scripting a non-interactive auth change (CI, provisioning) is no longer possible via CLI flags — the only programmatic surface left is hand-editing `~/.watchdog/credentials.json` or setting the provider's environment variable (which already took precedence over a stored key and still does). Accepted because this tool's primary audience is a working journalist at a terminal, not an automation pipeline, and the removed subcommands were the reported point of confusion.

### D94 — Gemini added as a fourth OpenAI-compatible backend, riding the existing shared client unmodified

Google's Gemini API ships an OpenAI-compatible Chat Completions endpoint (`https://generativelanguage.googleapis.com/v1beta/openai`) that speaks the identical wire format `_openai_complete_async` already sends to OpenAI and DeepSeek — same Bearer-token auth, same `response_format`/`reasoning_effort` fields — so no changes to the shared request path were needed, only new registrations: `_OPENAI_BASE["gemini"]`, `_ABACKENDS["gemini"]`, `_BACKEND_PROVIDER["gemini"]`, `_OPENAI_PRICING` rows for `gemini-2.5-pro`/`-flash`/`-flash-lite` and the newer `gemini-3.5-flash`/`gemini-3.1-flash-lite`/`gemini-3.1-pro-preview`, a `gemini-2.5`/`gemini-3` row pair in `_CONTEXT_WINDOWS` (both tiers share a 1M-token window), and `cmd/auth.py`'s generic `_PROVIDERS` dict gained a `gemini` entry (env `GEMINI_API_KEY`) that the existing interactive wizard picked up with no further code changes (D93).

Gemini's compat layer natively accepts `reasoning_effort` on every current model (mapped internally to the model's own thinking budget), unlike OpenAI where only a subset of models accept it — so `_gemini_effort` is an unconditional passthrough, simpler than `_openai_effort`'s capability-gated version (D92) and DeepSeek's separate on/off toggle (D88). Because Gemini isn't in the OpenAI-specific `_OPENAI_MODEL_CAPS` reasoning table, it falls into that table's existing chat-model default and sends classic `max_tokens` rather than `max_completion_tokens` — correct per Gemini's own compat docs, which never demonstrate the reasoning-model field.

Both the 2.5 and 3.x tiers are populated rather than only the newest models: 2.5 Flash/Flash-Lite/Pro are the established, fully-stable choice; 3.5 Flash and 3.1 Flash-Lite are Google's current stable ("Stable" per their own model-version documentation) generation and the more capable/cheaper pick going forward; `gemini-3.1-pro-preview` is included too as the only current Pro-tier alternative on the 3.x line, despite carrying "preview" in its own model id — Google's docs state preview models "will be deprecated with at least 2 weeks notice," which is a materially different (and worse) stability guarantee than the other rows in this table.

**Tradeoff:** Gemini 2.5 Pro's and Gemini 3.1 Pro Preview's published pricing each have a 200K-token prompt-size tier (input/output roughly double past that threshold) that `_OPENAI_PRICING`'s flat `(input, output, cached_input)` shape cannot express; only the ≤200K rate is modelled for both, so cost is under-reported on very large prompts routed to either Pro tier. Accepted as the same simplification already applied elsewhere in this table (rates are the vendor's published figures, not a live lookup) rather than reshaping the pricing table for two models' tiering. Separately, `gemini-3.1-pro-preview` is a preview model id that Google could swap or retire with two weeks' notice — accepted because it is still the only Gemini Pro-tier option on the current generation, and an unlisted/renamed id degrades to unpriced (`None` cost) rather than a hard failure.

### D95 — Claude Code is for general use; ingestion gets its own metered-provider setup wizard

A user who set a Gemini key and routed all three ingest stages (`classifier_model`/`extractor_model`/`finalizer_model`) to `gemini:...` still hit `Error: api-key mode is set but no key is configured — run watchdog auth` on `watchdog ingest`. Root cause: `cmd_ingest`/`cmd_finalize` called `resolve_auth()` (Claude-only) unconditionally, before any stage's backend was even resolved — so a fully non-Claude ingest config still hard-required Claude auth. Fixed by resolving all three stage backends first, then gating on `resolve_auth()` only if a stage actually needs Claude (`extract_backend/post_backend/classify_backend in CLAUDE_BACKENDS`, or unset — the default).

That bug was a symptom of a wider mismatch: setup and the `watchdog auth` status display both treated Claude as the only auth that mattered, with other providers bolted on as an afterthought ("Other providers?"), even though ingestion — the token-heavy stage — is exactly the case where a metered non-Claude provider is often the better default. Reframed the philosophy explicitly: **Claude Code for general use** (subscription or metered; it always runs the interactive investigation skills, §13) **and API-based services for ingestion** (optional, cheaper for volume). `watchdog setup`'s auth step now explains this up front, proactively reports whether a Claude Code login is detected, and — specifically on the subscription branch — warns that ingesting more than a few documents can be token-heavy for a Pro plan's session limits and offers to route ingestion to a metered provider instead (linking to `docs/configuration.md`'s existing "Model backends" section rather than a new doc page). Accepting routes into a new `_setup_metered_ingestion()`: pick a provider, store its key, then pick a model for each of the three ingest stages via a new shared `_pick_model_interactive()` picker (`setup.py`) — the same picker now also backs the interactive `watchdog configure` edit path for those three keys, replacing free-text entry. `watchdog auth`'s bare status view was split into a "Claude Code" section (mode, login detection) and an "Ingestion" section (each stage's resolved provider and a ✓/✗ readiness mark, computed independent of Claude's own mode), so the display answers "will ingest actually work" directly instead of requiring the user to cross-reference `watchdog configure`'s model keys by hand.

**Tradeoff:** the setup wizard is longer for a subscription user who accepts the metered offer (provider pick → key → three model picks) — accepted because it replaces what would otherwise be three separate manual `watchdog configure` edits plus a `watchdog auth` key add, and it is fully skippable (declining leaves subscription-for-everything, the prior default). The api-key branch's original "other providers?" offer is unchanged, since that path was never the source of confusion.

### D96 — `LiveRegion` queries the terminal width straight from the OS, not `shutil.get_terminal_size()`

A user reported the live progress region leaving stale duplicate "extracting…" rows on screen during a real ingest run. Root cause: `_render()` sized live rows with `shutil.get_terminal_size((80, 24)).columns`, which checks the `COLUMNS`/`LINES` env vars *before* asking the OS — in a terminal where those vars are stale or absent-but-cached, it can report a width wider than the real screen. A live row that then wraps onto a second physical line isn't accounted for by `LiveRegion`'s own rendered-line count, so the next redraw's cursor-up-N/erase undercounts and leaves the previous frame's text behind. Confirmed with a `pyte` VT100-emulator reproduction: an intentionally-wrong reported width reproduced the exact stale-duplicate-row symptom; the same scenario with a correct width stayed clean even with long lines that wrap.

Fixed with a small `_terminal_width(stream)` helper that calls `os.get_terminal_size(stream.fileno())` first (a direct OS ioctl query, immune to stale env vars) and only falls back to `shutil.get_terminal_size((80, 24))` on `OSError`/`ValueError`/`AttributeError` (non-tty stream, no real fd — the case `shutil`'s own fallback exists for).

**Tradeoff:** none identified — this is a strict correctness fix over the same fallback behavior `shutil.get_terminal_size()` already provided for non-tty streams.

### D97 — Post-flight validation warnings (quote-verify, entity-id/date sanitization) route through the live region and the ingest log instead of a raw stderr print

The same user-reported screenshot showed a quote-verification warning ("`document.key_facts[3].quote not found...`") appear once in the terminal and then vanish, and it was absent from `ingest.log` entirely. Root cause: `postflight.run()` printed these three warning classes directly with `print(f"Warning: {msg}", file=sys.stderr)`, bypassing `orchestrate.py`'s `_say`/`_log`/`LiveRegion` machinery completely. A raw print like this sits outside the live region's own line-count bookkeeping, so it can be erased by the next redraw's cursor-up/erase (D96's mechanism, but here the trigger is a second, uncoordinated writer rather than a wrong width) — and since it never went through `_log()`, it also never reached `ingest.log`, silently dropping a real signal a journalist would want on record.

Gave `postflight.run()` an optional `warn` callback parameter: when provided, each warning is handed to it instead of the raw print; when omitted, the exact original stderr behavior is preserved (needed by `watchdog postflight`'s standalone CLI path, `cmd/ingest.py`'s `cmd_postflight`, which has no live region to route through). `orchestrate.py`'s `_write_postflight` now passes a `warn` callback that prints through `_say()` (so `LiveRegion` knows about the line and won't erase it) and writes the same message to `ingest.log` via `_log()`.

**Tradeoff:** none identified — the default (no `warn` given) behavior is byte-for-byte the same as before, so only the orchestrator's own call site changes behavior.

### D98 — Gemini gets real `json_schema` structured output; OpenAI and DeepSeek stay on `json_object`

A comparison of extraction runs on the same source documents showed Gemini producing noticeably fewer entities than Claude Sonnet (e.g. 11 vs. 20 on one document), with real, verifiable entities missing rather than hallucinated extras on Sonnet's side. Part of the gap traces to `_openai_complete_async`'s structured-output path: all three OpenAI-compatible backends (D37, D94) requested `{"type": "json_object"}` with the schema only pasted into the prompt as text — a portable but weakly-enforced approach, since nothing at the wire level stops a model from drifting off-schema; a validation failure costs a full blind-resample retry (D-prior `acomplete_json` retry shell) rather than a targeted correction.

Checked whether each provider's own `json_schema` mode could safely replace this. DeepSeek's JSON Output docs describe only `json_object` — no schema field exists to send. OpenAI's real Structured Outputs (`strict: true`) requires every property to appear in `required` (optional fields are modelled as nullable unions instead of omitted) — the opposite of `schemas.py`'s deliberate omit-optional-fields design (`_obj()`'s partial `required` lists, matching `extract_instructions.md`'s explicit "omit the field, don't emit null" instruction) — and OpenAI has no non-strict schema-hint mode, so adopting it there would mean maintaining a second, all-fields-required schema variant just for OpenAI. Gemini's structured-output docs describe a real `json_schema` mode whose own schema engine treats `required` as an optional list, same as the existing schemas — a drop-in fit with zero schema changes.

Added `_openai_response_format(base_url, schema)`: returns `{"type": "json_schema", "json_schema": {"name": "watchdog_response", "schema": schema}}` for Gemini's base URL, `{"type": "json_object"}` for everything else. When the schema is wire-enforced, the "Return JSON matching this schema" text is dropped from the prompt too (redundant once the API itself constrains the output structurally) — `acomplete_json`'s local `jsonschema` validation stays in place regardless, as a safety net rather than the only guard.

**Tradeoff:** OpenAI and DeepSeek extraction keeps the weaker prompt-only enforcement for now; a real fix for OpenAI would need a parallel all-fields-required schema variant, scoped out here as a separate, larger piece of work. Gemini's remaining entity-count gap versus Claude (if any, after this change) has not been re-measured yet — this addresses one contributing cause, not necessarily the whole gap.

### D99 — Arrow-key picker's "↑/↓ move · Enter select · q cancel" hint is erased, not left in scrollback

A user testing a live `watchdog ingest` run noted the picker's control-hint line stayed on screen after a selection was made — outliving its usefulness, since it's only relevant while a choice is actually being made. Root cause: `interactive.py`'s `pick()` render loop writes the hint without a trailing newline (so the cursor sits at the end of that row for in-place redraws), and its `finally` block only restored terminal (`termios`) settings and printed one blank line — never erasing the hint text itself, so it was permanently committed to scrollback.

Changed the `finally` block to write `\r\x1b[K\n` instead of a bare `print()`: `\r` returns to column 0 of the hint's own row, `\x1b[K` erases it, and `\n` advances — preserving the pre-existing one-blank-line spacing before whatever the caller prints next, but without leaving the hint text behind.

**Tradeoff:** none identified — the erased text was never meant to be a persistent record of the interaction (the picker's own selection outcome is what the caller prints afterward).

### D100 — Post-flight warnings print after their own document's OK line, not whenever post-flight happened to run

Building on D97 (which got warnings into the live region and `ingest.log` at all), a user still reported a warning visually appearing to belong to the wrong document during a concurrent multi-document ingest. Root cause: `_write_postflight()` printed its warnings immediately, at post-flight-validation time — which always happens strictly *before* `_finish_extraction()`'s own "OK" line for that same document. Under async concurrency, another document's OK line can print in the gap between the two, so the warning reads as attached to whichever document happens to be finishing at that moment rather than the one it actually describes.

`_write_postflight()` now collects warnings into a list and returns them instead of printing, threading them through `_simple_extract`/`_extract_sectioned`/`_extract_document`/`_finish_batch_item` into `_finish_extraction()`, which prints them immediately after its own `_settle()` OK line — in the same style/indentation as the pre-existing coverage-warning block, so they visually tuck under the correct document's own block regardless of what else is concurrently in flight.

**Tradeoff:** none identified — this only changes *when* an already-collected warning prints, not whether it prints or what it says.

### D101 — Chew's progress/ETA row is pinned to always render last in the live region, not wherever it was first inserted

A user reported the chew-phase progress bar not staying "put" during a real run — it appeared sandwiched between finished-file lines above and in-flight rows below, rather than staying fixed at the bottom. Root cause: `LiveRegion` renders rows in the order their keys were first inserted into `self._order`, and `preprocess_batch.py` seeded the progress row (`_refresh_progress(0)`) *before* submitting any files to the `ThreadPoolExecutor` — so the progress key was always first in insertion order, with file rows added after it as worker threads picked up work.

Gave `LiveRegion.update()` an optional `pin: bool` parameter: a pinned key is tracked in a new `self._pinned` set and `_render()` now draws non-pinned keys first, pinned keys last, regardless of `self._order`'s actual insertion sequence. `preprocess_batch.py`'s `_refresh_progress` passes `pin=True` for `_PROGRESS_KEY`, so the bar now always renders below every in-flight file row no matter when it was seeded relative to them.

**Tradeoff:** none identified — `pin` is opt-in and unused by every other `LiveRegion` caller (ingest's per-document rows), so existing insertion-order rendering is unchanged for them.

### D102 — ingest.log gets a per-document START line, and usage records a per-call end_ts for wall-clock elapsed

Following a diagnostic thread about why `ingest.log` reads as if documents extract sequentially: the log only ever recorded completion (`OK`/`FAILED`) and the vault-commit `INGEST` line, both written after a document's multi-minute extraction finishes. Because extraction is concurrent (an `asyncio.gather` over a `Semaphore`) but the log is completion-ordered, a reader can't see that all documents started together — the staggered `OK` lines look like one-after-another work.

Two additions, both purely observational:

1. `_extract_document` now writes `START <filename>` to `ingest.log` the moment a document's extraction begins (after preflight, before classify). The gap between a document's `START` and its own `OK`/`FAILED` is now that document's real extraction time, and the clustered `START` timestamps make the parallel launch visible.

2. `_record_usage` now stamps each call with `end_ts` (epoch seconds at record time). Paired with the existing `latency_s`, this gives every call a `[end_ts − latency_s, end_ts]` interval, so `watchdog usage` can report **wall-clock elapsed** per stage — `max(end) − min(start)` — alongside the summed per-call latency it already showed. For a concurrent stage the summed figure overstates the real wait (three 4-minute calls that overlapped took ~7 minutes of wall time, not 12); the elapsed line makes that explicit, and is shown only when the calls actually overlapped. Old `usage-<ts>.json` files without `end_ts` fall back to the summed figure alone.

**Tradeoff:** the usage schema gains a field, but it's additive and back-compatible — `_wall_span` returns `None` when no call carries `end_ts`, so pre-existing usage files (and the `watchdog status`/estimate paths that read only the `totals` block) are unaffected.

### D103 — DeepSeek thinking-mode extraction/briefing get a higher `max_tokens` ceiling than non-thinking calls

A comparative ingest of the same 3 documents on DeepSeek-v4-pro with thinking enabled extracted 25-58% fewer key facts per document than the same run on Claude Sonnet, and elided the middle of one verbatim quote with "…". Root cause: DeepSeek's reasoning-model API caps chain-of-thought + final answer under one combined `max_tokens` (default 32K, max 64K — https://api-docs.deepseek.com/guides/reasoning_model), but `acomplete_json` applied the same flat, thinking-agnostic ceiling from `_TASK_MAX_TOKENS` (16000 for extract/extract-section/briefing) regardless of whether thinking was on. With thinking enabled, the CoT ate into that budget before the model wrote any of the actual JSON, starving the structured output (#337).

Added `_DEEPSEEK_THINKING_MAX_TOKENS = 48000`, applied in `acomplete_json` only when the resolved backend is `deepseek`, the model id carries the `-thinking` suffix, and the task is one of the large-output tasks already in `_TASK_MAX_TOKENS`. Every other backend/task keeps its existing ceiling — Claude's extended thinking uses a separate `budget_tokens`, not a shared pool with the final answer, so it doesn't have this failure mode.

**Tradeoff:** a DeepSeek-thinking extraction/briefing call now costs more per call (more output tokens available, and DeepSeek bills the CoT tokens as output) — acceptable since thinking mode is opt-in via the `-thinking` suffix, not the default.

### D104 — Response pagination + authoritative truncation detection: no truncated extraction is ever accepted

Sectioning (D89, #321) gates on a document's *input* size against the context window, but says nothing about the *output* ceiling. A large, entity-dense document can sit comfortably under the input threshold yet need more output than the provider's fixed `max_tokens` allows (extract/extract-section cap at 16K; DeepSeek-thinking at 48K per D103) — the JSON truncates mid-object. Worse, a truncated response can still *parse* if it happens to cut on a valid boundary, so the old "reject on parse failure" guard could silently store a partial extraction, and the reactive output-overrun fallback only fired for multi-page documents (a long single-page text file had no recourse).

Three layers now guarantee no truncated extraction is accepted, across all established backends (claude-agent-sdk, claude-api, deepseek, openai, gemini):

1. **Detection (universal).** Every backend returns its `finish_reason`/`stop_reason`; `acomplete_json` treats a max-token cut (`length`/`max_tokens`) as authoritative and rejects the result even when it parses — truncation is never inferred from a parse failure.
2. **Pagination (recovery).** For backends that can continue a partial reply by prefilling it as the assistant turn — claude-api (assistant prefill) and deepseek (chat-prefix-completion beta at `/beta/chat/completions`) — `_complete_with_pagination` re-issues with the partial prefilled and concatenates until a natural stop, guarded by `_MAX_CONTINUATIONS`. Structured-output enforcement is dropped on a continuation (constrained decoding can't resume mid-object; the concatenation is validated by the shared shell), but effort is preserved.
3. **Proactive sizing.** openai and gemini return a *new* message rather than continuing, so they can't paginate; instead `output_ceiling_for_sectioning` caps the sectioning threshold by an output-derived input ceiling so the first whole-document call is sized to fit. The agent-SDK backend has no client-enforced cap, so it needs neither.

The reactive fallback remains as a universal backstop and now also covers single-page documents (their text splits into character windows). Continuation is explicitly not escalation (I4): same model, same effort, finishing one response.

**Tradeoff:** pagination adds provider-specific request paths (assistant prefill vs. DeepSeek's `/beta` prefix flag) and a continuation loop, and the two prefill-less providers rely on an *estimated* output-per-input density (`_OUTPUT_PER_INPUT_RATIO = 0.8`, `_OUTPUT_SAFE_FRACTION = 0.7`) that can misjudge an unusually dense document — but the estimate only affects *how often* the first call fits; the detection layer means a miss degrades to a loud re-section, never to silently truncated data.

**Known limitations (acknowledged, not fixed here).** Three edges are accepted because each degrades to the safe path — a loud rejection and re-section — rather than to silent data loss: (1) *Continuation re-sends its own output as input.* Each pagination round prefills the whole accumulated partial, so a document needing many rounds grows the input side and could itself approach the context window and error mid-continuation; the `_MAX_CONTINUATIONS` guard and reactive fallback catch this. (2) *Detection depends on the provider surfacing a truncation `finish_reason`.* If a backend (e.g. Gemini's OpenAI-compat layer) returned no `finish_reason` on a cut, a truncated-but-parseable response could slip the detection layer — mitigated because openai/gemini are sized proactively (they rarely truncate) and any truncation that yields *invalid* JSON is still rejected on the parse path. (3) *Anthropic assistant-prefill composed with `output_config.effort` is unverified against the live API*; a rejection there is safe (the concatenation is validated and, failing that, the document re-sections).

### D105 — Entity `type` is a closed six-value vocabulary, canonicalized deterministically at the write boundary

`entity.type` was free text the extraction model invented per document, yet it is load-bearing twice: it is half the identity key that decides whether two same-named entities are the same real-world thing (`write_vault._reconcile_entity_ids`), and it is the `entities/<type>/` folder segment. When the model's type vocabulary drifted document-to-document — `company` in one filing, `financialinstitution` in the next — reconciliation silently missed and the same entity forked into two folders (#335). The failure was invisible: no error, just a quietly duplicated subject.

Fixed with a closed vocabulary of six **durable-referent classes** — `person`, `organization`, `public-body`, `place`, `asset`, `proceeding` (plus a code-only `other` backstop) — enforced in three layers: (1) the extraction prompt states the six as the only allowed values; (2) the extraction schema's `type` carries a `description` naming them; (3) `entity_type.canonical_type()` deterministically collapses whatever the model still emits (via a normalized synonym map) onto one bucket, applied in `write_vault.run()` before `type` becomes load-bearing, so both the reconciliation key and the folder follow one canonical value regardless of backend compliance. The vocabulary is deliberately coarse: only *actors, places, and things* earn a type — one-off occurrences live on the timeline (a dated `key_fact`) and records live in the document store, so neither needs a bucket. `case` was generalized to `proceeding` to cover any persisting adjudicative matter (litigation, insolvency, arbitration, inquiry), keyed one entity per matter rather than per hearing.

**Deliberate deviation — description, not a hard schema `enum`.** Only Gemini and Anthropic wire-enforce a JSON-schema `enum`; DeepSeek/OpenAI get `json_object` mode with the schema in the prompt, and `acomplete_json` hard-validates the parsed output against the schema (retry once on the same model, then raise — D98). A strict `enum` on `type` would therefore turn a DeepSeek type-drift from a *silent fragmentation* into a *hard extraction failure* — a regression on the exact backend in the issue. So the schema half is a `description`, and correctness rests on the deterministic `canonical_type` map, not on model compliance.

**Tradeoff:** folders are coarser than the model's free-text labels (a bank, a pension plan, and a union all file under `organization`), and a genuinely novel coinage the synonym map doesn't recognize falls to `other` rather than minting a new folder — prompt steering reduces coinage at the source, but the map is a living list that will need occasional additions. No migration: existing raw-typed entities keep their old folders, so a vault ingested before this change may still show a pre-canonical folder until those entities are next written; the fix prevents *future* fragmentation rather than rewriting history.

### D106 — Ruff linting in CI, conservative rule set, `cli.py` exempt from F401

CI ran the test suite but no static analysis, so a whole class of mistakes — chiefly unused imports and variables, the orphans a change is meant to clean up — could ship silently, since nothing failed unless a test happened to exercise the path (#347). Added ruff as a dedicated, blocking `lint` job (run once, outside the Python test matrix) with a deliberately conservative rule set: pyflakes (`F`) plus the pycodestyle logical-error subsets `E4`/`E7`/`E9`. Line-length (`E501`) and import-sorting (`I`) are intentionally excluded — `I` alone would have reordered imports across 66 files, formatting-adjacent churn unrelated to correctness, and the project adopts no autoformatter here.

`cli.py` is exempt from `F401` via a per-file ignore: it re-imports a wide surface of registry/vault/setup helpers purely so tests can reach them as `watchdog.cli.<name>` for monkeypatching — the same rationale already applied by hand to `import sys` with a `# noqa`. The auto-fix's removal of that seam broke 67 tests, confirming the imports are intentional re-exports, not dead code; scoping the ignore to that one module keeps F401 enforced everywhere else. Type checking (pyright) is split into a follow-up (#348) because, unlike ruff's mechanical findings, its 131 findings need per-case judgment (platform false positives, benign sloppiness, a few possibly-real bugs) that would bloat a lint PR.

**Tradeoff:** the conservative set leaves style and formatting unchecked (no line-length, no import order), and the `cli.py` F401 exemption means a genuinely unused import in that one file will not be caught — accepted because the module's test-seam role makes unused-looking imports the norm there.

### D107 — Briefing entity references are resolved against the registry manifest after synthesis, not trusted to the model

On DeepSeek, the post-ingest briefing's `new_entities` (and the "Recent additions" it mirrors into `hot.md`) sometimes came back as raw kebab-case entity ids (`andrew-hanrahan`) instead of display names (`Andrew Hanrahan`) — the RESULTS block the briefing model reads carries ids, and nothing told it which of those, if any, should surface as human-readable names (#342). Related: the DeepSeek/OpenAI path appends the JSON schema verbatim to the prompt, but `BRIEFING`/`SYNTHESIS` carried almost no field `description`s, leaving semantics like this to model discretion (#355).

Fixed at three layers, deterministic-first: (1) `_write_briefing` now loads `Registry/manifest.json` and runs every briefing string array (`new_entities`, `connections`, `leads`, `anomalies`, `emerging_patterns`, `open_questions`, `what_was_ingested`) through a resolver that replaces an item exactly matching a known entity id with its manifest display name, leaving everything else untouched; (2) the briefing prompt now states explicitly that entity mentions must use the display name, never the internal id; (3) `BRIEFING` and `SYNTHESIS` schema properties gained one-sentence `description`s (the extraction-family schemas were left alone — their semantics already live in `extract_instructions.md`).

**Tradeoff:** the resolver only fires on an exact whole-item match — a slug embedded inside a prose sentence (e.g. "...alongside andrew-hanrahan, who...") still relies on the prompt instruction rather than being deterministically caught, since rewriting substrings inside prose risks corrupting legitimate text. The prompt/schema layers are the mitigation for that residual case.

### D108 — OpenAI-compatible backend hardening: reasoning-model output ceiling + bounded 5xx retry

Two gaps from the #354 per-provider parameter audit. First, OpenAI reasoning models (gpt-5 family, o-series) share one `max_completion_tokens` budget between chain-of-thought and the visible answer — the same starvation mode #337 fixed for DeepSeek thinking, unhandled here: at the flat 16K ceiling, heavy reasoning could truncate the extraction JSON. Reasoning models now get the same raised 48K ceiling on the large-output tasks. Deliberately, `output_ceiling_for_sectioning` still plans against the base task budget for these models: the raise is shared with reasoning, so the JSON itself can't count on it — sectioning stays conservative while the wire cap prevents starvation. Second, the httpx path for openai/deepseek/gemini had no transient retry (the Anthropic SDK retries 429/5xx internally), so one transient 502/529 failed a document outright; it now retries 5xx twice with short backoff. 429 is excluded — it keeps raising `RateLimitError` on the first response so the orchestrator stops the batch cleanly.

**Tradeoff:** the sectioning-vs-wire asymmetry means a reasoning model that spends little on reasoning leaves headroom unused (sectioning was conservative), and one that spends heavily can still starve the answer in pathological cases — 48K is a static guess pending real telemetry, same status as the DeepSeek figure. The 5xx retry adds up to ~6s of backoff latency to a genuinely failing call before it surfaces.

### D109 — Pre-flight hoists prior timeline events into one shared deduped list

`postflight.explode_key_facts` (D26) deliberately fans each dated key_fact onto every tagged entity's registry timeline, so a note can render its own chronology. But pre-flight was re-sending each entity's full timeline digest inside its own candidate object, so a fact tagging N recurring entities cost N verbatim repeats in every later extraction prompt whose document mentioned them (observed via the #216 digest-size telemetry). Pre-flight now hoists prior timeline events out of the per-candidate digests into one top-level `existing_timeline` list, deduplicated by (date, event text) and each entry tagged with the candidate ids it concerns — the same shape the model emits `key_facts` in to begin with. `build_extract_prompt`/`build_section_prompt` render it as a new EXISTING_TIMELINE block, and `extract_instructions.md`'s contradiction check now looks there for an entity's prior dated events instead of on its EXISTING_ENTITIES entry.

**Tradeoff:** the extractor no longer sees a per-entity chronology inline — it must join events to candidates via ids; registry and note rendering are unchanged (the fan-out still happens at write time).

### D110 — Embedded file metadata captured deterministically, presented as forgeable evidence, checked by a deterministic date-mismatch rule

A document's own embedded metadata — a PDF's DocumentInfo, an Office file's core properties, an image's EXIF, a media file's container tags — is an investigative signal the extracted text alone can never surface: a "2019 board resolution" whose PDF was actually created in 2023 is a lead. `pipeline/file_metadata.py` reads it at chew time, always from the original source path (never a Ghostscript-cleaned or chunk temp file, which strips DocumentInfo), and normalizes every family onto one small allowlisted, flat shape — every value coerced to `str` and capped at 200 characters, the same posture already applied to the `.yml` sidecar, since this is untrusted, attacker-controllable content that could otherwise inject text into the extraction prompt via a crafted XMP/EXIF payload. It is stamped as a top-level `file_metadata` key (a sibling of the existing `metadata` key, never nested inside it — `metadata` is *processing* facts the pipeline asserts, `file_metadata` is *file-intrinsic* claims the file makes about itself) and persisted into the `documents.json` registry entry for future cross-document clustering, but never rendered into the document note body.

The model sees it only as data to weigh, not ground truth: the extraction prompt's `FILE_METADATA` block states explicitly that the metadata is forgeable and often machine-generated (a scanner's Producer field says nothing about who authored the scanned original; an Office template's creation date is inherited by every document built from it), alongside the `ocr_used`/`source_type` processing facts so the model can judge whether a creation date plausibly describes the original. The one check that matters most — flagging a suspicious gap between the file's creation date and the document's claimed date — is kept fully deterministic (`file_metadata.check_date_mismatch`, modeled on `quote_verify.verify_quotes`: an annotation, never a gate) rather than left to model judgment, and is suppressed outright when `ocr_used` is true, since a scanned document's file legitimately carries the scanner's creation date — without that suppression, every scanned exhibit in the vault would produce a false lead, which is precisely the failure this feature exists to prevent.

Two Office fields — `company` and `total_edit_minutes` — are read straight out of the OOXML zip's `docProps/app.xml`, because none of python-docx/python-pptx/openpyxl expose the extended-properties part. Both earn the extra reader: a shared `company` across supposedly unrelated documents means a shared template, the same class of cluster signal as a shared registered agent, and a long report carrying a few minutes of total editing time was assembled rather than written. That XML comes out of an untrusted document, so it is parsed with `defusedxml`, never the stdlib `xml.etree` — the stdlib parser expands internal entities, so a crafted `.docx` could otherwise hand chew a billion-laughs bomb. See I6.

**Tradeoff:** the allowlist (and 200-character cap) means some legitimately long metadata values are truncated, and jurisdictions/tools with dates the parser can't recognize (a shape neither the Office libraries nor the explicit PDF `D:` parser expect) silently drop that field rather than guessing — accepted because a dropped field is safe and a fabricated one is not.

### D111 — Document requests are a typed object distinct from a lead, moved out of scratchpad, resolved manually, never re-fed

Ingest already told the journalist "get the hearing transcript this order cites" — but only as prose buried in `scratchpad`/the briefing's leads, indistinguishable from an open-ended investigative thread and impossible to check off. A document request is a different kind of object: a concrete, known-to-exist artifact to acquire (a type, the specific thing, why it matters, and often where to get it), not a thread to investigate — the same distinction a reporter's own to-get list draws from their to-chase list. Added `document_requests` to `EXTRACTION`/`SECTION` (optional, omitted when a document names nothing obtainable — no padding, matching `key_facts`' discipline) and the extraction prompt now explicitly forbids listing documents-to-request in `scratchpad`/`observations`, so the content moves rather than duplicates. `pipeline/requests.py` follows §I1: the model authors `type`/`what`/`why_it_matters`/`likely_source`; Python stamps the id (`request:<sha7>:<hash of the normalized what>`, `resolutions.request_id`) and provenance into `.watchdog/Registry/requests.json`, inside `write_vault`'s registry lock, deduped by rid so a repair retry converges. `write_requests` renders the still-open entries to vault-root `requests.md`, grouped by type, with the same `<!--wid:...-->` checkbox convention as leads/alerts; `resolutions.sync_from_briefings` now reads it alongside the briefing files.

Resolution is deliberately manual only — a ticked checkbox or `watchdog resolve <id>` — with no fuzzy matching that could auto-close a request because a similarly-worded document arrived. A false-positive auto-close would silently drop a real to-get item with no trace, worse than the status quo of an occasionally-stale list. And once recorded, a request never re-enters any later model prompt (the briefing bundle, pre-flight digests) — it is a terminal, deterministic artifact like a lead or an alert, not context the model needs to reconstruct. The briefing does get one purely deterministic pointer — a `## Document requests` line counting this run's new open requests — computed from the ledger after write_vault has already run, never from a model call.

**Tradeoff:** a request that turns out to be a duplicate of prior wording under materially different phrasing won't auto-merge (content-keyed hashing, not semantic matching) — it lands as a second entry the journalist resolves separately. Accepted for the same reason fuzzy auto-close was rejected: a wrong merge is worse than an occasional duplicate entry.

### D112 — Figure-grounding advisory in post-flight is a warning, not a gate

Tributary's validation review surfaced a failure class quote verification doesn't catch: a computed sum presented as if it were extracted verbatim — "$430,000 across two transfers" when the source pages actually state $250,000 and $180,000 separately (#363). `figure_verify.verify_figures` runs in post-flight alongside `quote_verify.verify_quotes`: it extracts the numeric tokens from every stated (`basis` absent or `"stated"`) `key_facts[].fact`, normalizes them conservatively, and checks each against the cited page's text and its immediate neighbors (the same ±1 page window quote verification already uses for OCR/page-marker drift). A fact with `basis: "inferred"` is a declared derivation and is exempt outright.

Advisory, not a gate — same posture as the D32 coverage warning and D75 quote verification. A blocking gate would misfire on legitimate paraphrase: "about $1.2-million" for a page that says "$1,200,000" is a reasonable summary, not an invented figure, and a hard block would either reject good extractions or pressure the model to stop paraphrasing altogether. The companion fix on the prompt side (`extract_instructions.md`'s Basis paragraph) asks the model to name a derived figure's components in the fact text, so the check has something to verify against instead of the sum alone.

**Tradeoff:** normalization is deliberately conservative — no unit conversion, no arithmetic. A unit-reshaped paraphrase ("$1.2-million" vs "1,200,000") false-misses and gets flagged even though it's a legitimate rendering; accepted, because the warning is advisory and the journalist is meant to glance at the source anyway. Conversely, a small bare number ("5" as a docket or page reference) can coincidentally collide with something already on the page and false-match; accepted, because the check exists to catch invented or garbled figures, not to certify that every number is correct.

### D113 — `procurement-records` merged into `government-contracts`; skills may not instruct external lookups (issue #68)

Two routing/authoring rules from the domain-skill review. (1) The pre-award (`government-contracts`) / post-award (`procurement-records`) split was a distinction the documents themselves don't respect — both files claimed standing offers, amendments, and sole-source justifications, so the classifier coin-flipped on exactly the ambiguous cases. One `government-contracts` skill now covers the full procurement lifecycle; a future re-split should cut along a boundary documents actually present (e.g. by jurisdictionally distinct instrument types), not by procurement phase. (2) Extraction runs as a single completion with no tool or network access, but several skills said "cross-reference X" as if the extractor could. The rule now lives once in `extract_instructions.md`: any check/search/verify guidance in a skill means *record a lead in scratchpad/observations*, never attempt or claim the lookup. Skill authors keep writing natural investigator guidance; the prompt reinterprets it. (3) The same hoisting applies to the per-skill boilerplate: the "apply this knowledge" sentence and the non-exhaustive-fields blurb were extractor behaviour repeated in all 35 files, and now live once in `extract_instructions.md` ("treat the skill's field list as a floor, not a ceiling"). Skills carry only their scope sentence — which is genuinely per-skill: it holds the trigger list, the routing exclusions, and the descriptor fallback for user skills without frontmatter — plus domain content.

**Tradeoff:** the merged skill is ~30% longer than either half, paid on every contracting document; accepted because the halves shared most of their content anyway. Hoisting the fields blurb trades instruction-adjacency (a note sitting directly above the table it governs) for a single source of truth that also covers user-authored skills. Doc-type lists in sibling skills (court-documents/bankruptcy, land-registries/real-estate, the three finance skills) were deduped with cross-references instead of merges — those splits reflect real document boundaries.

### D114 — Universal red flags hoisted to `extract_instructions.md`; skill red flags must be extractor-actionable

The classifier loads exactly one skill, so `general-records`'s universal red flags — document integrity, what's missing, backdating and timeline anomalies, self-reported-vs-verified — only ever reached the no-match fallback. Every document that matched a specific skill missed them, though they apply to any record. They now live once in the always-loaded `extract_instructions.md`, so every extraction gets them beneath whatever type-specific flags the matched skill adds; `general-records` keeps only its orient-yourself framing and points to the standing set. This completes D113's "behaviour lives once in `extract_instructions.md`" hoist. The same pass codifies a red-flag *authoring* rule (in `CLAUDE.md` and `_template.md`): the extractor is the only reader of a skill's red-flags section — one pass over a single document plus the entity digest, no web, no prior knowledge — so each flag must reduce to capturing a stated pattern, comparing the digest where both sides are stated, or logging a lead. Proven-negative flags ("undisclosed", "not filed", "failed to") ask the model to know a fact and confirm its absence; they were reframed across the skills to lead with the extractable pattern and route the absence to a lead, with the deeper human-facing context moved to *What investigators typically miss*.

**Tradeoff:** the universal block is paid on every extraction prompt (a few hundred tokens) even when the matched skill is already rich; accepted because the patterns are genuinely universal and the alternative is either restating them in 34 skills or leaving matched documents blind to them. `general-records` loses its most concrete section to a pointer, which slightly weakens it as a standalone reference read outside the pipeline — acceptable because in the pipeline it always ships alongside the standing instructions.

### D115 — `land-registries` merged into `real-estate`

Revises the D113 footnote that kept this pair split with cross-references. On closer read the registry-system / market-transaction boundary fails the same test that sank the procurement split: the classifier loads exactly one skill per document, and most property documents straddle the line — a parcel register extract is a list of transfers, mortgages, and liens; a deed of sale is itself a registered instrument. The remaining deduped pairs (court-documents/bankruptcy, the finance skills) still pass that test.

**Tradeoff:** the merged skill is longer than either half (~230 lines vs. ~165/~135), paid on every property document; accepted because the halves shared most of their content, and a misrouted document under the split lost half the relevant guidance entirely. Extractions in existing vaults stamped `record_skill: land-registries` now reference a retired name — provenance metadata only, nothing loads it at read time.

### D116 — Catalog-wide overlap pass: every document type has exactly one owning skill

A full pass over the 34 skills removed every double-claimed document type, since the classifier loads exactly one skill and a coin-flip costs the losing file's guidance. The consequential call: annual and quarterly packages built around financial statements (10-K, 10-Q, annual reports, statements+MD&A) route to `financial-statements` — which carries the accounting red flags and already has an annual-report section — while `regulatory-filings` keeps event-driven and ownership paper (insider reports, material change/8-K, early warning/13D, proxies, prospectuses, AIFs, technical reports). Routing statement-centred filings to `regulatory-filings` would have stripped financial scrutiny from exactly the documents that carry the numbers. The same pass returned municipal procurement, municipal AG reports, ombudsman reports, assessments, and lobbyist registrations from `municipal-records` to their owning skills; official verbatim proceedings from `audio-video` to the transcript/court skills; and settled smaller claims (EA panels → `environmental-filings`, university statements → `financial-statements`, vehicle liens → `vehicle-registrations`, CPL court copy vs. registered copy). `professional-licensing`/`healthcare-licensing` stay split despite duplicated content: the regulator's name routes unambiguously, so the duplication costs maintenance, never extractions.

**Tradeoff:** single ownership means a document sitting near a boundary gets one lens only — a 10-K's insider-timing context, a municipal contract's council-politics context — accepted because the alternative (both skills claiming it) doesn't load both either; it flips a coin. Boundaries are stated as routing exclusions in both siblings' descriptions so the classifier sees the cut, not just the maintainer.

### D117 — Picking a model interactively prompts for that provider's key on the spot

`watchdog configure extractor_model` (and the setup wizard's model pickers) now ask for the chosen provider's API key immediately, if none is stored or in the environment. Before, routing a stage to, say, `gemini:gemini-2.5-flash` with no Gemini key succeeded and wrote the config, and the failure only surfaced on the next `watchdog ingest` — far from the action that caused it, with nothing in the config to suggest what was wrong. A journalist reading "extractor_model: gemini:gemini-2.5-flash" has no reason to suspect the missing piece is a credential. Keeping "pick a model" and "be able to run it" in one step is worth a prompt appearing in a command that otherwise only writes config.

Only the *interactive* picker prompts. `watchdog configure <key> <value>` stays silent and scriptable — a non-interactive command must not block on stdin.

**Tradeoff:** `configure` now has a side effect beyond writing config (it can write `credentials.json`), which is surprising if you read the command name literally; accepted because the alternative is a stage that is configured but unrunnable, and the prompt is skippable with an empty answer.

### D118 — Extraction is stateless; entity resolution and contradiction detection move to a finalizer reconciliation pass (issue #381)

Extraction used to read vault state: pre-flight snapshotted the entity registry at the moment each document's own extraction began and passed it into the prompt as `EXISTING_ENTITIES` / `EXISTING_TIMELINE`, and the extractor did three jobs against it — name what the document mentions, resolve those against existing entities (emitting `match_id`), and flag contradictions. Two of the three were structurally undoable there. With `DEFAULT_CONCURRENCY = 5`, the first wave of documents each snapshot before any of the others has written an entity, so they cannot see each other at all; and even at `--concurrency 1`, document *N* is only ever compared against 1…*N−1*, never backward — so the same corpus in a different order produces a different answer, and no cross-document contradiction among a fresh vault's first wave is detectable by any model. The distinction that fixes it: extraction needs only the *document* (it is the sole stage that reads it); resolution and contradiction detection need the *whole entity set* (only the finalizer sees that).

So pre-flight no longer reads entity state (only `known_document_types`, which is order-insensitive by nature), the extraction schema drops `match_id` and per-entity `contradictions`, and `pipeline/reconcile.py` runs once in `_post_ingest`, before synthesis, doing both jobs over every entity at once. Entity resolution is split: `write_vault._reconcile_entity_ids` already folds *exact* normalized-name duplicates in-lock at write time (untouched, concurrency-immune), and reconcile handles the *token-variant* judgement calls `normalize_entity_name` deliberately won't auto-merge ("Laurentian University" vs "…of Sudbury") — Python blocks candidate pairs (same canonical type, token subset or Jaccard overlap ≥ 0.5, one side touched this run, capped at 200) and the model only confirms each by index. Contradictions are detected over each recurring entity's `## Analysis` claim ledger (already source-attributed by document) and written through the existing `contradiction.run` writer (D81) — so a model naming a nonexistent document or a stale id yields a skipped item and a warning, never a bad note. I1 holds: the model answers only *which*; every write is deterministic code. This also removes the extraction prompt's largest and fastest-growing volatile block — every page of every document carried the vault's accumulated entity context — turning a roughly O(n²) per-page token cost into one O(n) finalizer call.

**Tradeoff:** the finalizer default is now load-bearing — it defaults to haiku (`_INGEST_STAGES`), and reconciliation is the two hardest inferences in the pipeline running on the cheapest model. That default is deliberately left for the #361/#215 benchmark to decide rather than swapped on instinct (the finalizer is ~3 calls per ingest and does not scale with corpus size, so spending up there is nearly free — but the number should come from data). Blocking can also miss a duplicate whose names share no tokens (an acronym vs its expansion with no overlap); that is a strict improvement over the old `match_id`, which caught it only when the two happened to land in the right order, and the manual `merge-entities` command remains the human override. `known_document_types` is a residual order-dependency in the extraction prompt, but it steers only document-type naming, not entities or facts, and is intentionally kept for vocabulary consistency (D-log rationale in `extract_instructions.md`).

### D119 — `.watchdog/Registry/` lowercased to `.watchdog/registry/` (issue #385)

The registry folder was the one capitalized name under `.watchdog/`, inconsistent with every sibling — `queue/`, `staging/`, `timeline/`, `tmp/`, `backups/` are all lowercase. Fixed by changing the literal path segment everywhere it's hardcoded: the ~30 Python files under `cmd/` and `pipeline/`, the markdown skill files that read registry paths directly (no code-level fallback for those), the vault's own `templates/vault/CLAUDE.md`, and the docs.

**Tradeoff:** pre-production, so no migration — unlike this project's other no-migration changes, which degrade softly (stale data until the next write), a bare rename here breaks a vault outright until fixed, since nothing resolves under the old path, including the skills that read it with no fallback. Accepted anyway: existing local vaults are few, and fixing one is a single `mv .watchdog/Registry .watchdog/registry`.

### D120 — A document's sidecar can pin its own record skill, overriding a run-wide `--skill`

`--skill`/`default_skill` pins one skill for the entire ingest queue (D21), so a batch spanning more than one document type needs one `chew`/`ingest` pass per skill — the corpus-v1 benchmark (#361/#215) is the case that exposed this: two skills across six documents, doubling the finalizer and briefing runs for no reason connected to what's being measured. Rather than add a per-document flag or a `--skill-map`, a document's own `.yml` sidecar can now carry a `skill:` field, read deterministically in Python (`_sidecar_skill`, mirroring `_sidecar_provenance`'s `source`/`obtained`) and resolved through the same `skills_catalog.resolve()` a `--skill` value uses. It never reaches the classifier prompt — unlike the sidecar's other fields (`notes`, `source`), which are explicitly framed to the model as data, not instruction (D84), this one is decided before the model is ever called, so there is no data/instruction line to police. A per-document pin takes priority over a run-wide one, being the more specific setting; an unresolvable value falls back to classification with a warning rather than failing the whole batch.

**Tradeoff:** `claude-batch` extraction is untouched — it already requires a run-wide pinned skill (classification isn't batchable), and a per-document sidecar pin isn't wired into the batch submission path. Extending it there would mean splitting one submission into per-skill batches, which no current use case needs.

### D121 — Chew filters a document's sidecar into the queue JSON and deletes the original; write_vault re-materializes it in morgue

Chew moves a document's source file from `_INCOMING/` into `.watchdog/staging/<sha>/`, but its `.yml` sidecar used to stay behind in `_INCOMING/`, read live off disk by filename at every later stage (`orchestrate._read_sidecar`/`_sidecar_provenance`/`_sidecar_skill`, and `write_vault`'s move-to-morgue step). That split state was itself a bug: `write_vault` derived the sidecar's expected location from the source's *current* path, which is staging once chew has run, not `_INCOMING/` — so the sidecar was never found and never moved to morgue, sitting orphaned in `_INCOMING/` indefinitely. It also meant the entire raw sidecar text — any key a hand-edited or research-authored `.yml` happened to carry — passed through unfiltered to every classify/extract prompt (D84's data-not-instruction framing was the only mitigation, no field-level check).

Fixed by making chew the single place a sidecar is ever read off disk. It's parsed there, filtered to an allowlist (`pipeline/sidecar.py`: `source`, `obtained`, `notes`, `skill`, plus the fields `pipeline/research.py` writes — `retrieved_by`, `source_type`, `title`, `relevance`, `archived`, `capture`), each value capped at 2000 characters, and the clean result embedded as the queue JSON's `sidecar` field; the original `.yml` is deleted (dropped keys are logged, not silently lost). `preflight.run` forwards that field; `orchestrate.py`'s sidecar readers become pure text-parsing functions over `pf["sidecar"]`, and `_stamp_document` carries the same text onto `doc["sidecar"]` so `write_vault` can write it back out as a `.yml` in morgue — a write, not a move, so there is never a loose sidecar file to lose track of in between. On a chew failure or empty-text skip, the sidecar still moves alongside the source into `_INCOMING/_FAILED/`/`_INCOMING/_SKIPPED/` unfiltered, since chew never consumed it in those cases. `research.seen_urls()` gains a second scan (`.watchdog/queue/*.json`'s embedded `sidecar`) for the chewed-but-not-yet-ingested state, since that state now has no `.yml` file on disk at all.

**Tradeoff:** a sidecar edited in `_INCOMING/` after `chew` has already run (but before `ingest`) is no longer picked up — the sidecar is frozen into the queue JSON at chew time, same as the document's OCR'd text already is. Accepted as the more consistent behavior (provenance shouldn't get a live-edit escape hatch page text doesn't); re-chewing picks up an edit the same way it already does for a source-file change.

### D122 — OpenAI-compatible backends (OpenAI/DeepSeek/Gemini) verify TLS via the OS trust store, not certifi's bundled list

The `httpx.AsyncClient` in `_openai_compatible_call` verified against `certifi`'s bundled CA list (httpx's default), which is deliberately independent of the operating system's own trust store. On a machine running a TLS-inspecting corporate proxy, that proxy terminates the real TLS connection and re-signs traffic with its own root CA — a CA the OS trusts (IT provisions it into the keychain via MDM) but certifi has never heard of, so every DeepSeek/OpenAI/Gemini call failed with `CERTIFICATE_VERIFY_FAILED` even though the browser and every other native app on the same machine worked fine. The Claude backends were unaffected (the `anthropic` SDK and `claude-agent-sdk` don't share this httpx client).

Fixed by verifying through the `truststore` package (`truststore.SSLContext`, passed as `verify=` on the client) instead of certifi. `truststore` delegates certificate verification to the OS's native APIs (Security framework on macOS, CryptoAPI on Windows, OpenSSL's default verify paths on Linux) — the same trust root the browser already relies on — so a corporate proxy's CA is picked up automatically and continues to work through any future CA rotation, with no exported `.pem` file to track or expire.

**Tradeoff:** this widens the trust root for these three backends from certifi's curated public-CA list to "whatever this machine's OS trusts," which is a strictly broader set on a device running enterprise MDM/proxy software. Accepted because it matches the trust model every other application on the machine already operates under, and the alternative (manually exporting and maintaining a proxy's root CA in a custom bundle) is brittle — it breaks silently on the proxy's next CA rotation.

### D123 — Tier 0: a deterministic + local-NER candidate harvest feeds a checklist into extraction (issue #361)

Benchmark hand-scoring of extraction misses (#361) found a consistent failure class: "buried" facts — a single sentence after a table, a table row, a one-line disclosure — missed even by strong models, and missed most of the time by cheap ones. Nearly every miss was anchored by something a deterministic pass or a small local model can find without an LLM at all: a money figure, a bare table figure, a percentage, a date, or a court file number. Rather than lean harder on the extractor's exhaustive-reading instructions, `pipeline/harvest.py` now harvests those spans directly from the chewed text — regex for money/figure/percent/date/docket, and the optional local GLiNER model for person/organization/location — and `format_checklist` renders them into a compact per-page list injected into the extraction prompt as a volatile block. The framing matters: the model isn't asked to notice a number on page 52, it's handed the number and asked whether it's material, which converts a recall problem into a verification problem.

**Tradeoff:** every extraction call now carries extra input tokens for the checklist, and GLiNER is a heavyweight optional dependency (`pip install gliner`) most users won't have without an explicit `pipx inject`. Both are bounded deliberately: candidates are deduped, capped at 3 page-occurrences each (recurring headers/footers), and capped at 80 per page by kind priority (money > docket > date > percent > figure > person > organization > location) — no global cap, since a large document should get proportionally more checklist, but no single page should dominate the prompt. GLiNER's absence degrades silently to the deterministic-only checklist rather than failing ingest, so the feature is free to adopt incrementally. The GLiNER model download also verifies TLS through the OS trust store via `truststore`, per D122, for the same corporate-proxy reason.

### D124 — Unknown JSON keys are pruned and logged rather than failing schema validation (#412)

Benchmarking (#412) found extraction calls that returned every required field correctly but with one stray extra property (e.g. a `date` on a role object that belongs on `date_range` instead) failing `_validate` outright — costing a full-document retry and, in Haiku's First Report case, aborting the document entirely. The extra key was never the problem the retry was trying to fix; a structurally sound extraction was being thrown away over one harmless property. `model_client._prune_unknown` now walks the parsed JSON alongside its schema before validation and removes any property not declared in `properties`, but only inside a schema object that itself declares `"additionalProperties": False` — a free-form object like `file_metadata` (plain `{"type": "object"}`, no such declaration) is left untouched, so this only tightens the contracts the pipeline already enforces strictly. Removed paths are reported on `ModelResult.pruned` and, when a vault is in scope, logged to `ingest.log` as a WARN line (`orchestrate._call_model`) and carried onto the run's usage record, so systematic schema drift stays visible instead of silently disappearing.

**Tradeoff:** strictness is unchanged for what actually matters — a missing required field or a wrong-typed value still fails validation and retries exactly as before. But a misplaced value (the role-date example above) is dropped rather than salvaged into the field it was probably meant for; recovering it would mean guessing the model's intent, which is a worse failure mode than losing one field on an otherwise-good extraction.

### D125 — Failed model calls are recorded in usage telemetry, flagged `failed: true`

`_record_usage` only ever ran when `acomplete_json` returned, and a retried success kept only the last attempt's usage — so a document that failed extraction after two costly attempts, or a call whose first attempt burned tokens before a retry succeeded, both under-reported (or entirely hid) real spend. On subscription auth this was material: one benchmark run (#412) burned an estimated $1.5–2 invisibly, and `watchdog usage` couldn't be trusted for session-window budgeting. Fixed on both ends: `acomplete_json`'s retry loop now merges usage across every attempt with the existing `_merge_usage` helper, so a successful `ModelResult.usage` is the aggregate over the whole call, not just the winning attempt; and `ModelError` gained optional `usage`/`cost_usd`/`attempts`/`model`/`backend`/`auth_mode` fields, populated on the two paths where an attempt actually reached the model (JSON-validation failure, truncation) — never on a backend/transport exception, which raises before any usage exists. `orchestrate._call_model` catches a `ModelError` carrying usage, records it via `_record_usage(..., failed=True)`, then re-raises unchanged; `watchdog usage` marks a `failed` row with a distinct `✗ failed` marker, and its tokens/cost count toward the normal subtotals since the record is otherwise ordinary.

**Tradeoff:** none of this changes what fails — a document that couldn't extract still fails exactly as before; it only makes the cost of that failure visible instead of silent.

### D126 — Extraction stages to a durable, sha-keyed artifact; a serial commit pass replays write_vault at finalize-start (#403 phase 1)

Post-flight used to call `write_vault.run()` inline, so the vault populated progressively, one document at a time, as extraction completed. That coupled two things that don't need to be coupled: paying for extraction, and writing it to the vault. #384/#398/#399 all traced back to it — extraction's output couldn't be held fixed and re-finalized, and the fragment queue/registry writes made the vault a moving target mid-batch. Phase 1 (of #403's five-phase design) splits the two: `postflight.run` now validates/sanitizes/explodes as before, then writes the result to `.watchdog/extracted/<sha>.json` instead of calling `write_vault.run()`. A new commit pass at the top of `orchestrate.finalize` (`_commit_pending`) finds every such artifact not yet a key in `registry/documents.json` and replays the *unmodified* `write_vault.run()` over each one, in sorted sha order, before any post-ingest model call.

The cache key is the sha alone, deliberately — not sha+model+effort+skill. Re-extracting a document under different settings needs an explicit `--force` (#424, not built here): normal use never wants a second extraction of the same bytes, and a bare sha check is the simplest thing that could work for that case. The corresponding read got a name split to match: `preflight.run`'s pre-existing `already_extracted` keeps its pre-existing meaning (committed to the registry) and a new `already_staged` (the artifact exists) answers a different question — has this document been extracted at all, regardless of commit state — checked *before* spending a classify/extract call. The queue file's deletion moved from "right after extraction" to "right after commit," since `write_vault._write_morgue_markdown` and the corpus indexer both still read it, and now do so later.

**Determinism fell out for free.** Ingest was not reproducible before this: concurrent extraction meant whichever document finished first wrote first, so `appears_in` ordering in the registry and fragment order in an entity note varied between two otherwise-identical runs. The golden-vault parity test that guards this refactor (`tests/test_golden_vault.py`) originally had to pin `concurrency=1` to make its fixture comparable at all. Because the commit pass is serial and sorted by sha, that nondeterminism is gone — extraction can still race, but the write that used to leak completion order into observable output no longer happens at extraction time. Verified by running the golden test dozens of times at default concurrency with no flake; the pin was then removed from the fixture.

**Tradeoff:** the vault now populates at the commit pass rather than progressively during extraction — a long `watchdog ingest` no longer shows notes appearing one by one in Obsidian as it runs, only once commit starts near the end. Storage cost of the durable artifact is negligible (tens of KB per document) against the benefit: extraction is now a durable, reusable, re-finalizable artifact, and `watchdog ingest --no-finalize` needs no vault copy to compare finalizer models against a fixed extraction (#384) — pre-commit, the vault is untouched by construction, not by convention.

### D127 — Batch-wide exact-name entity fold moves ahead of the commit pass (#403 phase 2)

Before phase 1, `write_vault._reconcile_entity_ids` folded exact normalized-name duplicates per document, in-lock, against a fresh read of the *live* registry — the one place a document saw entities that concurrent workers earlier in the same batch had already written (e.g. `ernst-and-young-inc` vs `ernst-young-inc`, coined from a pre-flight snapshot taken before either committed). Making commit a separate serial pass (D126) removed that per-document live-registry visibility, so the fold had to be re-established somewhere. Phase 2 does it deterministically up front: `orchestrate._batch_exact_fold` walks the pending shas in sorted order over an in-memory copy of the registry, reconciling each staged document's entities against it with the same `_reconcile_entity_ids` and folding them in with the same `_new_entity`/`_merge_entity` the real commit uses, then rewrites the folded ids (and alias/role-target remaps) back into each `.watchdog/extracted/<sha>.json`. The commit pass that follows replays already-folded entities, so a later document matches an earlier one exactly as it did under the old per-document call.

**Tradeoff:** the fold now runs twice-removed from the write — once over a throwaway registry copy here, then again for real at commit — rather than inline with the write itself. The copy is cheap, and the payoff is that the result is a function of sorted sha order, not of which document happened to extract first, which the per-document version never was.

### D128 — Entity-merge reconciliation runs before the commit pass; a reconcile failure defers the whole batch (#403 phase 3)

Reconciliation has two halves — entity-duplicate **merges** and cross-document **contradictions** — and phase 3 splits them by *when* each can run. The merge half moves *before* the commit pass, so `orchestrate.finalize`'s order becomes `_batch_exact_fold → _reconcile_pre_commit → _commit_pending → _post_ingest`. Reconciling over the staged batch (∪ the registry) before anything commits means a same-batch duplicate is folded while it is still just staged JSON — a cheap staged-id rewrite — instead of the post-commit note surgery it used to require. `reconcile.build_bundle(vault, shas)` reconstructs the reconcile input from the staged batch and the registry (a working copy built with the real `_new_entity`/`_merge_entity`), no longer from written notes or the retired fragment queue.

The **merge taxonomy** in `reconcile.apply_merges` turns on which sides are already committed: (a) the loser was never committed (batch-only) → rewrite its id in the staged JSON, with no surgery, stub, or backup; (b) both sides are already committed → the full `merge_entities.run` surgery, as before; (c) exactly one side is committed → the committed side always survives, its id and name winning. Two product decisions are locked here and should not be re-litigated: (1) a batch-vs-existing merge always keeps the already-committed entity, folding the new one onto it with the new name preserved as an alias; (2) a purely in-batch merge produces **no** redirect stub, backup, or "Merged from" provenance — the duplicate is folded before it ever exists as committed state, and findability is preserved by the alias alone. **Contradiction detection stays post-commit** (in `_post_ingest`, applied from the same `rec_result`), because `contradiction.run` validates both document slugs against `registry/documents.json`, which only holds this batch's documents once they are committed.

**Tradeoff / recovery semantics:** because reconciliation now precedes commit, a reconcile model failure (e.g. a rate limit) **defers the whole batch** — nothing commits, every staged artifact stays pending, and a re-run of `watchdog finalize` retries fold → reconcile → commit from scratch. This is deliberately stricter than the old enrichment-only posture: committing half-reconciled state would strand duplicates a later retry could never revisit, so the batch is kept atomic. `finalize` signals the early return with a `commit_skipped` flag, and `cmd/ingest.py` uses it to print "nothing written yet — re-run `watchdog finalize`" rather than the post-commit "documents are saved." Retired along the way: `reconcile._fold_fragments`, `_touched_ids`, and the `reconcile.apply()` composite.

### D129 — Entity synthesis reads the staged extraction corpus; the `entity-fragments/` mechanism is retired (#403 phase 4)

Entity synthesis needs a per-entity digest of each document's claims. `write_vault` used to build that as a side effect of every note write — a per-entity file under `.watchdog/tmp/entity-fragments/<id>.md` plus a `_queue.json` of touched entities — which `synthesis_bundle.build_bundle` then read. Once phase 3 stopped reconciliation reading those files, synthesis was their last consumer. Phase 4 points `build_bundle(vault, shas)` at the staged extractions directly: for the batch's shas it reads each `.watchdog/extracted/<sha>.json`, rebuilds the same per-entity fragment block on demand, and gates on the registry's `appears_in ≥ 2` exactly as before. The whole `entity-fragments/` mechanism — `_record_entity_fragment`, `_fragments_dir`, `_drop_fragment_block`, the fragment queue — is removed from `write_vault`, along with the mid-write-crash idempotence bookkeeping (D67) that only the fragment blocks needed; the note's own `## Analysis` block keeps its own replace-by-document idempotence.

The batch scope is the current run's `result_*.json` set (via the `results` list `_post_ingest` already holds), **not** `_pending_commits`. This matters on a resume: if a run commits but synthesis then rate-limits, the documents are already in the registry (so `_pending_commits` is empty) yet their `result_*.json` persist, and a re-run must still re-synthesize that batch. `has_pending_finalization`/`pending_finalization` were likewise repointed off the retired queue onto the result set + staged extractions.

**Tradeoff:** `build_bundle` re-renders the fragment blocks each finalize instead of reading a pre-accumulated file — negligible, since the staged JSON is already on disk and parsed cheaply, and it deletes a whole category of write-time bookkeeping. Observable vault output is unchanged (`tests/test_golden_vault.py`, green with no regeneration). `tests/test_golden_merge.py` was regenerated once, and only because its fixture began writing the `result_*.json` a real extraction always leaves — which moved that fixture's briefing/log document count from 0 to 2 (the merge write-surface itself stayed byte-identical, and the fixture now actually exercises the synthesis pass for the first time). A caution the golden tests exposed: they mock synthesis to return nothing, so they do not guard `build_bundle`'s selection — that logic is covered by dedicated, mutation-checked unit tests instead.

### D130 — `extract`/`finalize` are first-class pipeline-stage commands; `ingest --no-finalize` is removed (issue #425)

Phases 1–5 of #403 (D126–D129) made extraction a durable, idempotent stage separable from finalize, but the only way to reach that seam from the CLI was the awkward `watchdog ingest --no-finalize`, with `watchdog finalize` as its natural counterpart already a first-class command. `watchdog extract` now exposes the same seam directly: `cmd_extract` is a thin wrapper that forces `no_finalize` on `args` and delegates to `cmd_ingest`, inheriting the cost estimate, skill pinning, `--wait`, lock handling, and the "run `watchdog finalize` next" summary for free. Its parser only carries extraction-side flags (`--extractor-model`, `--extractor-effort`, `--classifier-model`, `--concurrency`, `--classify-pages`, `--skill`, `--wait`, `--estimate`) — no `--finalizer-model`/`--finalizer-effort`, which belong to `finalize`. Bare `watchdog` (`cmd_guided`) is unchanged: it still walks context → chew → ingest as one combo, not as separate extract/finalize atoms — the guided path and the manual-control commands are deliberately different surfaces over the same pipeline.

Because the app is pre-1.0, `ingest --no-finalize` was removed outright rather than kept as a deprecated alias — `watchdog extract` fully replaces it and there is no installed base to carry forward compatibility for. The internal `no_finalize` plumbing in `cmd_ingest`/`orchestrate.run(skip_finalize=...)` is unchanged; only the flag that used to set it from the CLI is gone.

**Tradeoff:** anyone with `ingest --no-finalize` in a script or muscle memory gets an argparse error instead of a working (if discouraged) flag — acceptable pre-1.0, where breaking the CLI surface to keep it honest costs nothing an install base would otherwise pay for.

### D131 — `--force` re-ingests fully, re-queueing from the morgue, gated by an overwrite confirm between extract and finalize (issue #424)

D126 made the sha alone the cache key, deliberately leaving "re-extract under a different model/effort/skill" to a future `--force`. That flag's only sensible meaning, per the repo owner, is a full re-ingest: a `--force` that refreshes the staged JSON but leaves an already-committed vault note stale would be a bug, not a feature — the whole reason to re-force a document is to end up with a new generated note. So `--force` bypasses both `already_staged` and `already_extracted` in `orchestrate._extract_document`/`_finish_batch_item`/`_submit_batch`, and `orchestrate.finalize` gained `force_shas`: shas `_pending_commits` includes in the commit-pass set even though they are already registry keys, so `_commit_extracted` replays `write_vault.run` over them again.

That replay is safe because it was already exercised, just never deliberately: `write_vault.run` merges into an existing registry entity (`_merge_entity`) and replaces (not appends) the document's own `## Analysis` contribution via `_drop_analysis_entry`, keyed by the doc-note link — the same idempotent-repair-retry path a crash-and-resume ingest always relied on (D126's docstring). Re-running it for a `--force` document is that same path, deliberately invoked instead of accidentally.

**Getting an already-committed document back into the queue.** A first pass at this flag assumed a committed document's original survives at `.watchdog/staging/<sha>/` — it doesn't: `write_vault.run`'s commit step moves it out of staging into the morgue and prunes the now-empty staging directory (`shutil.move`, then `rmdir`). The durable, sha-stable location of a committed document's original is `registry/documents.json[sha]["morgue_path"]`. So `watchdog ingest --force <document>` (a sha256, an unambiguous sha256 prefix, or a filename, resolved against `registry/documents.json` by `cmd/ingest._resolve_force_selectors`) re-chews that morgue file — reusing the real chew/OCR pipeline (`preprocess_batch.run_ingest`), not a duplicate of it — with two things bypassed for that sha alone: `_filter_already_seen`'s dedup check (being "already ingested" is the entire point of re-chewing it) and the near-duplicate MinHash comparison (which would otherwise always match the document against its own still-registered self at ~1.0 similarity). The re-chew moves the file from morgue into `staging/<sha>/`, same as any freshly-chewed document; the eventual recommit moves it back to the morgue, same as any commit. A selector matching no committed document is a clear error, never a silent no-op.

The two stages split by destructiveness: `watchdog extract --force` stays a bare flag, no document names — re-extracting and stopping, nothing committed touched, so no confirmation, and deliberately no selector-driven re-queue either (a re-queued-then-extracted document would sit staged with no `watchdog finalize` able to recommit it, since a plain finalize's `_pending_commits` excludes already-registered shas without `force_shas` — a footgun this flag avoids by construction). `watchdog ingest --force [document …]` re-queues any named documents from the morgue, extracts with finalize held off (reusing `extract`'s own skip-finalize path), then, only when some force-re-extracted document is already in `registry/documents.json`, lists the vault notes about to be replaced and confirms via `interactive.confirm`, defaulting to **Cancel** — genuinely destructive (replacing existing work), unlike the routine ingest confirm which defaults to proceeding. Cancelling leaves the re-staged extraction pending for a later plain `watchdog finalize`, with nothing rolled back.

**Tradeoff:** the gate only fires when the forced batch actually overwrites something, so a `--force` run over brand-new documents (or a `--force` typo with nothing cached) finalizes with no extra prompt — correct, but means the flag's cost (a full re-extraction spend on every queued document, cache or no) is visible only in the cost estimate and the extraction-phase "re-extracting (--force)" notice, not in the gate itself. The `--force` argparse value went from a plain `store_true` to `nargs="*"` on `ingest` (absent → `None`, bare → `[]`, named → the list) to carry the selector without a second flag; `extract` was left as `store_true` for the reason above.

`--estimate` stays read-only even with named documents: `cmd_ingest` skips `_requeue_forced_selectors` entirely when `--estimate` is set (printing a one-line note instead of silently ignoring the names), since re-chewing is a real mutation — it moves the morgue original into staging and writes a queue entry — and `--estimate`'s whole contract is no lock, no confirm, no extraction.

### D132 — Usage telemetry is persisted per call, not just at end-of-run (issue #407)

`_write_usage` only ever ran once, at the very end of `orchestrate.run`/standalone `finalize` — so a clean Ctrl+C during extraction (which stops the batch but still lets `run` reach its tail) kept that run's telemetry, but a hard interrupt, a crash, or an abort during finalize's reconciliation/synthesis/briefing calls never reached that line and lost the whole run's cost data, invisibly. A single end-of-run write can't survive an abort by construction — the fix is to stop treating the in-memory `_usage` list as the only copy.

`_record_usage` now appends each record as one JSON line to a run-scoped `usage-<ts>.partial.jsonl` the moment it's added to `_usage`, via a new module-level `_usage_partial_path` set alongside `_usage` itself. `_begin_usage_run`/`_end_usage_run` replace the bare `_usage = []` / `_write_usage(...)` pairs at every top-level entry point (`run()`, both extraction branches, and standalone `finalize()`): `_begin_usage_run` first folds any `*.partial.jsonl` orphaned by a run that never reached its own `_end_usage_run` into a real `usage-<ts>.json` (keyed by the partial's own timestamp, so it sorts where that run actually happened), then opens this run's own partial; `_end_usage_run` writes the canonical file as before and deletes the now-redundant partial. Consolidation happens once, at the start of the *next* run — nothing runs while a process is actually mid-crash — which is sufficient because the queue file for an aborted document isn't deleted until commit (D126), so a follow-up `watchdog ingest` or `watchdog finalize` is exactly what a user does next anyway.

**Tradeoff:** every recorded call now costs one small synchronous file append in addition to the in-memory list append — negligible against a model call's own latency, and it only runs on the same event-loop turn as `_record_usage` (no `await` in between), so it can't interleave with a concurrent extraction's own appends. The canonical `usage-<ts>.json` format is unchanged; the partial's own path never enters `usage_files()`/`watchdog usage`, so nothing surfaces a `.partial.jsonl` until it's been folded into a real file.

### D133 — A standing public-records warning replaces the generic ingest confirm, defaulting to Acknowledge (issue #426)

Before this, the only prompt at the point where extracted text actually leaves the machine was a generic "Ingest now? / Not now" — the README's "Public records only" warning existed, but nothing in the terminal flow repeated it at the moment it mattered. `_confirm_public_records(n_docs, *, skip_warning=False)` in `cmd/ingest.py` now gates both paths that trigger extraction — `_offer_ingest` (guided walk, after chew) and the `if confirm:` gate in `cmd_ingest` (direct `watchdog ingest`/`watchdog extract`, since `cmd_extract` delegates to `cmd_ingest`) — printing the full warning (wording tracked from README.md's `## Public records only` section) plus the queued document count, then an Acknowledge/Cancel pick. It replaces the old pick outright rather than stacking a second prompt; `_offer_ingest` calls `cmd_ingest(..., confirm=False)` same as before, so the guided path is gated exactly once.

**Acknowledge, not Cancel, is the default.** An earlier draft defaulted to Cancel; the repo owner reversed that deliberately — a safe default just trains people to reflexively select past it, the same way "Terms and Conditions" scroll-and-click habituates. The actual safeguard is the warning being shown in full, every time (not a one-time per-vault acknowledgement — the risk is per-document), plus requiring a real keypress past it, not which option is pre-selected. This is the opposite tradeoff from D131's `--force` overwrite gate, which defaults to Cancel deliberately because *that* prompt guards against irreversibly replacing already-committed work — a different risk shape (an accidental repeat action) than this one (routine, expected, every-run friction).

`--skip-warning` is a per-invocation flag on both `ingest` and `extract`, not a `watchdog configure` key — a persistent "never warn me" setting would quietly defeat the safeguard for every future run, which is exactly the failure this issue exists to prevent. It skips only the interactive pause; a one-line notice ("Sending N documents to a cloud AI model") still prints, so a scripted/`--wait` run is never silent about what it sent. `n_docs == 0` (checking on a pending `claude-batch` extraction with nothing newly queued) is a no-op — no new text is being sent this call, so there is nothing to warn about.

**Tradeoff:** every ingest now costs one extra keypress past what used to be a single Enter, even for a journalist who has already internalized the risk — accepted, since the warning is the point, and it's the standing full-text block (not the friction) that's meant to catch someone about to send the wrong file.

### D134 — `--skip-briefing` skips only the briefing model call, not the rest of finalize (issue #410)

A bulk backfill or a re-ingest after a fix often doesn't need a fresh briefing every time, but still wants entities reconciled, synthesized, and the timeline kept current — those are what later ingests and investigation sessions actually depend on. Folding this into `ingest` and `finalize` (rather than a new command) keeps with the CLI's no-near-duplicate-commands stance; a flag scoped to just the briefing call, rather than reusing `skip_finalize`/`watchdog extract`, is what lets synthesis and the timeline still run.

`skip_briefing` threads through `orchestrate.run`/`orchestrate.finalize` → `_post_ingest`, which skips step 3 (the `briefing` model call and `_write_briefing`) but leaves contradictions, synthesis, and timeline reconciliation untouched. Recorded as `out["briefing_skipped"] = True`, deliberately distinct from `briefing_error` — an intentional skip must not trip the "post-processing didn't finish, run `watchdog finalize`" path a genuine briefing failure (rate limit, output-cap truncation) does, and post-ingest inputs are cleared normally rather than left pending for a retry that was never wanted. `watchdog finalize --skip-briefing` takes the same flag directly, for completing an already-staged/interrupted batch without a briefing. The bare `watchdog` guided walk exposes it too, as a flag on the top-level CLI parser rather than `ingest`'s subparser — `cmd_guided` never builds its own `args`, it reuses the one `main()` parsed, so the flag reaches `cmd_ingest` through the same `args` Namespace `_offer_ingest` already passes through, no separate plumbing needed.

**Tradeoff:** `hot.md` and that run's `log.md` entry are only written by `_write_briefing`, so both go stale until a run without `--skip-briefing` (or a manual `watchdog finalize` once a standalone briefing-only command exists) catches them up — the leads sweep, watch-word scan, and `requests.md` are unaffected since they don't depend on the briefing.

### D135 — Tokens-in estimate calibrated from real telemetry; `watchdog finalize` gets its own `--estimate` (issue #417)

D72's dollar figure was always real — derived from this vault's own $/token history — but the tokens-in number it's multiplied against was still the flat `chars/4` heuristic from before any of that telemetry existed, with no feedback loop back to reality. Separately, `watchdog finalize` had no estimate at all, unlike `ingest`/`extract`: not an oversight so much as a genuine gap, since before #403 phase 4 (D129) the finalizer's inputs were smeared across the retired `entity-fragments/` mechanism rather than sitting in one measurable place.

Both fixes lean on the same move: carry a naive estimate alongside the real number a call already produces, so a later run can compare them. `_compact_result` now carries `est_input_tokens` — `section.est_tokens_from_pages` over the document's own pages — through to `_finish_extraction`, and `orchestrate.run` sums it across a run's successfully extracted documents onto that run's `usage-<ts>.json` totals, next to the real `input_tokens` the model reported. `ingest_setup._tokens_calibration` averages the actual/estimated ratio over a vault's last 3 such runs and scales `cost_estimate`'s displayed `est_tokens` by it; a vault with no history yet (or one that has only ever run standalone finalizes, which never set `est_input_tokens`) falls back to the raw heuristic rather than fabricate a correction. The calibration only touches the *displayed* estimate — `section.py`'s sectioning threshold, which governs what actually gets sent to the model, is untouched, since recalibrating live pipeline behaviour from a still-thin, self-reported history would be a much bigger claim than fixing a display number.

`ingest_setup.finalize_cost_estimate` prices `watchdog finalize --estimate` the same way `cost_estimate` prices ingest, but pointed at the staged `.watchdog/tmp/` corpus (`result_<sha>.json` + `notes_<sha>.md`, `chars/4`) instead of a queue. Its $/token ratio can't reuse `cost_estimate`'s own loop: a `run()` ingest's finalize tail shares its single usage file with extraction, and blending that in would badly misprice a lone finalize call in either direction. A new `orchestrate.FINALIZE_TASKS` set (`reconcile`, `entity-synthesis`, `timeline-dedup`, `timeline-precision`, `briefing`) marks which usage-`<ts>.json` files are safe to use: only ones where every recorded call falls in that set, which is true precisely when finalize ran standalone. A vault that has only ever finalized as part of `watchdog ingest` gets the token/doc counts with no dollar figure yet, the same treatment a first-run vault gets from `cost_estimate`.

**Tradeoff:** the calibration is not backend-aware — a queue about to extract on a different provider than produced the calibrating history gets the same correction as any other, matching `cost_estimate`'s own $/token ratio, which has never been backend-filtered either. And `finalize_cost_estimate`'s history requirement means a vault's first standalone `finalize --estimate` is always token-only; the dollar figure only appears once at least one standalone finalize has actually completed and left a usage file behind.

### D136 — `watchdog setup` auto-tunes `extract_concurrency` to 3 on a Claude subscription that keeps ingestion (issue #400)

Issue #400 traced a ~30-minute, 6-document ingest to one extraction call throttled to ~1/5 the normal token rate (12 tok/s vs 40–70 tok/s elsewhere) while 5 documents extracted concurrently under `extract_concurrency`'s default of 5. The cause is structural, not incidental: subscription auth is hard-routed to the `claude-agent-sdk` backend only (`model_client._resolve_backend_auth`), so every concurrent extraction on that path shares one Claude Code/Max session's rate limit — a separate, higher-throughput bucket exists for API-key auth (`claude-api`), which doesn't hit this.

Rather than lowering the global default (as a flat drop to 3 would do, penalizing API-key/claude-batch users who don't share the constraint) or making the default depend on auth mode at ingest time (which would make `extract_concurrency`'s displayed value diverge from what actually runs, undermining it as a config setting), the fix runs once, at the point the constraint is chosen: `cmd/auth.py`'s `_maybe_tune_concurrency_for_subscription`, called from `setup_auth_interactive` only when the user picks Claude subscription auth *and* declines to route ingestion to a metered provider instead (routing away means extraction no longer touches the subscription session, so nothing to tune). It writes `extract_concurrency: 3` to config and prints why, then behaves exactly like any other configured value from then on — visible in `watchdog configure`, overridable per-run with `--concurrency`, and left alone by every later run.

**Only fires when the key was never explicitly set.** A prior `watchdog configure extract_concurrency` — including an earlier auto-tune, or a value set before choosing subscription — is left untouched; the setup wizard silently overwriting a deliberate choice would be a bug, not a feature. This means re-running `watchdog auth` to switch modes later does *not* retune it (that entry point wasn't touched), and a user who wants the subscription-safe value after the fact sets it themselves.

**Tradeoff:** 3 is a judgment call, not a measured cap — the issue's evidence shows 5 throttles hard and doesn't establish where the ceiling actually sits, so this trades a still-uncertain safety margin for one less footgun on first setup. Because the tuning point is `watchdog setup`'s auth wizard specifically, it doesn't cover every way a vault could end up on subscription auth (e.g. hand-editing `credentials.json`) — those paths keep the flat default of 5 and rely on the existing rate-limit guidance in `docs/configuration.md` and `watchdog ingest --wait`.

### D137 — `finalizer_model` gains four per-stage overrides (issue #433)

`finalizer_model` was one knob over four independent `_call_model` tasks (`reconcile`, `entity-synthesis`, `timeline-dedup`/`timeline-precision`, `briefing`) — accurate for the common case, but it meant raising the whole post-ingest step's cost/quality just to fix one stage, e.g. a briefing that reads thin on the cheap default tier, with no way to leave reconciliation and synthesis on Haiku. `finalizer_reconciliation_model`/`finalizer_synthesis_model`/`finalizer_timeline_model`/`finalizer_briefing_model` (config keys, and the matching `--finalizer-<stage>-model` CLI flags on `ingest`/`finalize`) let any one of the four move independently; an unset stage still resolves to `finalizer_model`, so the existing single-knob behaviour is the default in every vault that never sets one.

`cmd/ingest._resolve_finalizer_overrides` resolves all four through the same `_resolve_stage` `[backend:]model` parsing the aggregate flag already uses, with `default` computed from the *already-resolved* `post_backend`/`post_model` — so an unset stage falls back to whatever the aggregate finalizer actually resolved to (flag, then config, then the `haiku` tier default), not a second hardcoded default. The four resolved `(backend, model)` pairs travel as one `finalizer_overrides` dict rather than eight new named parameters threaded through `orchestrate.run`/`finalize` — `_reconcile_pre_commit` and `_post_ingest` each pull only the keys they need via `dict.get(key, post_model_or_backend)`, so a key genuinely absent (any caller that predates this dict, including every existing test) falls back to `post_model`/`post_backend` exactly as before, while a key present with an explicit `None` backend — "route by auth mode", a legitimate resolved value — is never mistaken for "not overridden" (`dict.get` only substitutes its default when the key is *missing*, not when it maps to `None`).

Two places that already reasoned over "the backend(s) this run touches" needed to widen to include the four overrides, or they would have silently misjudged a lone overridden stage: the Claude-auth gate (a vault otherwise fully routed to another provider must still demand Claude auth if just `--finalizer-briefing-model claude-api:opus` is set) and the `claude-batch`-is-extractor-only guard. The pre-ingest "which model runs each stage" preview line gained a conditional `finalizer:<stage>` row per overridden stage — printed only when that stage's resolved value actually differs from the aggregate finalizer, so the common case (no overrides) prints exactly as before rather than repeating the finalizer row four times.

**Tradeoff:** four more config keys and CLI flags for a feature most vaults will never touch — accepted because the alternative (one blended finalizer tier) forces a real cost/quality tradeoff onto every stage to fix one, and the fallback-when-unset design means a vault that ignores all four pays nothing in behaviour change or documentation surface it has to read to stay on the old default.

### D138 — `ingest` retired in favour of the guided walk; `extract`/`finalize` renamed to `dig`/`bark` (issue #441)

#441 named the problem D130 left standing: `watchdog` (bare) and `watchdog ingest` both meant "run the pipeline for me," which is one too many entry points for a CLI aimed at journalists who may have little terminal background. The repo owner's call: retire `ingest` outright rather than fold it into the guided walk or vice versa — the two remaining paths are bare `watchdog` (guided, prompts at each stage, skips what's not pending) or the individual stage commands for manual control. Since `ingest`'s one-shot "extract + finalize, no prompts beyond the confirm" behaviour has no direct successor command, it's a straight retirement, not a rename.

The repo owner also asked, separately, to lean into the app's dog theme for the two commands that remain manual-control atoms: `extract` → `dig` (a dog digs to unearth something buried) and `finalize` → `bark` (a watchdog barks to raise the alert — apt for the stage that produces the briefing). `fetch` was the first pick for `extract` but was already taken by the unrelated URL-download command (`watchdog fetch`), so `dig` went with it instead.

All three old names are kept working through a deprecation window rather than deleted outright (pre-1.0, but this repo owner's call was explicitly "deprecate, don't break" here, unlike D130's precedent for `--no-finalize`). Two different mechanisms carry that, both in `cmd/base.py`/`cli.py`:

- **`extract`/`finalize`** are true 1:1 renames (same flags, same function — `cmd_extract`/`cmd_finalize` are untouched), so they go through a new `_DEPRECATED_ALIASES` dict, resolved in `main()` alongside the existing `_ALIASES` remap but — unlike a plain alias, which is silent by design — printing a one-line warning before rewriting `sys.argv[1]`. The subparsers themselves are registered under the new names (`sub.add_parser("dig", ...)`/`sub.add_parser("bark", ...)`); the old names never reach argparse.
- **`ingest`** keeps its own subparser and flags untouched (it still does more than `dig` alone — extract *and* finalize in one shot — so it can't remap onto either new name) and instead prints its deprecation warning from `main()` right before `args.func(args)` runs, pointing at both `watchdog` and `dig`+`bark`.

**Scope: CLI surface only.** Internal names — `cmd/ingest.py`, `cmd_ingest`/`cmd_extract`/`cmd_finalize`, `ingest_setup.py`, `.ingest-lock`, `ingest-state.json`, the general prose use of "ingest" as the pipeline concept — are unchanged. Renaming those too would be a much larger, riskier refactor than the issue asked for, and `cmd_extract`/`cmd_finalize` are exercised directly (not just through the CLI) by a large chunk of `tests/test_cli.py`, which would all need updating for no behavioural gain.

**Threading the right "run it again" hint.** `cmd_ingest` backs three surfaces now — deprecated `ingest` (full pipeline), `dig` (extraction only, `cmd_extract` sets `no_finalize`), and the guided walk (via `_offer_ingest`, `args.command is None`) — and its internal messages ("re-run to resume," "run X for the queued documents") used to hardcode `watchdog ingest`. A `pipeline_hint` local (`"watchdog dig"` if `args.command == "dig"` else `"watchdog"`) replaces those hardcodes, so a `dig` run points back at `dig` and everything else points at the bare walk, never at the retired command. The same value flows into `orchestrate.run` as its `resume_hint` parameter (stashed in a run-scoped `_resume_hint` module global, alongside the existing `_board`/`_usage` single-run state), so the extraction-side notices it owns — the rate-limit stop, and the claude-batch submit/poll/collect lines — name the launching surface too rather than always saying `dig`. Messages that unambiguously mean "run the finalize stage" (e.g. "post-processing didn't finish") always say `watchdog bark` outright, no hint needed — bark is bark's only successor regardless of which surface staged the batch. The one deliberately-fixed exception is the skill-pin nudge ("next time run `watchdog dig --skill <name>`"), which is advice about the extraction command specifically — `--skill` is a `dig` flag, so bare `watchdog` would not accept it.

**Tradeoff:** three names now do slightly different things depending on which deprecation era a user's muscle memory is from (`ingest`, `extract`/`finalize`, `dig`/`bark`), and every user-facing string that used to say "watchdog ingest" as a generic "run the pipeline" instruction needed a per-site judgement call on whether the right replacement is `dig`, `bark`, or bare `watchdog` — there's no mechanical rename here, just close reading of each call site. The three deprecated names have no removal date yet; issue #441 didn't set one, so they stay until a future decision retires them for real.

### D139 — `local`/`openrouter` backends: user-supplied base URL, optional API key (issue #380)

D37 already built the OpenAI-compatible backend abstraction (`openai`/`deepseek`/`gemini`, one fixed base URL each); every mainstream local runner (Ollama, LM Studio, llama.cpp's server, vLLM) and OpenRouter speak the same wire format, so the only things that actually vary are the endpoint and whether a key is required. Rather than two bespoke code paths, `_PROVIDERS` (`cmd/auth.py`) gained one generic shape — `base_url_key`/`base_url_env`/`default_base_url` for a user-supplied endpoint, `requires_key` for the rare provider (`local`) that doesn't need one — and `model_client._DYNAMIC_BASE_URL_BACKENDS` marks the two backends whose base URL is resolved per call (`auth.get_base_url`) rather than baked into `_ABACKENDS` as a fixed `functools.partial` the way `openai`/`deepseek`/`gemini` are. #413 (OpenRouter support) folded in here as the same mechanism with a key required and a fixed default endpoint, rather than a separate issue.

**Base URL lives in `watchdog configure`** (`local_base_url`, `openrouter_base_url`), not a new CLI flag or a `credentials.json` field — it isn't a secret, and the existing `configure` surface is where every other stage-routing knob already lives. `local`'s `requires_key: False` means `prompt_and_store_key`/`ensure_provider_key` treat a blank key entry as a normal, silent outcome rather than a declined step; the Authorization header itself is omitted (not sent as a literal `"Bearer None"`) when no key is configured, since most self-hosted runners don't check for one at all.

**Context window is genuinely unknowable, not just hard to look up.** Every other provider's context window is inferred from a substring match against its model id (`_CONTEXT_WINDOWS`); a self-hosted model's id is whatever the operator named it in their runner, with no vendor namespace to match against. `context_window` gained an explicit `backend` parameter — `local` skips the substring table entirely and reads `local_context_window` (a `watchdog configure` key) or falls back to a conservative 8,000-token default, favouring over-sectioning a genuinely large-window model over risking an overrun on an unknown one. `output_ceiling_for_sectioning` treats `local`/`openrouter` the same as `openai`/`gemini` (enforced `max_tokens`, no continuation) rather than exempting them, for the same reason those two needed it: a document sized to the input window alone could still overrun the output cap.

**Effort maps to a no-op for both**, not just `local` — an arbitrary self-hosted or OpenRouter-routed model has none of OpenAI's `_OPENAI_MODEL_CAPS` capability table to consult, so sending a reasoning-control param on spec risks a 400 from a model that doesn't recognize it; the conservative default is to never send one, matching the issue's own guidance ("map to `_no_effort` unless the served model exposes a reasoning control").

**Cost is genuinely $0, which `watchdog usage` now says explicitly rather than implicitly.** A local call has no pricing-table entry, so `cost_usd` reads as `None`/`$0.0000` exactly like any unpriced model already did — but unlike an unpriced hosted model, $0 here is not an oversight, it's the whole point, and it reads as "free" without the caveat that it was actually paid for in wall-clock time. `cmd/usage.py`'s per-stage header prints a one-line note when any call in that stage used the `local` backend, pointing at Latency as the real cost signal.

**Deliberately not yet claimed ready for extraction.** #380's own scope gate — evaluate against corpus-v1 (#361) before documenting any stage as recommended — has not run; `docs/configuration.md` says so directly rather than silently overselling it, and singles out the classifier and finalizer (short/forgiving output) as the more plausible first targets over the extractor (16K of schema-constrained JSON, the hardest case for a small model to hold together).

**Tradeoff:** `local`'s conservative context-window default will over-section a genuinely capable local model until the operator sets `local_context_window` themselves — accepted as the safe failure direction (more, smaller calls) over the alternative (an assumed-large window silently overrunning a small model's actual limit). OpenRouter's model catalogue is far too large and fluid for `cmd/setup.py`'s `_pick_model_interactive` picker to enumerate the way it does for OpenAI/DeepSeek/Gemini's fixed model lists, so both `local` and `openrouter` fall through to that picker's free-text "Type my own…" escape hatch instead of a curated group — a real gap versus the other providers' pick-from-a-list convenience, accepted because building and maintaining a synced OpenRouter catalogue is a much bigger commitment than the rest of this issue.

### D140 — `extractor_effort` defaults to `medium`, not `high` (issue #361)

`extractor_effort` defaulted to `high`, which `_claude_effort` treats as "omit the effort parameter" — the model's own native reasoning depth — so an unconfigured install and an install that explicitly set `high` behaved identically, and the cost lever D36 built had never actually moved from its no-op position. The corpus-v1 benchmark settled whether a lower setting costs recall: scored against the frozen keys with the deterministic anchor scorer, `medium` and `high` tied exactly (38/39 scorable facts, 22/24 `must_not_miss`, same items missed on both) on `bench-ex-sonnet-med` vs `bench-ex-sonnet-high`. Cost did not tie — same document (`Annual-Financial-Report-20-21`, the corpus's dense 70-page filing), medium produced 23,093 output tokens ($0.95) against high's 60,175 ($1.53), 2.6× the output for identical recall. A whole-corpus check (`bench-t0-sonnet-med`, complete, vs `bench-ex-sonnet-high`, complete) held the same direction: $4.81 vs $5.64 for extraction, even with the Tier-0 checklist's known output-inflation riding on the medium arm. Full record: issue #412's original assessment named the effort A/B as the next benchmark to score; the verdict is in issue #361's comments.

Changed at three call sites so an unconfigured install actually gets the new behaviour rather than continuing to omit the parameter: `cmd/setup.py`'s `DEFAULTS["extractor_effort"]`, and both `config.get("extractor_effort", ...)` reads in `cmd/ingest.py` (the cost-preview path and the real run path) — a raw `config.get(key)` with no fallback returns `None` for a key never written to `config.json`, which is why the default had to move at the read site, not just in the documented `DEFAULTS` table those reads don't consult.

**Scope: extractor only.** `finalizer_effort` keeps its `high` default unchanged — entity reconciliation is cross-document judgement, not harvesting, and the #412 assessment flagged it as a different quality/cost shape that this benchmark didn't test. Revisit separately if `finalizer_effort` is ever benchmarked the same way.

**Tradeoff:** a corpus of one domain (CCAA financial and legal filings, six documents) generalizing to "medium is the right default" for every domain and provider is an inference, not a proof — the config override (`watchdog configure extractor_effort high`, or `--extractor-effort high` per run) exists precisely for a corpus where it doesn't hold. `finalizer_effort` staying at `high` while `extractor_effort` moves to `medium` also means the two knobs' defaults no longer match, which the CLI help and `docs/configuration.md` now say explicitly rather than leaving as an unexplained asymmetry.

### D141 — Figure-grounding warnings gain exact scale matching and a separate citation warning (issue #397)

#397 asked Claude to inspect the `ingest.log` from 10 benchmark vaults for anything out of the ordinary. The dominant signal was volume, not hallucination: 375 `figure(s) … not found` warnings (D112/#363) across 6 real CCAA/financial-statement source documents, and cross-checking every flagged number against the actual PDF text showed the checker was almost never catching a fabricated figure. Two benign patterns accounted for the bulk of it: (1) financial statements report line items in thousands under a "(in $000s)" table header, and a model correctly writing the fact in full dollars (page shows `21,406`, fact says `$21,406,000`) is an exact ×1,000 shift of the same digits, not a paraphrase; (2) a fact combining a current-page figure with a comparative pulled from elsewhere in the same document (e.g. an MD&A highlights page) cites one page for a number that's real but sourced from another.

D112's original docstring called the "$1.2 million" vs "$1,200,000" case an accepted miss, reasoning that expanding a short decimal risked a coincidental false match. That reasoning holds for free-form rounding, but an *exact* ×1,000/×1,000,000 relationship is a different claim — `_scale_variants` (`figure_verify.py`) shifts a token's decimal point losslessly via `Decimal.scaleb` and checks both directions before giving up, which cannot produce the kind of coincidental small-number match D112 was guarding against (the two values are provably the same digits, not merely close). Rounded figures (a fact says "$198.4 million" for a page value of "198,397" thousand) still don't match — that's real arithmetic, not a scale shift, and stays out of scope deliberately.

For a figure that clears the near-page + scale check but is verbatim (or scale-equivalent) elsewhere in the whole document, `verify_figures` now emits a second, distinct warning ("the figure is real, the page citation may be wrong") instead of folding it into "may be derived or garbled" — the two failure modes have different remedies (fix a citation vs. check whether a number was ever grounded at all) and conflating them was itself part of why the warning read as noisy.

Re-running both checks against the #397 corpus: 42.6% of previously-flagged figures now produce no warning at all, 38.5% downgrade to the softer citation warning, and 18.9% remain flagged as before — spot-checking that remainder showed genuine cases (a rounded figure cited to a page that turned out to be the wrong financial statement entirely), not residual noise.

**Tradeoff:** the whole-document index (`_index_pages`) is built lazily and cached for the rest of the call — only a document with at least one near-page miss pays for tokenizing every page once, everything else is unaffected. `_SCALE_EXPONENTS` covers thousands and millions only (the two conventions actually seen in this corpus); a document using another convention (e.g. lakhs) would still miss, same as before.

### D142 — A single hand-editable model catalog (`model_catalog.yaml`/`.py`) replaces five parallel per-model tables (issue #453)

#453 asked whether a third-party abstraction (e.g. LiteLLM) would fix the "adding a model/provider touches too many places" pain in `model_client.py`. It wouldn't cleanly: LiteLLM doesn't unify the Anthropic Batches path, has no equivalent for the `claude-agent-sdk` backend (the Claude Code agent loop, not a chat completion), and doesn't touch Watchdog's deliberate per-provider structured-output design (D98). It also adds real dependency risk — a March 2026 supply-chain compromise of LiteLLM's own PyPI publishing credentials shipped two backdoored releases, on top of 800+ open issues — for a benefit (a maintained pricing/model table) this change gets directly instead.

`model_client.py` carried five separate per-model tables (`_MODEL_IDS`, `_PRICING`, `_OPENAI_PRICING`, `_CONTEXT_WINDOWS`, `_OPENAI_MODEL_CAPS`) that a new model or provider had to be threaded through individually — exactly the drift D91/D92 already hit once for OpenAI. `cmd/base.py` also carried a **sixth**, silently divergent copy (used by `_launch_claude`, which shells out to the `claude` CLI for `watchdog context` etc.): it pinned haiku to a dated snapshot (`claude-haiku-4-5-20251001`) left over from a June 12 commit predating the current Python-orchestrator architecture, while `model_client.py`'s table had already moved on to the plain alias (`claude-haiku-4-5`) — accidental drift, not a deliberate difference, confirmed and fixed with Tom.

All six collapse into one YAML file, `model_catalog.yaml`, one record per model — id, provider, pricing, context window, and (OpenAI only) whether it's a reasoning model — plus two small substring/prefix fallback tables (verbatim from the old `_CONTEXT_WINDOWS`/`_OPENAI_MODEL_CAPS`) for a model that isn't explicitly catalogued (an unpriced `local`/OpenRouter model, or a new id shipped before Watchdog catalogs it). A new leaf module, `model_catalog.py` (stdlib + `yaml` only, no watchdog-internal imports), loads it via `importlib.resources` — the same mechanism `pipeline/prompts.py` already uses for packaged non-`.py` files — and both `model_client.py` and `cmd/base.py` import from it, avoiding an import cycle (`model_client` → `cmd.auth` → `cmd.base`, so `cmd.base` can't import `model_client` directly). Every model also carries a pretty `name` (e.g. `gpt-5.6-terra` → "GPT-5.6 Terra"), exposed via `display_name()` and consumed by `watchdog usage`'s per-stage model line and `cmd/setup.py`'s interactive picker, in place of the raw id — a full name, not an abbreviation, so it doesn't reintroduce the mangling D112-era abbreviation logic caused for non-Claude ids (`gemini-3.1-flash-lite` → `3.1`).

Two new OpenAI models (`gpt-5.6-terra`, `gpt-5.6-luna`) were added to the catalog in the same change, pricing confirmed against two independent sources.

**Tradeoff:** PyYAML's default float resolver requires a decimal point before the exponent (`2.5e-6` parses as a float; `15e-6`, no dot, silently parses as the string `"15e-6"`) — several existing rates use the no-dot form. Rather than reformat every value and hope it's never mistyped again, `model_catalog.py`'s loader coerces every number with an explicit `float()`/`int()`, so a bad hand-edit fails loudly at import time instead of corrupting a cost calculation later. The backend-dispatch registry consolidation that rides alongside this in the same change (`_BackendMeta`/`_BACKEND_META`, replacing `_BACKEND_PROVIDER`/`_OPENAI_BASE`/`_DYNAMIC_BASE_URL_BACKENDS`/`_CONTINUATION_BACKENDS`/`_BATCH_ONLY_BACKENDS`) is a pure internal refactor with no behavior change and isn't part of this decision's rationale — it doesn't foreclose any option, so it isn't recorded here separately.

### D143 — `--estimate-all` projects a queue/batch estimate across the whole model catalog by list price, not by this vault's own $/token history (issue #469)

#469 asked for a way to see what ingesting (or finalizing) the current batch would cost under every model Watchdog knows about, not just whichever one is configured — the catalog now has close to twenty entries (D142), too many to eyeball by hand-editing `extractor_model`/`finalizer_model` and re-running `--estimate` once per model. #469 itself flagged the open question: with that many models, a naive "estimate every kind of call for every model" fans out fast.

`cost_estimate`'s existing single-model estimate resolves this by multiplying tokens by a $/token ratio drawn from this vault's own usage history for the model that actually ran — that ratio has no equivalent for a model that has never run here. Rather than invent one, `--estimate-all` instead prices `est_tokens` (the same already-calibrated figure the single-model estimate shows) directly against each catalog model's own published input/output rate, scaling the output side by this vault's own recent output:input *token* ratio (`ingest_setup._output_token_ratio`) — a backend-agnostic extrapolation in the same spirit as D135's existing tokens-in calibration, just applied to the output side and reused across providers instead of scoped to one. The result is a single cheapest-first table, one line per catalog model, which is what keeps the "too many estimates" problem from #469 from actually showing up: one number per model, not one per model per call type.

Cache pricing is deliberately not modeled — every input token is priced as a cache-miss, which overstates cost for any model whose real usage would benefit from caching, consistently across the whole table rather than picking a hit rate per provider that would just be a second guess layered on the first. Every catalog model appears, including all three Claude tiers, regardless of whether this vault is on subscription auth: the table is a list-price comparison across providers, explicitly not "what would I actually be billed," so withholding Claude's figures under subscription auth (the way the single-model `--estimate` already does, D72) would defeat the point of a cross-provider comparison. A vault with no usage history yet has no output ratio to project from, so `--estimate-all` shows the same "not enough history" treatment the single-model estimate already gives a first-run vault, rather than a fabricated table.

**Tradeoff:** treating the output:input token ratio as a property of the vault's documents rather than of the model that produced it is an approximation — a genuinely more verbose model (or one that reasons more before answering) would skew the real ratio for itself specifically, and this table can't know that in advance. Accepted for the same reason D135's own input-side calibration accepts an equivalent approximation: a rough, self-consistent comparison across many models beats no comparison at all, and the alternative (waiting for real per-model history before showing anything) would make the feature useless for exactly the "which model should I try" question it exists to answer.

### D144 — `claude-batch` resolves each document's own skill instead of requiring a run-wide pin (issue #475)

Batch extraction (D52) is the single largest untapped cost lever in the pipeline: 50% off every token, stacking with prompt caching, for a stage that is inherently batch work. It had gone unused, and the reason was a precondition rather than the discount — `cmd_ingest` refused a `claude-batch` run without a run-wide `--skill`/`default_skill`, on the reasoning that "classification isn't batchable." That conflated two things. Classification genuinely can't be *batched* (it is one cheap call over one document's first pages), but nothing required it to be *skipped*: it can simply run synchronously, per document, before the batch is assembled — which is exactly what the non-batch path already does.

The requirement was also self-defeating for the workflow batch mode targets. A journalist's bulk drop is routinely mixed — filings, financial statements, correspondence in one tranche — and a run-wide pin forces every document to be read under one skill. Sorting a dump by type before ingesting it, or running one pass per type, is precisely the manual work the sidecar-pin mechanism (D120) exists to remove. Watchdog's own benchmark corpus spans two skills, so the constraint made corpus-v1 unbenchmarkable on the batch backend at all — the discount could not be measured on the one corpus set up to measure things.

`_run_batch` no longer requires `pinned_skill`. Each document resolves its own skill through a new shared `_resolve_skill` helper following D120's existing precedence — sidecar pin, then run-wide pin, then one classify call — and that helper is now the single implementation used by both the synchronous per-document path and the batch submit path, so the precedence cannot drift between them (duplicating it once is what produced this constraint). A batch may therefore mix skills: the skill lives inside each request's own prompt content blocks, which the Batches API treats independently, so one submission carries them all rather than needing one batch per skill group. Requests are sorted by skill label before submission so adjacent same-skill requests still share the cached instructions+skill prefix — a cost optimization only; correctness does not depend on the ordering. Because collection happens in a *later* process (a batch can sit in flight for up to 24 hours), the per-sha skill mapping is persisted in `batch-pending.json`; `_batch_skill` reads it, falling back to the pre-D144 single `skill_label`, then to the run's own pin, so a batch submitted before this change is still collectable after an upgrade instead of stranded.

**Tradeoff:** an unpinned batch now pays classification at full price — one Haiku call per document over a five-page excerpt, undiscounted, since it happens before submission. That is a real cost the old constraint avoided, and it is deliberately accepted: it is a trivial fraction of a run whose extraction is half price, and paying it is what removes the requirement to pre-sort documents by type. Anyone with a genuinely homogeneous batch can still pass `--skill` and skip classification entirely, so the old behaviour remains available as an option rather than an obligation. The narrower alternative — keeping the pin requirement and adding a `skill:` field to benchmark arms — was rejected because it would have forced one skill across corpus-v1's two document types, making the batch arm's recall scores incomparable with every other arm while measuring only cost.

### D145 — The agent-SDK backend disables built-in tools with `tools=[]`, not just `allowed_tools=[]` (issue #475)

The #475 cost audit found Claude extraction calls billing far more input than their content accounted for. Reconstructing each prompt from its parts (page text + `extract_instructions.md` + the matched skill + the EXTRACTION schema + the harvest checklist) and comparing against billed input showed a gap that was **constant per call**, not proportional to document size: ~12.2K tokens on a 5-page order, ~13.1K on a 34-page report, ~11.6K on a 70-page report. A tokenizer difference would scale with the text; a fixed preamble does not. For reference the same prompts on the DeepSeek backend bill 1.01× the chars/4 estimate — essentially exact.

The cause was a misreading of the Claude Agent SDK's options. `_agent_query` passed `allowed_tools=[]` under the comment "reasoning only — no tools", but that option governs **auto-approval**, not availability: with it empty the model is never permitted to call a tool, while every built-in Claude Code tool remains **defined** in the request. Availability is `tools`, which we never set — and `ClaudeAgentOptions.tools` defaulting to `None` makes the transport omit `--tools` entirely, so the CLI falls back to its full default tool suite. Because the model duly never called anything, behaviour was correct and nothing surfaced the cost; only the token bill showed it. A direct two-call probe (identical prompt: "Reply with the single word: ok") confirmed it: **11,297 input tokens with the old options, 143 with `tools=[]`** — 11,154 tokens, matching the measured per-call gap.

`tools=[]` is now passed alongside `allowed_tools=[]`. The two are independent and both are kept: `tools` removes the definitions, `allowed_tools` keeps nothing auto-approved. Since `tools` postdates the `claude-agent-sdk>=0.1` floor in `pyproject.toml` and `ClaudeAgentOptions` is a dataclass (an unknown kwarg raises `TypeError`), `_agent_supports_tools()` inspects the installed dataclass's fields rather than a version string, and an older SDK silently keeps the previous behaviour.

The saving is **per call, not per page**, which makes it scale with document *count* — the opposite of intuition, and the bad case for Watchdog's own workflow. At the cache-write rate a Claude tier pays for this prefix, ~11.2K tokens is roughly $0.042 per extraction call on Sonnet: negligible on a corpus of a few large reports (~5% of the six-document benchmark run), but about $8 of pure waste on a 200-document ingest. It also removes ~11K tokens of irrelevant tool schemas from a context window the extractor is meant to spend on the document.

**Tradeoff:** this narrows what the agent-SDK backend *could* do — a future pipeline stage wanting genuine tool use (a web-enabled research call routed through this backend) would have to name the tools it needs rather than inheriting the full suite. That is the right default anyway: every current pipeline stage is a single-shot, schema-bound completion (I4, `max_turns=1`), so inheriting an agent harness's tool suite was never intentional, and an explicit opt-in is what the option is for. The `claude-api` and OpenAI-compatible backends were never affected — they define no tools at all.

### D146 — Benchmark vaults get an isolated, gitignored shadow root instead of the real `projects_dir`, and both of `cmd_new`'s registrations are undone (issue #475 follow-up)

Running `run_benchmark.py` created its `bench-*` vaults through the installed watchdog's own `_projects_dir()` — the user's real `~/investigations` — and `cmd_new` registers every vault it creates in **two** places by design: `~/.watchdog/projects.json` and, via `_register_obsidian_vault`, the Obsidian app's own `obsidian.json` (its vault switcher). Every benchmark run left permanent trace in both: by the time this was noticed, 12+ stray `bench-*` entries had accumulated in `projects.json`, and separately 18 of the user's 19 registered Obsidian vaults turned out to be `bench-*` fixtures — the more user-visible of the two, since it's the switcher in the app itself.

`run_benchmark.py` now resolves a `vault_root()` — `--vault-root`, then benchmark.yaml's optional `vault_root:` key, then the default `benchmarks/.vaults/` (gitignored) — and creates every master/arm vault under it instead. It still builds each vault with the real `cmd_new`, not a hand-rolled directory tree, because fidelity to an actual vault's layout is the point of the benchmark; the tradeoff is that both of `cmd_new`'s registration side effects have to be explicitly undone. `_deregister_benchmark_vault` removes just the slug `cmd_new` was given from `projects.json`; `_deregister_obsidian_vault` does the Obsidian-side equivalent, matching on the vault's `path` (Obsidian keys its `vaults` dict by an opaque random id, not the path) and mirroring `_register_obsidian_vault`'s own non-fatal error posture, so a missing, unreadable, or corrupt `obsidian.json` — or Obsidian not being installed at all — never fails a benchmark run. Both run immediately after creation, so a benchmark vault never appears in either registry at all rather than being registered and later cleaned up. The pre-existing stray `bench-*` entries and vaults from before this fix — in both `projects.json` and `obsidian.json` — are left untouched; they are the user's data, not this change's to migrate or delete, though the user may want to clean up `obsidian.json`'s switcher entries by hand.

### D147 — Section overlap scales with the section budget instead of a fixed token count; the output-ceiling budget is no longer halved a second time (issue #490)

Benchmarking the extractor sweep found openai/gemini arms needing 51 model calls for a 6-document corpus that Claude clears in 6 — one 70-page document alone split into 22 sections. Tracing `section.plan_ranges` against the real numbers found two independent, compounding bugs in `section.py`, both inherited from constants tuned for Claude's much larger default budget and never re-examined for the much smaller output-ceiling-capped one openai/gemini actually run under.

`DEFAULT_OVERLAP_TOKENS` was a fixed 4,000-token value, calibrated so Claude's historical 60,000-token default budget got a sensible 6.7% overlap between consecutive sections. On the output-capped path (~7,000-token budget, pre-fix), that same fixed value was 57% of every section — most of each section's content was pages the previous section had already covered, multiplying section count for no benefit page-boundary tables/paragraphs actually needed. `model_defaults` also halved the ceiling-derived budget a second time (`max_input // 2`) on top of that — inherited from the *input-window* path, where halving genuinely serves a purpose (`_BUDGET_FRACTION` is deliberately half `_THRESHOLD_FRACTION`, so a document just over threshold still splits into ≥2 sections), copied onto the output-ceiling path where that reasoning doesn't apply: the ceiling-derived value already represents the full safe amount a single call can handle, for a whole document or one section alike, so halving it again was a straight 2x tax with no added safety margin behind it.

Fixing both (overlap as a fraction of budget, calibrated to reproduce Claude's exact historical behavior at its default budget; dropping the second halving) took the 70-page document's plan from 22 sections down to 6 — matching Claude's own call count for the same document, with total pages re-read across all sections dropping from 220% over-read to 7%. Also fixed in the same change: `model_defaults` checked both `threshold` (which gates the whole-document `extract` task) and `budget` (which sizes an `extract-section` call) against a single `output_ceiling_for_sectioning("extract", ...)` lookup — currently harmless since both task keys map to the same value in `_TASK_MAX_TOKENS`, but the wrong capability was being checked for `budget`, not merely a redundant one; each is now checked against its own task's ceiling.

Separately, `SECTION`'s `morgue_entity_id`/`morgue_document_type`/`observations` were widened from bare `"string"` to nullable — `gpt-nano` (an OpenAI reasoning model, where watchdog gets no wire-level structured-output enforcement, only prompt-level schema-in-text plus post-hoc validation) was hard-failing every sectioned document with `"None is not of type 'string'"`, three identical errors matching exactly these three optional fields: without real enforcement, a model meaning "nothing for this section" sometimes emits an explicit `null` rather than omitting the key. Every downstream reader already treated null and absent identically (`merge.py`'s `sec.get(...) or ...` folding, postflight's emptiness checks on the merged document), so this cost nothing.

**Tradeoff:** widening those three fields raises `SECTION`'s count of *nullable* optional properties from one to four. Anthropic's own optional-parameter-count limit (D-adjacent to the #487 fix earlier this session) is undocumented on whether nullable-typed fields weigh more heavily than plain ones — if they do, at a hypothesized worst-case 2x weighting `SECTION`'s count could approach the hard limit of 24 (raw count 21, worst case ~25) rather than sitting comfortably inside the existing safety margin. Accepted rather than built around, since the weighting theory itself was never confirmed (only inferred defensively during the earlier fix) and this failure mode — if it does materialize — surfaces as an immediate, loud per-document 400 error identical to the one #487 already fixed, not a silent one, and only on a Claude-backed extraction large enough to need sectioning at all (none of corpus-v1's documents currently are).

### D148 — `SECTION`'s `document.key_facts` is required on every section, and `document` is required at the top level (issue #496)

`bench-ex-gemini-flash` (#488, `extractor_effort: low`) came back with zero `key_facts` on every one of its four sectioned documents, while reporting a clean `OK` in `ingest.log` — entities extracted normally for the same documents, so this was specific to facts, not a wholesale extraction failure. Root cause: `SECTION`'s inline `document` sub-schema carried no `required` list at all (unlike `EXTRACTION`'s `_DOCUMENT`, which has required `["title", "document_type", "summary", "key_facts"]`) — a leftover from the sub-schema being loosened, correctly, so later sections could omit title/document_type/summary (only section 1 fills those). That loosening collaterally dropped the one field every section, first or later, was always supposed to carry. `document` itself was also optional at the `SECTION` top level, so a section could dodge the inner requirement by omitting the object entirely. Neither gap raised a schema-validation error — jsonschema's `required` check only fires on keys actually listed, so an omitted `key_facts` (or an omitted `document`) validated cleanly, merged into an empty list, and postflight found nothing wrong because an empty `key_facts` array is also the legitimate shape for a section that truly has nothing to report.

The bug is old — the sub-schema has carried no `required` list since the very first Python-orchestrator commit (#118) — but effort pins are what surfaced it now. At `medium`/`high` reasoning effort a model apparently attends to the field anyway, out of following the prose instructions (`extract_instructions.md` calls `key_facts` "the heart of the extraction"); at `low` effort, with less budget spent reasoning about what to include, an optional field with no wire-level enforcement is exactly the kind of thing a model economizes away first. The fix makes `key_facts` required inside `document` and `document` required at the `SECTION` top level, unconditionally — regardless of section index — so the model can no longer silently skip either. An empty `key_facts` array is still valid (a section can genuinely carry no material facts); what's no longer valid is omitting the field or the object to avoid deciding.

**Tradeoff:** none of substance — this closes a validation gap that was never protecting a real invariant, matching the same reasoning the sibling nullable-widening fix above used to justify *loosening* three other `SECTION` fields the opposite direction. The one open question the originating issue raised and this change does not resolve: `gemini-flash`'s two *unsectioned* documents also came back low on facts (4 and 8, against 56 on the same 70-page document from `sonnet-med`) — `EXTRACTION`'s `document.key_facts` was already required, so that's not the same schema gap, and is left as a follow-up model-quality question rather than folded into this fix.

### D149 — `SECTION`'s `title`/`document_type`/`summary` widened to nullable, section-only (issue #490 follow-up)

A live `gpt-nano` rerun after D147/D148 landed hit the exact same `"None is not of type 'string'"` × 3 failure D147 had already fixed once, on a different trio of fields: `document.title`, `document.document_type`, `document.summary`. Cause: D148 made `document.key_facts` required on every section, which meant later sections — which have nothing to say on the genuinely section-1-only fields — started returning to that part of the object at all, and `gpt-nano`'s weak `json_object` mode nulled the three rather than omitting them, same failure shape as the morgue/observations fields D147 already widened. Reproduced directly against `schemas.SECTION` before fixing: a section document with these three set to `None` throws the identical three errors seen live.

Fix mirrors D147 exactly, but scoped to `SECTION` only, not `EXTRACTION`: a `_SECTION_DOCUMENT_PROPS` dict copies `_DOCUMENT`'s properties and overrides just these three to `_NULLABLE_STR`, rather than widening `_DOCUMENT` itself (which `EXTRACTION` also uses, and where these three are required to carry real content — a whole-document extraction has no analogous "this is section 2, I have nothing to add" excuse). `merge.merge_extractions` only ever reads `title`/`document_type`/`summary` from the first section that has a non-empty `document` dict (`next((dict(d) for d in docs if d), {})`), so a later section nulling them was already inert downstream — this is a validation-only fix, same as D147's.

**Tradeoff:** raises `SECTION`'s nullable-optional-field count from four to seven, further into the unconfirmed-but-flagged Claude optional-parameter-limit risk D147 already accepted rather than built around. Same reasoning applies: unverified live, surfaces loud and immediate if wrong, and only on a Claude-backed extraction large enough to section at all.

### D150 — `_validate` now path-qualifies error messages; `SECTION.entities` is optional and `key_facts[].date` is nullable (issue #490 follow-up)

Rerunning `bench-ex-gpt-nano` after D149 landed hit the identical `"None is not of type 'string'"` × 3 failure D149 had just fixed, on the same two documents — but D149's fix was independently verified correct (mutation-tested, reproduces and clears the exact repro). A same-shaped failure recurring after a verified fix meant *different* fields were null this time, but there was no way to tell: `model_client._validate` kept only jsonschema's bare `e.message`, discarding `e.path`, and truncated to the first three errors with no note that more existed — any three nulled string fields produce the exact same three-line message. `_validate` now prefixes every message with its JSON path (`document.entities[2].name: ...`), and the caller appends `(+N more)` when errors are truncated; this alone required no schema change and is a pure diagnostics improvement (D125-adjacent: even a failed call's errors are worth logging legibly, the same instinct that made a failed call's usage worth logging at all).

That fix immediately paid for itself: the very next rerun surfaced two distinct, previously-indistinguishable failures. First, `"'entities' is a required property"` — a section naming no new entities omitted the key entirely rather than returning `[]`. Unlike `document`/`key_facts` (D148), `entities` has been required since the original Python-orchestrator commit, not from a documented silent-omission incident, and `merge.merge_extractions` already reads it as `sec.get("entities", [])` — so the requirement was stricter than the code needed, with no compensating benefit against a weak-enforcement backend that doesn't reliably obey `required` in the first place. `entities` is now optional at the `SECTION` top level. Second, `document.key_facts[].date` — nulled on 21 of 26 facts in one document rather than omitted, the same weak-`json_object`-mode null-vs-omit gap D147/D149 already fixed elsewhere in this schema. `date` (shared by `_KEY_FACT`, used identically in both `EXTRACTION` and `SECTION`) is now nullable; every reader already treats null and absent identically (`postflight._sanitize_dates`'s `if date and ...`, `explode_key_facts`'s `(fact.get("date") or "").strip()`).

**Tradeoff:** raises `SECTION`'s nullable-optional-field count from seven to eight and its raw optional-property count from 19 to 20, both further into the unconfirmed-but-flagged Claude optional-parameter-limit risk D147 first accepted. Same reasoning applies unchanged. Loosening `entities`' requiredness also reopens, narrowly, the kind of silent-omission risk D148 closed for `key_facts` — a model that quietly skips all entities in a section now fails validation rather than the whole document — but the alternative, given no per-section checkpointing yet (#498), is a hard failure that discards an entire already-paid-for document over one section's harmless "nothing new here," which is a worse outcome for a field with far weaker "silently dropping this is a known incident" grounds than `key_facts` had.

### D151 — OpenAI gets real strict-mode `json_schema` structured output, via a mechanically-derived schema variant (issue #479)

D98/D147/D149/D150 fixed four rounds of the same failure on OpenAI's `json_object` mode — a null emitted in place of an omitted optional field — one field (or field family) at a time, each round costing a full merge/pull/delete-benchmark/rerun cycle to even discover the next one. D98 had already scoped out the real fix ("a real fix for OpenAI would need a parallel all-fields-required schema variant... a separate, larger piece of work") pending evidence that prompt-only enforcement failed often enough to be worth it (issue #479's own stated acceptance criteria). Four consecutive rounds against the same schema family, on the same two documents, is exactly that evidence — the risk was never actually confined to the fields already hit; every optional bare-typed field in `schemas.py` (`_KEY_FACT.basis`, `_DOCUMENT_REQUEST.likely_source`, etc.) was next in line, just not yet exercised by this benchmark's specific documents.

Built the derivation #479 sketched, mechanically rather than as a hand-maintained parallel schema (the thing D98 explicitly wanted to avoid): `model_client._to_strict_schema(schema)` recursively sets every object's `required` to all of its properties, and widens each newly-required property to a nullable union if it was originally a scalar type (matching the `_NULLABLE_STR` convention already used throughout `schemas.py` — "no value" is expressed the same way everywhere) — including appending `None` to an `enum` list, since a nullable `type` alone doesn't let a null value satisfy an otherwise-null-free enum. A newly-required *array*-typed property is left as a plain array: the model can already express "nothing here" as `[]`, so no null union is needed there, and there are currently no optional object-typed properties anywhere in `schemas.py` to worry about. `_openai_response_format` routes real OpenAI (matched the same way `_openai_complete_async` already gates `max_completion_tokens`) to `{"type": "json_schema", "json_schema": {"strict": true, "schema": _to_strict_schema(schema)}}`; Gemini keeps using the schema as-authored (its engine already tolerates partial `required` lists), and DeepSeek/local/OpenRouter are unaffected (D98/D139's reasons still hold).

The round trip back is symmetric: `_denormalize_strict_json` parses the raw response and runs `_strip_none` over it before returning `text`, recursively dropping every `None`-valued key — undoing the nullable-widening so the parsed payload has exactly the omitted-vs-present shape `schemas.py`'s real (non-strict) schema, and every existing downstream reader's long-established null-tolerant `.get(...)` handling, already expect. `acomplete_json`'s shared validate/prune path needed zero changes: it still validates against the schema callers actually pass (`schemas.SECTION`, etc.), never the derived strict variant, which exists only inside `_openai_complete_async` for the duration of one request/response pair.

**Tradeoff:** the issue's own measurement estimated ~2,600 extra output tokens on OpenAI's most expensive single-document call (a 70-page report, ~438 now-mandatory nullable fields) — a real, unmeasured-until-a-live-run cost increase, directly opposed to #475's cost-reduction goal, accepted because eliminating a category of failure that has now cost four separate PR-and-rerun cycles is worth more than the token cost of a single call, and because the wire-level guarantee also means a genuine schema violation is caught and can be corrected in one targeted retry instead of the "full blind resample" D98 flagged as the old failure mode's own cost. Whether the token cost is worse in aggregate than the retries it avoids is exactly what the next `bench-ex-gpt-nano`/`bench-ex-gpt-mini`/`bench-ex-gpt-luna` rerun will show.

### D152 — Sectioned extraction gets a section-1-only repair retry on post-flight rejection, mirroring `_simple_extract`'s existing repair loop (issue #505)

A live `bench-ex-gpt-nano` run (2026-07-29, benchmarking #361/#215) failed post-flight on one document — *Laurentian First Report of the Monitor.pdf* — with `morgue_entity_id is missing or empty`, even though D151's strict-mode fix had landed minutes earlier. Traced, not guessed: the document went through `_extract_sectioned` (too long for a single call at `gpt-5.4-nano`'s output budget), and `morgue_entity_id`/`morgue_document_type` are section-1-only fields by prompt design (`build_section_prompt`'s `is_first` branch) — `merge.merge_extractions` already takes the first non-null value across all sections (so a later section supplying one would have been picked up), but no later section is ever prompted to supply them, so a model that nulls them on section 1 has no path to recovery. `_simple_extract` (the whole-document path) already has exactly this kind of safety net — `for _ in range(2):` with `_append_repair_note` re-asking the model once if post-flight rejects — but `_extract_sectioned` ran post-flight once on the merged result and simply returned the failure with no equivalent.

Added a single targeted repair attempt: if post-flight fails and every error is one only section 1 could ever have caused (`morgue_entity_id`/`morgue_document_type` — `_repairable_by_section1`), re-call *just* section 1 with the repair note appended, re-merge, and re-run post-flight once. Deliberately not a whole-document re-section: the other sections were never the problem, so re-running them would spend money without fixing anything. Deliberately not a general retry-on-any-postflight-error: an unrelated failure (e.g. a malformed `key_facts[].basis`) could come from any section, and section 1 alone re-answering wouldn't reliably fix it — better to fail clearly than to spend a repair call on a guess. `_extract_one_section` and `_merge_sectioned` were factored out of `_extract_sectioned`'s body so the repair path reuses the exact same prompt-building/digest/stamp logic as the normal loop, rather than a second hand-copied version that could drift.

**Tradeoff:** this repair path only covers the two fields it was built for — a different section-1-only field failing the same way would need its own prefix added to `_SECTION1_OWNED_ERROR_PREFIXES`, not a free ride. Accepted because scoping broadly (retry on *any* postflight failure) risks masking real key_facts/entities defects behind a repair call that can't actually fix them, which is a worse failure mode than a document that still fails, clearly, after one honest attempt.

### D153 — Zero `key_facts` on a substantive document is now a hard post-flight failure, not a silent OK (issues #507/#510)

A `sonnet-high` benchmark arm (2026-07-29, the #361/#215 qualitative judge pass) billed a real, normal-looking call — 8,690 input tokens, $0.032 — against a 17-page CCAA court order dense with extractable facts (the sibling `sonnet-med`/`gpt-mini` arms both extracted 13+ entities and dozens of facts from the identical chewed text) and got back `key_facts: []`, one entity, and a placeholder `"summary": "..."`. Nothing in the pipeline caught it: `postflight._validate` never checked `key_facts` for emptiness, and the existing skim detector (`_find_coverage_gap`, #339) is structurally unable to — it needs at least one page-cited fact to measure a gap against, so zero facts trips its own early-return (`if not cited: return None`) rather than its gap logic. The document shipped as a plain `OK` in `ingest.log`, indistinguishable from a document that genuinely had nothing to extract.

`_validate` now rejects `document.key_facts == []` when the document's *actual* chewed source text (`page_texts`, read from the queue descriptor at the chew-time queue's page markdown, not the model's own reported `page_count`) totals at least `empty_extraction_min_words` (default 500). Word count rather than page count is deliberate: a page count is a poor proxy for how much there was to extract from — an exhibit-heavy filing can run many pages of near-blank scans, while a dense short order can carry more real text than a longer, sparser one — so gating on the real text volume catches both a short-but-dense document a page-count gate would have missed and avoids flagging a long-but-thin one a page-count gate would have wrongly caught. `postflight.run` now reads the queue file before calling `_validate` (previously read afterward, only for quote/figure/date-mismatch checks) so this text is available at validation time. The threshold is exposed as `empty_extraction_min_words` (`watchdog configure`) rather than fixed in code, since 500 is a heuristic guess calibrated against corpus-v1 (smallest real document: a 5-page order at ~1,200 words) — a domain with unusually terse-but-substantive documents may need a different value, and there is no way to derive it automatically. Reusing the existing error-list mechanism means the failure path itself needed no new plumbing: `_simple_extract`'s repair loop already re-asks the model once with a repair note on any post-flight rejection, so a flaky empty response now gets one automatic second attempt before anything is lost; if the retry is still empty, the document fails loudly (`status: failed`, logged as `FAILED` with the reason) instead of silently succeeding with nothing in it. Sectioned extraction gets the hard failure but not the repair retry — the emptiness isn't section-1-owned the way D152's `morgue_entity_id` gap is, so `_repairable_by_section1` correctly declines to retry it, and the document fails straight to `_failed/` for a manual `watchdog ingest` retry.

**Tradeoff:** the threshold is a heuristic, not a proof — a genuinely fact-free document with 500+ words of source text (unlikely in this domain, but not impossible: a lengthy boilerplate appendix, a long disclaimer) will now fail post-flight and need a manual look, or a raised `empty_extraction_min_words`, rather than silently passing through empty. Accepted because the alternative — as this incident showed — is a billed, unflagged extraction that looks identical to a working one until someone happens to read the vault note, which is a worse failure mode for a tool whose whole job is not missing things.

### D154 — `write_vault._defang` extended from name/title to every free-text field written into a note (issue #508)

D78 (#305) routed entity `name` and document `title` through `_defang` before wikilink interpolation, since a hostile value could close a wikilink early and forge a second one. A #508 review of prompt-injection exposure on the deterministic side found the same interpolation risk in fields D78 didn't reach: `_role_line`'s `role['relationship']` sits in the same Markdown line as a real wikilink, and `_render_evidence_fragments`'s `claim`/`reason`/`quote` are written straight into an entity note's Analysis section. `quote` is the sharpest of these — it's meant to be verbatim source text, so a document's author has direct, unfiltered control over its contents, unlike a name or title the model itself derives.

All four now route through the same `_defang` wrapper used since D78; no new mechanism, just closing gaps in an established one. `_defang`'s docstring was widened accordingly.

**Tradeoff:** none beyond D78's own (a literal `[[`/`]]` in legitimate claim/quote/reason text gets a cosmetic space inserted) — this is strictly a coverage extension of an already-accepted mechanism.

### D155 — `merge.merge_extractions` derives `morgue_entity_id` deterministically when section 1 leaves it empty (issue #505)

D152 gave sectioned extraction a repair retry when post-flight rejects on `morgue_entity_id`/`morgue_document_type` — but a retry is still one more model call for a field only section 1 is ever asked to supply, and it still fails the document outright if that retry also comes up empty. `morgue_document_type` turns out already to have a stronger safety net: `orchestrate._stamp_document` unconditionally derives it from `document_type` (`slugify(doc.get("document_type") or "") or "document"`), so it can't actually reach post-flight empty regardless of what section 1 returns — D152's repair path for that field has been dead code since it was added, discovered while updating this change's tests. `morgue_entity_id` had no equivalent: `write_vault` uses it raw as the morgue folder segment, and nothing downstream of extraction ever supplies a fallback value.

Deciding *which* entity a document is about is a reading-comprehension call the extractor is well-placed to make with the whole document in front of it — the real gap isn't judgment, it's that a single missed field on section 1 has no second source to draw from. `merge_extractions` now fills that gap itself, after unioning every section's entities and facts: if no section supplied `morgue_entity_id`, derive it from the entity mentioned in the most `key_facts` (the closest available proxy for "primarily about"), falling back to the first entity encountered if no fact carries an entity tag. It stays `None` — still a post-flight failure, correctly, since the repair retry is the only thing that can help there — when the whole document has no entities at all to derive anything from.

This doesn't fully replace D152's repair path; it narrows what still needs it down to that one all-sections-zero-entities case. It also doesn't need to worry about picking an id that's about to be folded into a different canonical one during pre-commit reconciliation — issue #513 makes that remap cover `morgue_entity_id` too, so any staleness here (same as in the model's own answer) gets corrected before commit regardless of which of the two supplied the value.

**Tradeoff:** "most-mentioned entity" is a heuristic, not the model's judgment — on a document with two comparably prominent entities and a fact-count tie, the derived id could reasonably have gone either way. Accepted because getting it "slightly wrong" only misfiles the source document into a plausible-but-imperfect morgue folder (recoverable later), never touches an extracted fact, and is strictly better than the alternative this issue was filed over: a single missed field on section 1 failing the whole document outright.

### D156 — `run_benchmark.py` gets a pre-flight vault-staleness gate and a resilient report path; `cmd_extract`/`cmd_ingest` gain `non_interactive` (issue #494)

A 4-arm `extractor` run hung on arm 4: its vault had 5 documents staged from an earlier cancelled run, so `cmd_extract` hit the two-phase `dig`/`bark` "a previous batch is pending finalization" prompt — a blocking `input()` call underneath `interactive.pick()`. Because `run_benchmark.py` drives `cmd_extract` through `_quiet()` (stdout captured so the underlying pipeline's own verbose output doesn't clutter the terse per-arm line), the prompt's text was captured along with everything else — invisible on the terminal, but stdin was still listening. Ctrl+C at that point raised a bare `KeyboardInterrupt` outside the async SIGINT-trap scope that makes Ctrl+C graceful during real extraction (`orchestrate.py`'s `signal.add_signal_handler`), which killed `run_benchmark.py` before it ever reached `bench_report.write_run(...)` — losing the report for a run where 3 of 4 arms had real, complete, paid-for results already safe on disk.

Two independent fixes, addressing the two distinct failures: staleness went undetected until deep into one arm's turn, and the runner had no floor under an unexpected interrupt.

**Pre-flight staleness gate.** `run_benchmark.py` now computes every vault this run's selected stages/arms will target (`planned_arm_vaults`, mirroring `main`'s own stage-gating without creating or seeding anything) and checks each for an existing queue, `.watchdog/tmp/result_*.json` (pending finalization), a `batch-pending.json`, or already-extracted documents (`_stale_reason`). Any hit refuses the *entire* run before any vault is touched or preview computed, naming every stale vault and the `rm -rf` to clear it — rather than `seed_arm_vault`'s existing reseed-refusal, which only fires per-arm, mid-loop, potentially after earlier arms already spent real money.

**`non_interactive` closes the design mismatch, not just this one gap.** Even with the gate above, a programmatic caller reaching a prompt built for a human is a mismatch worth closing at the source — `cmd_ingest` (and `cmd_extract`, its thin `dig` wrapper) now take a `non_interactive` kwarg that fails loud (`sys.exit`, caught by the arm runner and turned into a normal failed-arm result) instead of blocking on the pending-finalization pick, and skips the quarantined-documents requeue offer instead of blocking on that confirm. `run_benchmark.py` passes `non_interactive=True` on every `cmd_extract` call. This is a backstop behind the pre-flight gate, not a replacement for it — the gate is what actually prevents the scenario in normal operation.

**Report survives an interrupt or crash.** `bench_report.write_run(...)` was previously only reached if the arm loop in `main()` completed normally or broke via the *designed* `result.cancelled` path. The loop is now wrapped in `try`/`except (KeyboardInterrupt, Exception)`; either one prints what completed and falls through to scoring/`write_run` against whatever `results` accumulated, returning exit code 130 or 1 respectively instead of losing the run's output to a bare traceback.

**Tradeoff:** the staleness gate is conservative — it refuses on any sign of prior state, including a vault a human left behind for their *own* future inspection, not just a genuinely broken one; the existing `rm -rf` remedy in `BENCHMARKING.md` already covers this, so no new operational cost. `non_interactive`'s failure mode (an unattended run stops on an unexpected pending batch rather than guessing merge/discard) is deliberate: a script must never choose on the operator's behalf.

### D157 — `_extract_sectioned` checkpoints each section to disk and resumes from it on retry (issue #498)

Before this change, `_extract_sectioned` held every section's result only in memory for the life of one call: a rate limit, a Ctrl-C, or a post-flight rejection that exhausts D152's repair retry all discarded every already-succeeded section's paid-for result, and the next attempt started over from section 1. For a document split into many sections (the scenario #490's investigation measured directly, before its own fixes landed — D147/D149/D150/D151 already cut the typical case from ~22 sections to ~6), that meant re-paying for most of a document's extraction over one flaky call.

Each section's parsed result is now written to `.watchdog/tmp/section_ex_{sha}_{index:02d}.json` as soon as that section's call succeeds — reusing the exact naming convention `abort.py`'s cleanup glob already expected (until now, nothing wrote files matching it in the live async pipeline; it dates to an older synchronous flow). `_load_section_checkpoints` replays a *contiguous* prefix of these on the next attempt, but only sections whose checkpointed metadata (index/label/`pages_path`) exactly matches the freshly recomputed plan at the same position — `section.run()` is deterministic, so an unchanged plan reproduces identical section dicts; any mismatch (a changed budget/model/backend between attempts, or a different section count) means the plan moved, and everything from that point on is re-extracted rather than risk merging content across a section boundary it was never actually extracted from. Per-section cost is tracked in the same checkpoint (`cost_usd`) so a resumed run's total still reflects calls paid for in an earlier attempt, including a repaired section 1's cumulative cost across both its original and repair calls.

Checkpoints are cleared once post-flight finally succeeds — both inside `_extract_sectioned` itself (the common case) and, belt-and-braces, in `_finish_extraction` (covers a document that leaves checkpoints from a failed sectioned attempt, then later succeeds via a *different* path on retry, e.g. whole-document extraction). They deliberately survive the automatic-failure path: `abort.run` gained a `keep_section_checkpoints` parameter, `False` by default (preserving its existing behaviour, including the explicit `watchdog ingest-abort` command, which still means "reset this document entirely"), and `orchestrate._fail` — the only other caller — passes `True`, since an automatic failure should still let the next `watchdog dig` resume rather than start cold.

`build_section_prompt`'s cache TTL default moved from the implicit 5 minutes to `"1h"` (mirroring the batch-submission path's existing override, #214) — checkpointing makes a multi-minute-to-multi-hour gap between a document's sections a normal, designed scenario rather than an edge case, and the resumed section's model call would otherwise almost always miss the prompt cache on the stable instructions+skill prefix.

**Tradeoff:** the metadata-equality resume guard is conservative by design — a plan that moved for any reason discards the *entire* checkpoint prefix rather than trying to salvage a partial match, even sections that would have stayed identical. Accepted because a wrong guess here would risk silently merging one section's content against a different one's boundary, which is a correctness bug, not a savings-left-on-the-table one; re-extracting everything is always safe.

### D158 — `document_requests` are content-keyed vault-wide, not per source document (issue #416)

D111 deliberately keyed a request's id on the source document plus the normalized `what` text, so two filings citing the same artifact ("the transcript") each got their own ledger entry, traceable to the document that named it. In practice this meant volume scaled with citation count, not with distinct artifacts: a six-file ingestion in the same matter produced 26 ledger entries, most of them the same handful of real-world documents cited more than once across filings, cluttering `requests.md` with rows the journalist has to individually resolve for what is, to them, one thing to go get.

`resolutions.request_id` drops the source-document scoping — a request's id is now `request:<sha1[:12] of the normalized what>` alone, so the same wording from any document in the vault converges on one ledger entry. Traceability isn't lost: `requests.record` now appends the citing document to that entry's `sources` list (`{sha256, filename, document_note}`) instead of dropping the second citation, and `requests.md`'s "Referenced in" line lists every citing document. One checkbox now closes the request regardless of how many documents named it.

**Tradeoff:** matching is still exact-string on the normalized `what` (same as D111's within-document dedup, just widened in scope) — two documents describing the same real-world artifact in materially different wording still land as separate entries, and in principle two *different* artifacts that happen to be phrased identically could wrongly collapse into one. Accepted for the same reason D111 accepted it at document scope: a wrong exact-string merge is a much narrower failure mode than fuzzy/semantic matching, and worth it against the noise of citation-count-scaled duplicates. No ledger migration was needed — the project has no production vaults yet.

### D159 — A model pass judges near-duplicate document requests; Python performs the merge (issue #416)

D158 fixed exact-text repeats, but checking it against the real `run_benchmark.py` corpus vaults (10 vaults, 292 recorded requests, same Laurentian University CCAA case documents processed by different extractor models) showed exact-string matching collapsed **zero** of them — every real duplicate was paraphrased. A hand-verified sample in one vault found the "Affidavit of Dr. Robert Haché sworn January 30, 2021" cited four different ways across four filings, including a 2020/2021 year drift, none sharing normalized text. A from-scratch deterministic heuristic (TF-IDF cosine over `type`/`what`/`likely_source`, IDF-weighted, plus a same-date bonus) was prototyped and tested against that same vault before deciding anything: it caught every verified real duplicate cluster, but also ranked a false positive (two unrelated documents that happened to both mention "March") *above* several true positives, and missed a real duplicate (two differently-worded creditor lists) that scored well below threshold. On data this sparse (dozens of short, human-written strings per vault), no fixed threshold cleanly separates signal from noise — confirmed empirically, not assumed.

`orchestrate._post_ingest` gains a step (5b, between the lead sweep and `write_requests`) that, when a run recorded at least one new open request and more than one request is open, sends every currently-open request (index, type, wording, likely source) to a model call (`schemas.REQUEST_DEDUP`, `request_dedup.md`) and asks it to group indices that name the same real-world document — explicitly warned against collapsing same-type/same-date/same-person requests that are nonetheless different documents (the two concrete false-positive patterns the heuristic hit). `orchestrate._apply_request_dedup` validates the returned indices (mirroring `_select_kept`'s discipline for `TIMELINE_DEDUP`) and calls `requests.merge_duplicates`, which folds each duplicate's `sources` onto the survivor and carries forward any prior resolution via `resolutions.remap_rid` so an already-resolved paraphrase doesn't reappear as newly open.

This is the same code/model split §I1 already uses for entity reconciliation and `TIMELINE_DEDUP`/`TIMELINE_PRECISION_MATCH` — the model answers only *which* entries are the same, Python performs every write — so it does not weaken I1. It does narrow D111's specific "a document request is never re-fed into any later model prompt" claim: open requests' text is now shown to one more model call, though only to judge sameness among themselves, never as context for prose generation or extraction. Gating on "this run added something new" keeps the common case (nothing new to reconsider) free, matching the discipline the 2b timeline-precision gate already established.

**Tradeoff:** cost and latency — one extra call on any ingest that adds a request while others are already open, and the call's size grows with how many requests are open, unbounded (a vault that accumulates hundreds of open requests over a long investigation pays for the whole list every time, not just the new ones); accepted for now as genuinely cheap relative to extraction, revisit if a real vault's request count grows large enough to matter. No per-stage CLI override or `finalizer_*_model` config key was added (`finalizer_overrides["request_dedup_model"/"request_dedup_backend"]` exists for programmatic/benchmark use, falling back to `post_model`/`post_backend`) — deliberately smaller surface than the four `--finalizer-<stage>-model` flags, since nothing asked for that knob yet; it is a one-line addition to `_FINALIZER_STAGES` later if it turns out to be needed. And because it can silently merge (not just flag), a wrong verdict is a real failure mode, not a cosmetic one — mitigated by the prompt's explicit false-positive warnings (drawn from the heuristic's concrete failures) and "when in doubt, keep both" instruction, but not eliminated; watch for reports of a folded request that shouldn't have been.

### D160 — Pre-commit entity-id reconciliation now also rewrites `morgue_entity_id` and `key_facts[].entities` (issue #513)

Both halves of pre-commit entity-id reconciliation — `write_vault._reconcile_entity_ids`'s deterministic exact-name fold (#403 phase 2) and `reconcile._rewrite_staged_ids`'s staged half of a confirmed AI-driven merge (#403 phase 3) — only ever rewrote `entities[].id` and `role.target_id` when an id got folded onto a different canonical one. Two other fields name an entity id by the same convention but sat outside that scope: `morgue_entity_id` (the top-level field `write_vault` uses to build the morgue file path) and `document.key_facts[].entities` (the per-fact entity tags postflight's fact-to-entity fan-out reads). If the entity a document was filed under, or a fact was tagged against, got folded into a different id later in the same batch, both went stale — e.g. a document ending up filed at `morgue/ernst-and-young-inc/...` even though that entity's note now lives under `ernst-young-inc` (D155 flagged this gap as pending work when it landed `morgue_entity_id`'s own empty-value fallback).

This isn't a new judgment call for either pass to make — deciding *which* entity a document is primarily about, or which two entities are duplicates, was already settled by the time these functions run (exact-name matching for the fold, the model's confirmed merge for reconciliation). The fix is the same remap dictionary each pass already computes, applied to two more fields: `_reconcile_entity_ids` now returns its `old_id → new_id` map instead of only mutating in place, and `orchestrate._batch_exact_fold` applies it to `morgue_entity_id`/`key_facts[].entities` alongside the entities it already folds; `_rewrite_staged_ids` does the equivalent inline for its single `merge_id → keep_id` pair. Both stay purely deterministic — no new model call, consistent with I1.

### D161 — `extractor_effort`/`finalizer_effort` extended to `xhigh`/`max`; `model_catalog.yaml`'s new `effort_levels` field becomes the single source of truth for effort capability, and an unsupported level now always fails loud (issue #518)

D36 deliberately left `xhigh`/`max` unexposed, on the assumption they were Opus-only and the knob's job was spending *less*. Two things had changed since: OpenAI's GPT-5.6 family exposes `reasoning_effort` up to `max` (needed to re-benchmark Luna at higher effort now that its price dropped ~80%, #509), and Anthropic's own `output_config.effort` now defines `xhigh`/`max` too — but coverage is per-model, not a flat "Claude supports it": Sonnet 4.6 takes `max` but not `xhigh`; Opus 4.8 takes both.

The first design gated only the two new levels, on a hand-rolled per-provider check, leaving the original `low`/`medium`/`high` on their pre-existing behaviour: silently dropped wherever a model didn't support them (Haiku, a chat-tier OpenAI model, DeepSeek, local, OpenRouter). Watchdog is pre-production, so nothing depends on that silence — keeping two different failure behaviours for old vs. new levels was arbitrary, not load-bearing, and the fix folds them into one: **every** unsupported effort request now raises `ModelError` with a clear message, regardless of level. This also let the whole thing collapse onto one source of truth instead of four separate per-provider functions (`_claude_effort`/`_openai_effort`/`_no_effort`/`_gemini_effort`) plus a hardcoded `_EFFORT_UNSUPPORTED` set: `model_catalog.yaml` gets a new `effort_levels` field per model (alongside the pricing/context-window/reasoning fields already there), and `model_client._resolve_effort` checks the requested level against it directly. A catalogued model with no `effort_levels` entry (Haiku, DeepSeek) has none at all — the field's *absence* is the fact, not a separate flag. An uncatalogued id (a local/OpenRouter model, or a raw OpenAI id newer than the catalog) falls back to a conservative provider-wide default: an OpenAI id recognized as a reasoning model via the existing `reasoning_fallback` table gets `low`/`medium`/`high` only (not `xhigh`/`max`, unconfirmed for anything but the catalogued GPT-5.6 family); Gemini gets `low`/`medium`/`high` unconditionally (a real provider-wide fact, not a guess); everything else gets none. Claude's `high`≡default sentinel is the one remaining special case in `_resolve_effort` — it's a value-mapping quirk (sending `"high"` and omitting the param are equivalent), not a capability gap, so it stays separate from the support check.

Making every level loud surfaced one real regression before it shipped: `extractor_effort` (unlike `finalizer_effort`) has always carried a baked-in implicit default — `medium`, per D26's benchmark finding — applied via `config.get("extractor_effort", "medium")` whether or not the user ever touched the setting. Under a uniform loud-fail gate, that default would break the documented "route `extractor_model` to Haiku for cheap batches" workflow outright: every extraction would raise, because Haiku takes no effort at all, and the user asked for none of this — they only changed the model. `cmd/ingest.py`'s `_effort()` now distinguishes the two cases explicitly: an *explicit* flag/config value is the user's own call and is passed straight through to fail loud downstream exactly as intended; the *implicit* `default="medium"` is applied only when `model_client.effort_supported(backend, model, "medium")` confirms the resolved model actually takes it, and silently omitted otherwise — an implicit default adapting to what's actually configured is not the same silent behaviour being removed above, since nothing the user typed is ever swallowed.

**Tradeoff:** `effort_levels` needs an explicit list on every catalog model that has any effort control — no cross-model inheritance, matching how pricing is already repeated per row rather than deduplicated. `xhigh`/`max` cost meaningfully more than `high`. The CLI/`watchdog configure` validation (`cli.py`/`cmd/ingest.py`/`cmd/setup.py`) still only checks a value is one of the five known level *strings*, not whether the model supports it — that real check lives once, in `_resolve_effort`, rather than duplicated at every syntax-validation site.

### D162 — `watchdog auth` mode switches also auto-tune `extract_concurrency`; the metered-path default rises from 5 to 20 (issue #493)

D136's auto-tune (#400) only fired from `setup_auth_interactive`, the one-time `watchdog setup` wizard. In practice, switching Claude auth mode happens through `watchdog auth`'s own picker far more often than through initial setup — e.g. the benchmark backend A/B protocol in BENCHMARKING.md walks through switching to api-key mode and back to subscription via `watchdog auth` repeatedly. Every one of those later switches back to subscription skipped the tune entirely, silently reintroducing the throttling D136 was built to prevent whenever `extract_concurrency` had ever been raised above 3 — including simply by `watchdog setup` originally running under api-key mode, which never touches the subscription branch at all.

`_pick_anthropic_mode_interactive` now calls `_maybe_tune_concurrency_for_subscription` under the same guard D136 already established: only when switching *to* subscription, and only when `extractor_model` actually resolves to the `anthropic` provider (D136's "declined metered routing" condition, expressed here as "not already routed elsewhere" — the two call sites reach the same state by different means, since `watchdog auth` has no metered-ingestion offer of its own to decline).

The mirror-image gap surfaced immediately: nothing undid the tune on the way back out. Once `extract_concurrency: 3` is written, it is indistinguishable from a deliberate `watchdog configure` choice — D136's own "never overwrite an explicit value" guard, which protects the user's choices, also means nothing would ever raise it again on its own. A user who auto-tuned to 3 on subscription and later switched to an api-key would silently keep running extraction at concurrency 3 on a metered key with no such constraint, forever, until they noticed and fixed it by hand. `_maybe_restore_concurrency_from_subscription` closes this the same way the tune itself is scoped: it clears `extract_concurrency` from config only when the stored value is *exactly* `_SUBSCRIPTION_CONCURRENCY` (3) — a coincidentally-matching manual choice of 3 is indistinguishable from the auto-tune and is left alone, same asymmetry the tune already accepts in the other direction. It runs from both switch-to-api-key sites: `watchdog auth`'s picker, and `watchdog setup`'s api-key branch (covering the case where a prior `watchdog setup` run left the subscription tune in place and a later run picks api-key instead).

Separately: #493 also flagged that the metered-path default of 5 was never itself measured, unlike D136's subscription value of 3, which traces to an observed throttling incident. Checking official provider rate-limit documentation (not guessed): Anthropic's API "Start" tier — the default, lowest tier — allows 1,000 RPM for Sonnet/Haiku; OpenAI's Tier 1 (reached after any successful payment) is reported at roughly 500 RPM. Both comfortably clear a concurrency of 20 given that extraction calls process full document pages and take several seconds each, well under the ~1.2s (Claude) or ~2.4s (OpenAI) per-call ceiling that would be needed to actually hit those floors at that concurrency. DeepSeek publishes account-level concurrency limits (500–2,500), not RPM, so it isn't a constraint either. The default rises from 5 to 20 on that basis — a real but non-account-specific floor, since watchdog cannot read a user's actual negotiated rate limit.

**Tradeoff:** the new default of 20 is still a guess relative to any individual account's actual tier — Gemini's own lowest paid tier (150–300 RPM) is tighter than Anthropic's or OpenAI's and was excluded from this default only because it wasn't the binding constraint being solved for; a user on a low OpenAI/Gemini tier who hits 429s should lower it with `watchdog configure extract_concurrency`, same as before. `extract_concurrency` also remains a single global knob shared across every metered provider (`cmd/ingest.py`'s `concurrency = ... or config.get("extract_concurrency") or 20`), not a per-provider one informed by the model catalog — that stayed out of scope here since it would require encoding tier-floor guesses per provider into `model_catalog.yaml` rather than fixing the specific auth-switch gap and default-value gap #493 raised.

### D163 — `_agent_query` opts every call out of claude.ai connectors, telemetry, error reporting, and other non-essential CLI traffic (issue #491)

Under api-key auth, the `claude-agent-sdk` backend printed a stderr warning ("claude.ai connectors are disabled because ANTHROPIC_API_KEY … takes precedence") once per call, since the underlying CLI harness checks connector eligibility on every session startup regardless of whether the call actually uses any tools. `_agent_query`'s calls are headless, single-turn, `tools=[]`/`setting_sources=[]` completions (D145) — claude.ai connectors were never reachable from them in the first place, under either auth mode. The same reasoning extends further: this backend spins up a fresh CLI subprocess per document, and the CLI's own telemetry and error-reporting traffic serves no purpose in that shape of call — and is worth actively avoiding, since a crash report could in principle carry prompt fragments from documents that are often privileged or confidential.

`ClaudeAgentOptions.env` is merged over the subprocess's inherited environment (confirmed against the installed `claude-agent-sdk` transport), so `_agent_query` now always sets four env vars in that dict: `ENABLE_CLAUDEAI_MCP_SERVERS=false` (routes the CLI's connector-eligibility check onto its already-existing "disabled via env var" branch, which logs at debug level instead of printing the visible warning — a targeted opt-out, not a blanket stderr suppression that could also hide a genuine crash traceback), plus the documented `DISABLE_TELEMETRY=1`, `DISABLE_ERROR_REPORTING=1`, and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (per code.claude.com/docs/en/env-vars).

**Tradeoff:** `ENABLE_CLAUDEAI_MCP_SERVERS` is undocumented — reverse-engineered from the installed CLI binary's strings, not a published SDK option — so it could be renamed or removed in a future `claude-agent-sdk`/CLI release; if that happens the warning simply comes back (a cosmetic regression, not a functional one). The other three are officially documented and stable. None of the four touch anything these calls use — no bash tool, no IDE, no MCP servers, no subagents — so there's no coverage this trades away.

### D164 — Model-response fixtures are auto-captured during benchmark runs, not hand-authored (issue #352)

#352 originally proposed a hand-curated library of recorded backend responses (truncation, malformed JSON, schema drift, pagination continuation) so `test_model_client.py` could pin the deterministic code around the model without live calls. Revisited before any of it was built: `benchmarks/run_benchmark.py` already runs every backend against `corpus-v1` (public court filings, no PII risk) and is the one place these conditions occur for real, so hand-authoring synthetic examples would duplicate a signal the harness already produces.

`model_client.py`'s existing choke points for each condition — `_is_truncated`'s check in `acomplete_json`, the `parsed is None` branch, `_prune_unknown`'s per-round removed-keys result, and `_complete_with_pagination`'s continuation loop — now each call `fixture_capture.capture(...)`, a module that is a no-op unless a benchmark run has called `fixture_capture.enable()`. `run_benchmark.py` enables it only around a confirmed, real (non-`--estimate-only`) run, writing to a local gitignored `benchmarks/.fixture-capture/` scratch directory, and disables it (via `finally`) whether the run finishes, is interrupted, or crashes. **Tradeoff:** `capture()`'s no-op check runs unconditionally on every `acomplete_json` call in production, including real `watchdog ingest` runs — negligible cost (one `is None` check), but it means `model_client.py`, otherwise a pure backend adapter, now has a side-channel hook baked in. The guardrail against that hook ever firing against real (non-benchmark) document content is purely operational — nothing in `model_client.py` itself refuses a `backend`/`task` combination — so it depends on production code paths never calling `fixture_capture.enable()`, not on a structural barrier. Conditions that don't occur often on well-behaved documents (e.g. truncation) may still need an occasional deliberately-tight token cap during a benchmark run to force them, rather than waiting for one to happen organically.

### D166 — Benchmark cost preview borrows a $/token ratio from archived runs of the same model/effort/backend, falling back to a documented static ratio, instead of always reading the (always-empty) target vault (issue #478)

Every benchmark arm targets a freshly seeded vault (`BENCHMARKING.md`: "every condition is its own fresh vault, never reuse a vault"), but `ingest_setup.cost_estimate`/`finalize_cost_estimate`'s $/token ratio and `_output_token_ratio`'s output:input ratio (D72, D143) both read *that same vault's own* `usage-<ts>.json` history — which a benchmark arm vault never has. The cost preview `run_benchmark.py`'s own docstring commits to ("this tool computes and prints the full cost preview for every arm up front... it never spends money silently") was structurally incapable of pricing anything, for every arm, every time.

Fix, in two parts. First, `cost_estimate`/`finalize_cost_estimate` gained an optional `usage_files` parameter that replaces the internal `orchestrate.usage_files(vault)` scan when given — a minimal, backward-compatible seam (default `None` preserves every existing caller's behaviour) rather than duplicating either function's pricing arithmetic in the benchmark harness. Second, a new `benchmarks/cost_reference.py` supplies what to pass through it: `reference_usage_files` scans every prior benchmark run's archived `artifacts/<vault>/usage/usage-*.json` (written by `bench_report.write_run` after every real run) for one whose calls all match the *exact* model, effort, **and backend** of the arm being estimated, and `fallback_estimate` prices directly against `model_catalog.yaml`'s list rate, scaled by a small hand-seeded per-effort output ratio, only when no archived run matches at all. `confirm_run` marks a fallback-priced arm `(rough projection, no matching run history yet)` rather than showing it indistinguishably from a run-calibrated range.

Backend is part of the match key, not just model+effort: the same model metered through `claude-batch` (50% off) vs `claude-api` prices completely differently, so borrowing across backends would misprice by the backend gap on top of whatever the model/effort variance already is. Effort is part of the match key for the reason a follow-up comment on #478 raised with real data: the same model (`gpt-5.6-luna`) swung its measured output:input ratio ~4x across low/medium/high effort alone on an identical corpus — a ratio borrowed from the wrong effort tier isn't a rough approximation, it's off by multiples in a predictable direction.

**Tradeoff:** the static fallback table (`DEFAULT_OUTPUT_RATIO_BY_EFFORT`) is seeded from a single model's measured behaviour — an order-of-magnitude placeholder, explicitly documented as such, not a calibrated figure; nothing says another model's verbosity scales with effort the same way. It only fires for a model/effort/backend combination that has never been benchmarked at all, so its accuracy matters least exactly when it's used most (a brand-new arm nobody has real numbers for yet) and least when real archived data already exists to replace it. `reference_usage_files` also does a full filesystem walk of every prior run's artifacts on every preview — fine at current benchmark-history volume, would need an index if the archive grows large enough for the glob itself to matter.

### D167 — The OpenAI reasoning-model output ceiling scales with `effort` instead of D108's flat 48K, and a starved (zero-visible-output) truncation is reported distinctly from a partial one (issue #354)

A benchmark sweep of `openai:gpt-5.4-mini` at effort low/medium/high (`benchmarks/2026-08-03-1459/`) failed 4/6 documents at `high`, 1/6 at `medium`, 0/6 at `low`, all with the same truncation error. The captured fixtures (`benchmarks/.fixture-capture/truncation-*.json`) showed why: `completion_tokens_details.reasoning_tokens` equalled the full `completion_tokens` count, and `text` was empty — the model spent its entire output budget on invisible chain-of-thought and was cut off before writing any answer at all, exactly the failure mode OpenAI's own reasoning guide warns can happen "before any visible output tokens are produced." D108's flat `_OPENAI_REASONING_MAX_TOKENS = 48000` ceiling ignored `effort` entirely, even though reasoning volume is almost entirely a function of it (the same document measured ~3.8K reasoning tokens at low, ~12.6K at medium, 48K+ at high) — a flat number either starves `high`/`xhigh`/`max` or wastes headroom at `low`. The visible answer was never the binding constraint (final merged extractions ran 7–9K estimated tokens at every effort level), so the fix raises the reasoning reserve, not the answer budget.

The flat constant is replaced by `_OPENAI_REASONING_RESERVE`, a per-effort-level reserve (`low`: 16K, `medium`: 48K, `high`: 80K, `xhigh`/`max`: 100K) added on top of the existing 16K visible-answer task budget — 32K/64K/96K/116K/116K, all under the gpt-5-mini class's documented 128K output-token limit. `_task_max_tokens` gains an `effort` parameter (default `None`, treated as medium) so every existing call site keeps working unchanged; `acomplete_json` threads its already-resolved `effort_arg` through. `output_ceiling_for_sectioning`'s OpenAI-reasoning branch is deliberately left alone — sectioning still plans against the base 16K task budget, since the JSON itself can never count on the reasoning share regardless of how large that share is allowed to get.

Separately, `acomplete_json`'s truncation branch now distinguishes the two failure shapes: empty visible text (any provider) gets a message naming the reasoning-token count when reported and suggesting a lower `extractor_effort`, instead of the old "output truncated at the model's max-token ceiling" wording, which implied a partial answer existed and pointed at the wrong fix (re-sectioning). A genuinely partial response keeps the original message unchanged. `orchestrate._record_usage` and `_usage_totals` also gained a `reasoning_tokens` field (from `completion_tokens_details.reasoning_tokens`, only when non-zero — OpenAI reports a 0 there for its chat models, which says no more than the key's absence) — the diagnostic signal for this whole investigation had been arriving on every OpenAI call since D108 and being discarded; `watchdog usage` now surfaces it as a per-call note.

**Tradeoff:** a bigger reserve means a runaway reasoning call can burn more tokens before hitting the ceiling — accepted because today's failure burns the entire 48K (or more) for a zero-token answer; a call that actually needs the larger reserve now has a chance to finish instead of guaranteed-failing. The per-effort figures are a reasoned scale-up from one document's measured totals, not a calibrated table across models — the same caveat D108's original 48K guess carried, now attached to five numbers instead of one.
